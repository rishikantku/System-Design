The official module

Authoritative

Coding with AI (CWAI) · 60 minutes · AI assisted

Solve software engineering problems using strong computer-science fundamentals while effectively incorporating AI into your development workflow. One or more coding problems involving common data structures, algorithms and problem-solving techniques.

What they evaluate

  • Apply strong engineering fundamentals to solve technical problems
  • Use AI intentionally to support and accelerate your workflow
  • Critically evaluate AI-generated output rather than accepting it at face value
  • Identify issues, make improvements and iterate when appropriate
  • Clearly communicate technical decisions and trade-offs
  • Deliver solutions that are correct, maintainable and well-reasoned

What to expect

  • Designing an appropriate solution
  • Writing clean and correct code
  • Validating your implementation
  • Communicating your technical decisions throughout
  • You are expected to use AI — it is not optional in this module
  • You own the final solution: understand it, validate it, explain it, fix it

How to run it

  • Conducted in CoderPad using its built-in AI Assist feature — a conversational assistant
  • Use it to explore approaches, generate or refine code, debug, create test cases, iterate
  • No prescribed workflow: reason first then accelerate, or explore with AI then refine yourself
  • It is not a prompt-engineering test
  • The interviewer may interrupt to ask about your thought process and how you are using AI

The model

What is LinkedIn actually testing?

What changes when typing is free

Two different loops

Traditional coding round

Problem → Think → Code → Test → Optimise

AI-assisted round

Understand → Clarify → Design → Decide what to delegate → Prompt → Inspect output → Validate → Test → Debug → Absorb a requirement change → Refactor → Reason about production → Explain the trade-offs

Blue steps are yours alone. The assistant can help with the grey ones.

AI is a tool, not a substitute for engineering judgement. You may let it type almost everything. You may not let it decide anything you cannot defend.

Typing is no longer the bottleneck

In a normal round, writing a correct LRU takes most of the 45 minutes, so finishing it is the signal. Here an assistant produces a plausible one in thirty seconds. Finishing stops being evidence of anything. The interviewer has to look somewhere else for signal, and they look at the decisions around the code: what you asked for, what you accepted, what you caught.

The interviewer gets more code to judge, not less

A LinkedIn employee put it bluntly: "it's a lot more code to write". Because the typing is cheap, the problem is bigger, and the requirements keep arriving. You will be extending code you did not fully write, which is a reading skill as much as a writing one.

Your judgement is now visible

In CoderPad the AI conversation sits on screen next to your code. Every prompt is evidence of how you decompose a problem. Every accepted answer is evidence of what you checked. A silent paste is evidence too.

Follow-ups decide the result

Every source agrees the follow-ups are where the round is won: concurrency, synchronisation, scale, "how would you productionise this?". Candidates who spend 35 minutes getting the first version working run out of room for the part that is actually scored.

Playbook

LinkedIn AI Coding — Interview Playbook

15 parts · each links to its detail below
1

What the round tests

Engineering fundamentals, used through an assistant. The pack lists six things: fundamentals; intentional AI use; critical evaluation of AI output; iterating on issues; communicating decisions and trade-offs; and a correct, maintainable, well-reasoned result. Note what is not on that list: speed of prompting, number of prompts, or cleverness with the tool. Production thinking is not in the pack's list, but every candidate report says the follow-ups go there.

2

Likely interview format

60 minutes in CoderPad with AI Assist (pack). The editor is in the middle, the chat panel is on the right, and you copy code across yourself (reported). Expect a familiar problem, then requirements added one at a time, then a concurrency or production pivot (reported). You may instead be handed existing code with a bug (reported once, ≈Mar 2026). The pack says "one or more coding problems", so plan for a second, smaller problem if the first finishes early.

3

How to use AI

For things you can verify faster than you can write: implementing a design you specified, boilerplate (parsing, model classes, test scaffolding), alternative approaches to compare, a second pair of eyes on a named class of bug, and a complexity check. Each use should have a stated purpose you could say out loud.

4

How not to use AI

Not to choose the data structure, the invariant, the synchronization boundary or the API contract. Not to "solve the problem". Not to re-ask a question until the answer looks right. Not to explain code to the interviewer for you. If you find yourself reading output to learn what your design is, you have handed over the wrong thing.

5

Prompting strategy

Context, constraint, output shape. Give it your interface. Tell it what must not change. Ask for only the piece you need. Ask it to state assumptions before writing code. Prefer several small prompts you can verify over one large one you cannot. Templates are below.

6

Code-review strategy

Read before running. Check in this order, because this is the order the bugs cost you: (1) does it do what the contract says on the edges; (2) the complexity, against the target you stated; (3) shared state and thread safety; (4) behaviour on bad input; (5) resource growth. Say each check out loud in one sentence.

7

Testing strategy

Happy path, boundaries, empty, invalid, duplicates, large, concurrent. Write the two or three that pin the core invariant yourself. Let the assistant generate the rest, then audit every expected value — a generated test with a wrong expectation is worse than no test. Inject time (IClock) and randomness (Func<int>) so tests are deterministic.

8

Debugging strategy

Reproduce first: a failing test before any change. Form two hypotheses, not one. Read the code path for the failing input. Use the assistant for hypotheses, never for the fix you have not understood. After the fix, keep the test.

9

Requirement-change strategy

Restate the change. Name the component it touches and the ones it does not. Change the smallest thing. Keep the old tests passing; add new ones. If the change does not fit the design, say so and say what you would refactor — that is a Staff signal, not a failure.

10

Concurrency strategy

Ask "what happens if two threads run this at once?" for every method that writes — including reads that write, like an LRU Get. Name the shared state. Name the invariant that spans it. That invariant is your synchronization boundary. Start with one lock; say what you would do when it contends (shard, read-mostly structures, lock-free counters). Full section below.

11

Productionisation strategy

Bounded memory, bounded latency, observable behaviour, safe failure. For each: what grows without limit; what can block; what you would measure; what happens when the dependency is slow or down. Give a priority order, not a list.

12

Time-management strategy

The most-reported failure is spending too long on the first version. Have a working, tested first version by about minute 25 of 60. If you are stuck on a mechanical piece for more than two minutes, delegate it; if an assistant answer is wrong twice, write it yourself.

13

Common failure modes

Silent pasting; letting the assistant choose the design; accepting a wrong complexity; tests with wrong expectations; restarting on each follow-up; overengineering a small addition; running out of time before the concurrency question. Bad-versus-good examples are below.

14

Staff-level behaviours

Owning decisions out loud. Naming the invariant. Pricing trade-offs. Changing the smallest component. Rejecting at least one AI suggestion with a reason. Raising the production concern before being asked — once, briefly, then returning to the task.

15

Mock interview framework

Ten rounds per problem on the simulator page — problem, implement, requirement change, test, "would you ship this?", then five follow-up levels (correctness, complexity, concurrency, scale, production) — timed against the 60-minute module and scored on the Staff standard: 15 dimensions, 7 AI-collaboration checks, eight headline scores out of 10, with gates that make blind acceptance of AI output fail.

Workflow

The core workflow — eight steps

Understand → design → delegate → generate → review → test → modify → defend
1

Step 1 — Understand

0–5 min
  • Restate the problem in one sentence, out loud.
  • List the operations and what each returns, including on a miss.
  • Write down the constraints you have been given and the ones you are assuming.
  • Ask the two or three clarifying questions that change the code.
"So this is a cache with two reasons to forget: capacity and time. Before I write anything — does a re-put renew the TTL, and does an expired entry still count toward capacity?"
AI here
Usually none. If the statement is long or the starter code is unfamiliar, it is fine to ask the assistant to summarise the code — then check the summary against the code.
Trap
Pasting the statement into the assistant before you have read it. The pack allows exploring with AI first; it does not reward skipping the reading.
2

Step 2 — Design

5–10 min
  • Write the interface — signatures only — in the editor.
  • Name the data structures and why each one is there.
  • State the invariant the structure maintains.
  • State the complexity target.
  • Say how you will test it.
"Dictionary for lookup, LinkedList for recency; the invariant is that both hold the same keys. O(1) for both operations. I'll test capacity one, update-in-place, and eviction after a read."
AI here
Optional: "Give me two other ways to structure this and their complexity — no code." Useful at Staff level because it shows you considered alternatives.
Trap
Letting the assistant pick the data structure. That is the decision being scored.
3

Step 3 — Decide what to delegate

no fixed slot
  • Delegate: implementation of a design you specified, boilerplate, parsing, test scaffolding, alternative approaches, bug hunts, complexity review.
  • Keep: the data structure choice, the invariant, the synchronization boundary, the API contract, the decision about what "correct" means.
"I'll have it write the list manipulation — that's mechanical. The eviction rule I'll check by hand."
AI here
The test of a good delegation: could you check the answer in less time than writing it yourself? If not, write it yourself.
Trap
"Solve this problem completely." You will spend the next ten minutes reading code you did not ask for.
4

Step 4 — Generate

10–20 min
  • Give context (the interface you wrote), constraints (complexity, no new public members), and the output shape (only this method; a diff; no prose).
"I'm giving it my interface and asking only for Put, keeping the field names."
AI here
See the prompt templates below. A precise prompt is shorter to verify, which is the real time saving.
Trap
Re-prompting the same request with small wording changes, hoping. If the second answer is wrong, write it yourself.
5

Step 5 — Review

as you go
  • Read it before running it. Out loud, briefly.
  • Check: correctness on the edges, complexity, thread safety, API behaviour on bad input, error handling, resource use.
  • Look for the defects assistants produce on this kind of problem (each question below lists them).
"It used ConcurrentDictionary. That protects the map, not the recency list, so this isn't thread-safe — I'm rejecting it."
AI here
Ask it to review its own output for one named class of bug. Never "is this correct?" — it will say yes.
Trap
Running it, seeing green, and moving on. Tests you did not write test what the assistant thought of.
6

Step 6 — Test

20–28 min
  • Run the happy path, then the boundaries: empty, one, capacity, duplicate, invalid.
  • Ask the assistant for adversarial tests, then read each one and check the expected value yourself.
  • Add the one test that would have caught the bug you fixed.
"It generated eight tests. Two of these expected values are wrong — it thinks an expired key still counts as present."
AI here
Generated tests are the highest-value delegation in the round — and generated expected values are the most common thing to be wrong.
Trap
Treating generated tests as verification. A test with a wrong expected value verifies the bug.
7

Step 7 — Modify

28–45 min
  • Restate the new requirement and which part of the design it touches.
  • Change that part. Keep the tests that still apply; add ones for the new behaviour.
  • Say what did not need to change — that is the evidence the design was right.
"TTL only touches the entry and the read path. Eviction and the list don't change, which is why I kept recency separate."
AI here
"The requirement changed to X. Modify the existing code with minimal disruption; list which members change and which do not."
Trap
Asking the assistant to regenerate the whole class with the new requirement. You lose the code you already verified.
8

Step 8 — Defend

45–60 min
  • Why this approach, this data structure, this locking strategy.
  • What happens under concurrency, at scale, when the dependency is slow, when memory grows.
  • What you would change for production, in priority order.
"One lock is right until it shows up in a profile. The next step is sharding by key hash, which makes LRU approximate — I'd accept that and measure the hit-ratio cost."
AI here
None. This part is yours.
Trap
"The AI chose it." Every accepted line is your decision now.
Minutes are for the 60-minute module and are my plan, not a published one. Step 5 has no slot because it happens every time code arrives.
Prompting

AI prompting for the interview

8 templates, each with why it works
The patternEvery template has the same three parts: context (your code or interface), constraint (what must not change), output shape (only this; no rewrite; list first). The why under each is the part to learn — the words will differ on the day.
ImplementationAfter you have written the interface and named the structures.
Implement the following C# interface. Before writing code, state your assumptions, the data structures you will use and the expected complexity of each method. Keep the implementation minimal and testable: no extra public members, no logging, no comments beyond one line per method.

<paste interface + your field declarations>
  • "State assumptions first" makes the assistant expose the decisions it would otherwise make silently — you catch a wrong assumption before reading 60 lines.
  • "No extra public members" stops it widening your API, which you would then have to defend.
  • Pasting your own field declarations pins the data structures — the design stays yours.
ReviewWhen you have code — yours or generated — and want a second reader.
Review this implementation for correctness, edge cases, complexity and concurrency issues. Do not rewrite it. First list the problems you find, most severe first, each with the input that triggers it.

<paste code>
  • "Do not rewrite it" keeps the output short enough to verify, and keeps your code your code.
  • "The input that triggers it" turns a vague concern into a test you can run in ten seconds — and exposes false alarms.
  • Ranking by severity tells you which finding to spend your limited minutes on.
TestsAfter the first working version.
Generate adversarial test cases for this implementation as plain assertions: boundary conditions, duplicate keys, empty input, capacity one, and concurrent access where applicable. For each test, state in a comment why the expected value is correct.

<paste code + the contract you stated>
  • "Why the expected value is correct" is the line that matters: it makes the assistant's reasoning checkable, and wrong expected values are its most common test defect.
  • Plain assertions rather than a framework — CoderPad may not have xUnit, and you do not want to debug test infrastructure.
  • Giving it your contract stops it testing behaviour you never promised.
OptimisationWhen the interviewer says "now assume millions of requests" or you see a hotspot.
Analyse this implementation for performance bottlenecks under <workload>. Suggest improvements without changing the external API. For each, give the complexity before and after and what it costs.
  • Naming the workload stops generic advice. "Read-heavy, 10:1" and "write-heavy" have different answers.
  • "Without changing the external API" is the constraint a Staff engineer imposes on every refactor.
  • "What it costs" forces the trade-off into the answer — which is what you will have to say out loud anyway.
ConcurrencyThe concurrency follow-up, which you should expect.
Analyse this implementation for race conditions and thread-safety issues if Get and Put are called from multiple threads. For each race, give the interleaving that breaks it. Then identify the smallest synchronization boundary that preserves correctness. Do not write code yet.
  • "The interleaving that breaks it" separates a real race from a vague worry, and gives you the sentence to say.
  • "Smallest boundary" is the Staff-level question: not "add locks" but "where exactly".
  • "Do not write code yet" — you decide the boundary, then ask for it.
Requirement changeEvery time the interviewer adds something.
The requirements have changed: <new requirement>. Modify the existing design with minimal disruption. First list which types and members need to change and which do not, then show only the changed members.
  • Asking for the impact list first means you can disagree before any code exists.
  • "Only the changed members" protects everything you already verified.
  • The "which do not change" half is the evidence your original design was right — say it to the interviewer.
Bug huntA test fails and the cause is not obvious within a minute.
This test fails: <test>. Expected <x>, got <y>. Here is the code. Give the two most likely causes, each with the line responsible and the reasoning. Do not fix it.
  • Two hypotheses, not one: stops it anchoring on the first idea and gives you a choice to make.
  • "Do not fix it" — you verify the cause, then fix it yourself or ask for the specific fix.
Explain unfamiliar codeDebug-and-extend rounds that start with existing code.
Summarise what this class does, its invariants, and any method whose behaviour looks inconsistent with the others. Quote line numbers.
  • Line numbers make the summary checkable against the code in seconds.
  • "Inconsistent with the others" is a cheap way to find the planted bug in a debug-first round.
Failure modes

What gets candidates rejected

12 patterns · bad versus good

Asking AI to solve everything immediately

BAD AI USAGE
"Implement an LRU cache with TTL that is thread-safe." → 80 lines, three decisions you never made, ten minutes reading them.
GOOD AI USAGE
Write the interface and the invariant. "Implement Put for this interface, O(1), keep my field names." → 15 lines you can check in one pass.

Copy-pasting code without understanding it

BAD AI USAGE
Pastes the response, runs it, says "looks good".
GOOD AI USAGE
Pastes it, then: "It evicts from _order.Last — that's the LRU end, right. It doesn't remove from the map on update — fine, the key is the same."

Not checking generated code

BAD AI USAGE
Accepts a "thread-safe" version that swapped Dictionary for ConcurrentDictionary.
GOOD AI USAGE
"ConcurrentDictionary makes each map call atomic, but Get also moves a list node. Two threads can corrupt the list. Rejecting."

Missing edge cases

BAD AI USAGE
Tests put-then-get.
GOOD AI USAGE
Tests capacity one, update-in-place, eviction after a read, an expired key exactly at the TTL boundary, and an empty cache.

Accepting incorrect complexity

BAD AI USAGE
The assistant says GetRank is O(1); the candidate repeats it.
GOOD AI USAGE
"It walks the frequency map — that's O(distinct frequencies). Not O(1). Fine for this; an order-statistics tree gives log n."

Not running tests

BAD AI USAGE
Explains why the code is correct instead of running it.
GOOD AI USAGE
Runs the tests first, then explains — and lets a failure change the plan.

Not explaining generated code

Why P0
The best-attested AI-round question: one first-hand AI-round report, two guides, three more LinkedIn reports of the same family. Every follow-up you are likely to get is in this one ladder.
1 · Problem

Build a key-value cache with a fixed capacity. When it is full and a new key arrives, evict the least recently used entry. Both reads and writes count as use. Then the requirements grow: entries expire, many threads call it, traffic reaches millions of requests.

2 · Requirements
  • TryGet(key, out value) and Put(key, value), both O(1)
  • A read is a use — it changes the eviction order
  • Re-putting an existing key updates it in place and counts as a use
  • Capacity ≤ 0 is rejected at construction
3 · Key insight
Two jobs need two structures. A dictionary finds a key in O(1) but has no order. A linked list keeps order and moves a node in O(1) — if you already hold the node. Store the list node in the dictionary and you get both. Everything after that — TTL, threads, shards — is a change to one of those two structures, never a rewrite.
4 · Design

Dictionary<TKey, LinkedListNode<…>> for lookup; LinkedList<…> for recency, most recent at First. Invariant: both hold exactly the same keys. Every method that touches one touches the other before returning. That one sentence is also the synchronization boundary later.

5 · Data structures — and why each C# type
TypeWhy
Dictionary<TKey, LinkedListNode<T>>O(1) lookup that returns the list handle, so unlinking needs no search
LinkedList<T>O(1) Remove(node), AddFirst, RemoveLast; the BCL type is one less thing to get wrong than a hand-rolled list

6 · Algorithm
  • Get: look up; if absent, miss. (TTL: if expired, remove from both and miss.) Move the node to the front. Return.
  • Put: if present, update, move to front, return. If full, evict (TTL: prefer an expired entry near the cold end; else Last). Add to front and to the map.
  • Sweep (TTL): walk at most budget nodes from the cold end, removing expired ones. Bounded work per call.

Level 1 — plain LRU

// Level 1. The textbook structure: a map for lookup, a list for recency. // LinkedList<T> is used instead of a hand-rolled node list because its LinkedListNode handle // gives O(1) unlink, and in an interview the BCL type is one less thing to get wrong. public class LruCache<TKey, TValue> { private readonly int _capacity; private readonly Dictionary<TKey, LinkedListNode<(TKey Key, TValue Value)>> _map; private readonly LinkedList<(TKey Key, TValue Value)> _order = new(); // First = most recent public LruCache(int capacity) { if (capacity <= 0) throw new ArgumentOutOfRangeException(nameof(capacity)); _capacity = capacity; _map = new Dictionary<TKey, LinkedListNode<(TKey, TValue)>>(capacity); } public int Count => _map.Count; public bool TryGet(TKey key, out TValue value) { if (!_map.TryGetValue(key, out var node)) { value = default; return false; } _order.Remove(node); // a read is a use: move to the front _order.AddFirst(node); value = node.Value.Value; return true; } public void Put(TKey key, TValue value) { if (_map.TryGetValue(key, out var node)) { node.Value = (key, value); // update in place, then treat it as a use _order.Remove(node); _order.AddFirst(node); return; } if (_map.Count == _capacity) { var victim = _order.Last; // least recently used _order.RemoveLast(); _map.Remove(victim.Value.Key); } _map[key] = _order.AddFirst((key, value)); } }

Level 2 — TTL with lazy expiry and a bounded sweep

A01_Lru.cs
// Level 2. Every entry carries an absolute expiry. Expiry is checked lazily on read, and a // bounded sweep reclaims entries that are never read again, so memory does not grow without // limit and no single call pays for scanning the whole cache. public class LruTtlCache<TKey, TValue> { private sealed class Entry { public TKey Key; public TValue Value; public long ExpiresAt; } private int _capacity; private readonly IClock _clock; private readonly Dictionary<TKey, LinkedListNode<Entry>> _map; private readonly LinkedList<Entry> _order = new(); public LruTtlCache(int capacity, IClock clock) { if (capacity <= 0) throw new ArgumentOutOfRangeException(nameof(capacity)); _capacity = capacity; _clock = clock ?? throw new ArgumentNullException(nameof(clock)); _map = new Dictionary<TKey, LinkedListNode<Entry>>(capacity); } public int Count => _map.Count; public bool TryGet(TKey key, out TValue value) { value = default; if (!_map.TryGetValue(key, out var node)) return false; if (_clock.NowMs >= node.Value.ExpiresAt) { // dead on read: reclaim it now Remove(node); return false; } _order.Remove(node); _order.AddFirst(node); value = node.Value.Value; return true; } public void Put(TKey key, TValue value, long ttlMs) { if (ttlMs <= 0) throw new ArgumentOutOfRangeException(nameof(ttlMs)); long expiresAt = _clock.NowMs + ttlMs; if (_map.TryGetValue(key, out var node)) { node.Value.Value = value; node.Value.ExpiresAt = expiresAt; // a re-put renews the TTL — say so out loud _order.Remove(node); _order.AddFirst(node); return; } if (_map.Count == _capacity) EvictOne(); var entry = new Entry { Key = key, Value = value, ExpiresAt = expiresAt }; _map[key] = _order.AddFirst(entry); } // Prefer an expired victim if one is at the cold end; otherwise evict the LRU entry. // Looking at only a few entries keeps Put O(1) — a full scan for "any expired entry" would not. private void EvictOne() { long now = _clock.NowMs; var n = _order.Last; for (int i = 0; i < 4 && n != null; i++, n = n.Previous) if (now >= n.Value.ExpiresAt) { Remove(n); return; } Remove(_order.Last); } // Bounded, incremental cleanup: walks at most `budget` entries from the cold end. // Called from a timer or piggy-backed on writes. Returns how many it reclaimed. public int SweepExpired(int budget) { long now = _clock.NowMs; int reclaimed = 0; var n = _order.Last; while (n != null && budget-- > 0) { var prev = n.Previous; if (now >= n.Value.ExpiresAt) { Remove(n); reclaimed++; } n = prev; } return reclaimed; } // Resizing at runtime (memory pressure, or a config push). Shrinking evicts immediately — // expired entries first, then from the cold end — so Count never exceeds the new capacity. public void Resize(int capacity) { if (capacity <= 0) throw new ArgumentOutOfRangeException(nameof(capacity)); _capacity = capacity; while (_map.Count > _capacity) EvictOne(); } private void Remove(LinkedListNode<Entry> n) { _order.Remove(n); _map.Remove(n.Value.Key); } }

10 · Follow-ups — the ladder
  1. Implement LRU.
    Dictionary of list nodes + linked list. State the invariant. Test eviction after a read.
  2. Resize it at runtime.
    Shrinking evicts immediately — expired first, then from the cold end — until Count ≤ the new capacity. Growing just raises the bound. Resize in the listing; tested both ways.
  3. Add TTL.
    Absolute expiry per entry, injected clock, lazy check on read. Re-put renews. Decide and say whether an expired entry counts toward capacity until reclaimed.
  4. Make it thread-safe.
    One lock around each operation, because Get mutates the list. Reject ConcurrentDictionary alone — it protects the map, not the list.
  5. Millions of requests.
    The lock serialises everything. Shard by key hash, N independent caches. Each shard is exact LRU; the whole is approximate. Measure the hit-ratio cost.
  6. Expired-entry memory growth.
    Lazy expiry alone leaks keys that are never read again. Add a bounded sweep from the cold end, on a timer or piggy-backed on writes. Never a full scan under the lock.
  7. Memory limits, not entry counts.
    Entries vary in size: track a byte weight per entry and evict until under a byte budget. Under memory pressure (GC notifications, a container limit), Resize down.
  8. Hot keys and high contention.
    One hot key lands on one shard and one lock. Options: a small per-thread or read-replicated front cache for the hottest keys, or approximate recency so reads stop writing.
  9. Observability.
    Hit ratio, eviction rate split by reason (capacity vs expiry), expired-on-read rate, lock wait time, size in entries and bytes. Alert on a relative hit-ratio drop.
  10. Distribute it.
    Consistent hashing across nodes; a client-side or proxy router; replication only if a miss is expensive. This is now a design question — Memcached/Redis Cluster, and say when you would just use one.
11 · Concurrency

What happens if two threads run this at once? Shared state: the map and the list. The invariant spans both, so they must change together — one critical section per operation. Two threads in Get on different keys both call _order.Remove and AddFirst; without a lock the list's internal pointers interleave and corrupt. That is exactly what review exercise R3 does in 20/20 trials.

12 · Production
  • Bound memory: capacity in entries is not bytes — for variable-size values, cap by weight.
  • Hit ratio, eviction rate, expired-on-read rate as metrics; alert on hit-ratio drop.
  • A slow source behind the cache: collapse concurrent misses (cache the in-flight Lazy), and add a timeout.
  • Warm-up after deploy: a cold cache is a thundering herd on the source.

C# deep-dive — asked only if your solution uses it

Dictionary

Expected complexity? O(1) average for lookup, insert, remove; O(n) worst case if many keys collide. Enumeration is O(n) and order is not guaranteed.

How are collisions handled? Separate chaining, but without node objects: an int[] buckets of indices into an Entry[] array, each entry carrying its hash, key, value and a next index. Colliding keys form a chain through next.

What happens on resize? When the entries array is full it grows to a larger prime (about double) and every entry is rehashed into new buckets — O(n) for that insert, amortised O(1). Pre-size with the constructor capacity when you know n.

Memory behaviour? Removing does not shrink anything: freed slots go on a free list for reuse. TrimExcess() shrinks. A struct key that is large is copied into every entry.

LinkedList

Why LinkedList<T> for LRU? O(1) Remove(node), AddFirst, RemoveLast given a LinkedListNode<T> handle. Storing the handle in the dictionary avoids an O(n) search.

Is it thread-safe? No. Concurrent Remove/AddFirst corrupts its pointers (R3 corrupted in 20/20 runs).

lock

What exactly is synchronised? Only code that locks the same object. lock (x) is Monitor.Enter/Exit on x's object header, in a try/finally. It also acts as a full memory barrier, so writes inside are visible to the next locker.

Can this deadlock? Yes, with two locks taken in different orders (D5), or with a call out to unknown code while holding the lock. One lock and no callouts cannot deadlock. Monitor is re-entrant for the same thread.

How does contention affect throughput? Uncontended, a lock is tens of nanoseconds. Contended, threads spin briefly then block, causing context switches; throughput collapses toward one thread's worth. The fix is less work under the lock, or more locks (striping).

Anything to avoid locking on? this, a Type, a string — other code can lock them too. Use a private readonly object (or System.Threading.Lock in .NET 9+).

ConcurrentDictionary

Which operations are atomic? Each single call: TryAdd, TryRemove, TryUpdate (compare-and-swap on the value), TryGetValue, the indexer. AddOrUpdate/GetOrAdd atomically store — but see the next question.

Does a read take a lock? No — reads are lock-free. Writes lock one stripe of buckets (lock striping), not the whole table. Count and ToArray take all the locks, so avoid them on a hot path.

Is a read-modify-write across two calls safe? No. TryGetValue then d[k] = v + 1 is check-then-act (debugging exercise D4 lost ~80% of increments). Use AddOrUpdate, or a TryUpdate loop.

Do GetOrAdd / AddOrUpdate run the factory once? Not guaranteed: the delegate runs outside the lock and can run on several racing threads; only one result is stored. For an expensive factory, store Lazy<T> (review exercise R8).

C# deep-dive — asked only if your solution uses it

SortedSet / SortedDictionary

Complexity? Red-black tree: O(log n) insert, remove, lookup; in-order enumeration.

How do you get a floor (largest ≤ x)? GetViewBetween(min, x).Max — O(log n). There is no floorKey like Java's TreeMap.

LINQ

Deferred or immediate? Most operators (Where, Select, OrderBy) are deferred: nothing runs until enumeration. ToList, ToArray, Count(), First, Sum execute immediately. OrderBy is deferred but buffers everything when enumerated.

What does enumerating twice cost? The whole pipeline runs twice — including any I/O behind the source. Materialise once with ToList() if you need it twice.

Allocations? An enumerator per operator, plus delegate and closure allocations for captured variables. Negligible for setup code, measurable in a per-request hot path.

When is an explicit loop better? Hot paths, early exit with complex state, mutating as you go, or when you need to state complexity exactly — R5 hid an O(n log n) sort per call inside one readable line.

lock

What exactly is synchronised? Only code that locks the same object. lock (x) is Monitor.Enter/Exit on x's object header, in a try/finally. It also acts as a full memory barrier, so writes inside are visible to the next locker.

Can this deadlock? Yes, with two locks taken in different orders (D5), or with a call out to unknown code while holding the lock. One lock and no callouts cannot deadlock. Monitor is re-entrant for the same thread.

How does contention affect throughput? Uncontended, a lock is tens of nanoseconds. Contended, threads spin briefly then block, causing context switches; throughput collapses toward one thread's worth. The fix is less work under the lock, or more locks (striping).

Anything to avoid locking on? this, a Type, a string — other code can lock them too. Use a private readonly object (or System.Threading.Lock in .NET 9+).

C# deep-dive — asked only if your solution uses it

Dictionary

Expected complexity? O(1) average for lookup, insert, remove; O(n) worst case if many keys collide. Enumeration is O(n) and order is not guaranteed.

How are collisions handled? Separate chaining, but without node objects: an int[] buckets of indices into an Entry[] array, each entry carrying its hash, key, value and a next index. Colliding keys form a chain through next.

What happens on resize? When the entries array is full it grows to a larger prime (about double) and every entry is rehashed into new buckets — O(n) for that insert, amortised O(1). Pre-size with the constructor capacity when you know n.

Memory behaviour? Removing does not shrink anything: freed slots go on a free list for reuse. TrimExcess() shrinks. A struct key that is large is copied into every entry.

LINQ

Deferred or immediate? Most operators (Where, Select, OrderBy) are deferred: nothing runs until enumeration. ToList, ToArray, Count(), First, Sum execute immediately. OrderBy is deferred but buffers everything when enumerated.

What does enumerating twice cost? The whole pipeline runs twice — including any I/O behind the source. Materialise once with ToList() if you need it twice.

Allocations? An enumerator per operator, plus delegate and closure allocations for captured variables. Negligible for setup code, measurable in a per-request hot path.

When is an explicit loop better? Hot paths, early exit with complex state, mutating as you go, or when you need to state complexity exactly — R5 hid an O(n log n) sort per call inside one readable line.

async/await

Does async create a new thread? No. async lets a method be suspended; await on an incomplete task returns to the caller and schedules the rest as a continuation. No thread exists for the waiting.

What happens while awaiting I/O? The OS completes the I/O (I/O completion ports on Windows, epoll on Linux) and the continuation is queued to the thread pool or the captured context. The thread was free the whole time — that is the point.

How does cancellation work? Cooperatively. You pass a CancellationToken down; APIs that accept it observe it and throw OperationCanceledException. Nothing is aborted from outside. Blocked primitives need a registration to wake them (BoundedBlockingQueue does this).

Can you await inside a lock? No — the compiler forbids it, because the continuation may run on another thread. Use SemaphoreSlim.WaitAsync with Release in a finally (R12 is what happens without the finally).

// The production shape: Log() enqueues into a bounded channel and returns; one background // task drains it to the sinks. When the channel is full the NEWEST event is dropped and counted — // logging must never block the request path, and a drop counter is the honest signal. // // FullMode is Wait, not DropWrite, and that is deliberate. My first version used DropWrite and the // 10,000-thread test caught it: under DropWrite, TryWrite returns TRUE even when it drops the item, // so "accepted 10,000, dropped 0" was reported while 1,026 were written. Under Wait, a non-blocking // TryWrite returns false when full — which is the signal the drop counter needs. public sealed class AsyncLogger : IAsyncDisposable { private readonly Channel<string> _ch; private readonly ILogSink[] _sinks; private readonly Severity _min; private readonly Task _pump; private long _accepted, _dropped, _written, _sinkFailures; public AsyncLogger(Severity min, int capacity, params ILogSink[] sinks) { _min = min; _sinks = sinks; _ch = Channel.CreateBounded<string>(new BoundedChannelOptions(capacity) { FullMode = BoundedChannelFullMode.Wait, // TryWrite (never WriteAsync) returns false when full SingleReader = true, SingleWriter = false }); _pump = Task.Run(PumpAsync); } public bool Log(Severity sev, string msg) { if (sev < _min) return false; if (_ch.Writer.TryWrite($"{sev} {msg}")) { Interlocked.Increment(ref _accepted); return true; } Interlocked.Increment(ref _dropped); return false; } private async Task PumpAsync() { await foreach (var line in _ch.Reader.ReadAllAsync()) { foreach (var s in _sinks) { try { s.Write(line); } catch (Exception) { Interlocked.Increment(ref _sinkFailures); } // isolate, count, carry on } Interlocked.Increment(ref _written); } } public (long Accepted, long Dropped, long Written, long SinkFailures) Metrics => (Interlocked.Read(ref _accepted), Interlocked.Read(ref _dropped), Interlocked.Read(ref _written), Interlocked.Read(ref _sinkFailures)); // Shutdown: stop accepting, drain what was accepted, with a bound on how long we wait. public async ValueTask DisposeAsync() { _ch.Writer.TryComplete(); await Task.WhenAny(_pump, Task.Delay(TimeSpan.FromSeconds(5))); } }

How are collisions handled? Separate chaining, but without node objects: an int[] buckets of indices into an Entry[] array, each entry carrying its hash, key, value and a next index. Colliding keys form a chain through next.

What happens on resize? When the entries array is full it grows to a larger prime (about double) and every entry is rehashed into new buckets — O(n) for that insert, amortised O(1). Pre-size with the constructor capacity when you know n.

Memory behaviour? Removing does not shrink anything: freed slots go on a free list for reuse. TrimExcess() shrinks. A struct key that is large is copied into every entry.

lock

What exactly is synchronised? Only code that locks the same object. lock (x) is Monitor.Enter/Exit on x's object header, in a try/finally. It also acts as a full memory barrier, so writes inside are visible to the next locker.

Can this deadlock? Yes, with two locks taken in different orders (D5), or with a call out to unknown code while holding the lock. One lock and no callouts cannot deadlock. Monitor is re-entrant for the same thread.

How does contention affect throughput? Uncontended, a lock is tens of nanoseconds. Contended, threads spin briefly then block, causing context switches; throughput collapses toward one thread's worth. The fix is less work under the lock, or more locks (striping).

Anything to avoid locking on? this, a Type, a string — other code can lock them too. Use a private readonly object (or System.Threading.Lock in .NET 9+).

Channel / Interlocked / SemaphoreSlim

What does a bounded Channel do when full? Depends on FullMode. Wait: WriteAsync waits, TryWrite returns false. DropWrite/DropNewest/DropOldest: drops and TryWrite returns true (R14).

When Interlocked instead of a lock? A single-word update with no invariant tying it to other fields — counters. Two fields that must agree need a lock.

SemaphoreSlim vs lock? SemaphoreSlim can be awaited (WaitAsync) and counts beyond 1; it is not re-entrant and must be released in a finally.

async/await

Does async create a new thread? No. async lets a method be suspended; await on an incomplete task returns to the caller and schedules the rest as a continuation. No thread exists for the waiting.

What happens while awaiting I/O? The OS completes the I/O (I/O completion ports on Windows, epoll on Linux) and the continuation is queued to the thread pool or the captured context. The thread was free the whole time — that is the point.

How does cancellation work? Cooperatively. You pass a CancellationToken down; APIs that accept it observe it and throw OperationCanceledException. Nothing is aborted from outside. Blocked primitives need a registration to wake them (BoundedBlockingQueue does this).

Can you await inside a lock? No — the compiler forbids it, because the continuation may run on another thread. Use SemaphoreSlim.WaitAsync with Release in a finally (R12 is what happens without the finally).

That is how hit ratio is // normally measured — a miss is a trip to the slow thing behind the cache. public TValue GetOrLoad(TKey key, Func<TKey, TValue> load) { if (_lru.TryGet(key, out var v)) { _hits++; return v; } _misses++; v = load(key); if (_lru.Count == _capacity) _evictions++; _lru.Put(key, v); return v; } // Counters are plain longs because this class is single-threaded. Workloads and the simulator

public static class Workloads { // 0,1,2,…,n-1 repeated. With n > capacity, LRU hits NOTHING: every key is evicted just // before it is needed again. The classic LRU pathology — a scan larger than the cache. public static IEnumerable<int> Cyclic(int distinct, int length) { for (int i = 0; i < length; i++) yield return i % distinct; } // Uniform random over `distinct` keys: expected steady-state hit ratio ≈ capacity / distinct. public static IEnumerable<int> Uniform(int distinct, int length, int seed) { var r = new Random(seed); for (int i = 0; i < length; i++) yield return r.Next(distinct); } // Skewed (Zipf-like, s = 1): a few keys take most traffic, so a small cache does well. public static IEnumerable<int> Skewed(int distinct, int length, int seed) { var r = new Random(seed); var cdf = new double[distinct]; double sum = 0; for (int k = 0; k < distinct; k++) { sum += 1.0 / (k + 1); cdf[k] = sum; } for (int i = 0; i < length; i++) { double u = r.NextDouble() * sum; int idx = Array.BinarySearch(cdf, u); yield return idx >= 0 ? idx : ~idx; } } public static CacheStats Run(int capacity, IEnumerable<int> keys) { var c = new CountingLruCache<int, int>(capacity); foreach (var k in keys) c.GetOrLoad(k, x => x); return c.Stats; } }

LFU with GetRank

A03_LfuRank.cs
// A03 — LFU cache with GetRank(), LRU as the tie-breaker. Reported Feb 2026 (Hello Interview) // as the Staff-level variant of the AI round's cache question. // // Rank is defined as the key's position in KEEP order: rank 1 is the entry the cache would // evict last (highest frequency, most recent among equals); rank Count is the next victim. // State that definition before writing code — the statement does not fix it. public sealed class LfuRankCache<TKey, TValue> { private sealed class Entry { public TKey Key; public TValue Value; public int Freq; } private readonly int _capacity; private readonly Dictionary<TKey, LinkedListNode<Entry>> _byKey = new(); // frequency → entries at that frequency, First = most recent. One list per frequency // is what gives O(1) Get/Put: a touch moves a node from list f to list f+1. private readonly Dictionary<int, LinkedList<Entry>> _buckets = new(); // frequency → number of keys, kept sorted so GetRank can sum "everyone more frequent". private readonly SortedDictionary<int, int> _freqCounts = new(); private int _minFreq; public LfuRankCache(int capacity) { if (capacity <= 0) throw new ArgumentOutOfRangeException(nameof(capacity)); _capacity = capacity; } public int Count => _byKey.Count; public bool TryGet(TKey key, out TValue value) { if (!_byKey.TryGetValue(key, out var node)) { value = default; return false; } Touch(node); value = node.Value.Value; return true; } public void Put(TKey key, TValue value) { if (_byKey.TryGetValue(key, out var node)) { node.Value.Value = value; Touch(node); return; } if (_byKey.Count == _capacity) { var list = _buckets[_minFreq]; var victim = list.Last; // least recent among the least frequent Detach(victim); _byKey.Remove(victim.Value.Key); } var fresh = new LinkedListNode<Entry>(new Entry { Key = key, Value = value, Freq = 1 }); Attach(fresh); _byKey[key] = fresh; _minFreq = 1; // a new key always has the lowest frequency } // O(F + B): F = distinct frequencies above this key's, B = size of its own bucket. // Not O(1), and that is fine as long as it is said. An order-statistics tree gets O(log n). // GetRank does NOT count as a use — reading the rank must not change it. public int GetRank(TKey key) { if (!_byKey.TryGetValue(key, out var node)) return -1; int f = node.Value.Freq, rank = 1; foreach (var (freq, count) in _freqCounts) if (freq > f) rank += count; for (var n = _buckets[f].First; n != node; n = n.Next) rank++; return rank; } private void Touch(LinkedListNode<Entry> node) { int f = node.Value.Freq; Detach(node); if (f == _minFreq && !_buckets.ContainsKey(f)) _minFreq = f + 1; node.Value.Freq = f + 1; Attach(node); } private void Attach(LinkedListNode<Entry> node) { int f = node.Value.Freq; if (!_buckets.TryGetValue(f, out var list)) _buckets[f] = list = new LinkedList<Entry>(); list.AddFirst(node); _freqCounts[f] = _freqCounts.GetValueOrDefault(f) + 1; } // Empty buckets are deleted, not left behind: otherwise _minFreq bookkeeping and the // GetRank walk both slow down over time. private void Detach(LinkedListNode<Entry> node) { int f = node.Value.Freq; var list = _buckets[f]; list.Remove(node); if (list.Count == 0) _buckets.Remove(f); if (--_freqCounts[f] == 0) _freqCounts.Remove(f); } }

The follow-ups were: is the maze well formed including the // outer wall; generate a maze that always has a path; why did you choose the AI's approach; // how would you test each change; what would you change for production. public sealed class Maze { private readonly bool[,] _wall; // true = wall public int Rows { get; } public int Cols { get; } public (int R, int C) Start { get; } public (int R, int C) End { get; } public Maze(string[] rows) { if (rows == null || rows.Length == 0) throw new ArgumentException("empty maze"); Rows = rows.Length; Cols = rows[0].Length; if (rows.Any(r => r.Length != Cols)) throw new ArgumentException("ragged maze"); _wall = new bool[Rows, Cols]; for (int r = 0; r < Rows; r++) for (int c = 0; c < Cols; c++) { char ch = rows[r][c]; _wall[r, c] = ch == '#'; if (ch == 'S') Start = (r, c); if (ch == 'E') End = (r, c); } } public bool IsWall(int r, int c) => _wall[r, c]; // Well formed: the whole border is wall, except that S and E may sit on it as openings, // and S and E are distinct open cells. "Including the outer wall" was the reported wording. public bool IsWellFormed() { if (Rows < 3 || Cols < 3 || Start == End) return false; for (int r = 0; r < Rows; r++) for (int c = 0; c < Cols; c++) { bool border = r == 0 || c == 0 || r == Rows - 1 || c == Cols - 1; bool opening = (r, c) == Start || (r, c) == End; if (border && !opening && !_wall[r, c]) return false; } return !_wall[Start.R, Start.C] && !_wall[End.R, End.C]; } // BFS: fewest steps from S to E, or -1. Visited is marked when a cell is ENQUEUED. // Marking on dequeue still returns the right number, but lets the same cell enter the // queue many times — on an open grid that is the difference between O(cells) and much worse. public int ShortestPath() { var dist = new int[Rows, Cols]; for (int r = 0; r < Rows; r++) for (int c = 0; c < Cols; c++) dist[r, c] = -1; var q = new Queue<(int R, int C)>(); dist[Start.R, Start.C] = 0; q.Enqueue(Start); ReadOnlySpan<(int, int)> dirs = [(1, 0), (-1, 0), (0, 1), (0, -1)]; while (q.Count > 0) { var (r, c) = q.Dequeue(); if ((r, c) == End) return dist[r, c]; foreach (var (dr, dc) in dirs) { int nr = r + dr, nc = c + dc; if (nr < 0 || nc < 0 || nr >= Rows || nc >= Cols) continue; // bounds before indexing if (_wall[nr, nc] || dist[nr, nc] >= 0) continue; dist[nr, nc] = dist[r, c] + 1; q.Enqueue((nr, nc)); } } return -1; } // Extension: generate a maze that ALWAYS has a path. Randomised depth-first carving over a // grid of odd dimensions produces a spanning tree of the cells, so every open cell — // including S and E — is connected. Iterative, so a large maze cannot overflow the stack. public static Maze Generate(int rows, int cols, int seed) { if (rows < 5 || cols < 5 || rows % 2 == 0 || cols % 2 == 0) throw new ArgumentException("use odd dimensions >= 5"); var g = new char[rows, cols]; for (int r = 0; r < rows; r++) for (int c = 0; c < cols; c++) g[r, c] = '#'; var rnd = new Random(seed); var stack = new Stack<(int R, int C)>(); g[1, 1] = '.'; stack.Push((1, 1)); (int, int)[] steps = [(2, 0), (-2, 0), (0, 2), (0, -2)]; while (stack.Count > 0) { var (r, c) = stack.Peek(); var options = steps.Where(s => { int nr = r + s.Item1, nc = c + s.Item2; return nr > 0 && nc > 0 && nr < rows - 1 && nc < cols - 1 && g[nr, nc] == '#'; }).ToList(); if (options.Count == 0) { stack.Pop(); continue; } var (dr, dc) = options[rnd.Next(options.Count)]; g[r + dr / 2, c + dc / 2] = '.'; // knock down the wall between g[r + dr, c + dc] = '.'; stack.Push((r + dr, c + dc)); } g[1, 1] = 'S'; g[rows - 2, cols - 2] = 'E'; var lines = new string[rows]; for (int r = 0; r < rows; r++) { var row = new char[cols]; for (int c = 0; c < cols; c++) row[c] = g[r, c]; lines[r] = new string(row); } return new Maze(lines); } }

lock

What exactly is synchronised? Only code that locks the same object. lock (x) is Monitor.Enter/Exit on x's object header, in a try/finally. It also acts as a full memory barrier, so writes inside are visible to the next locker.

Can this deadlock? Yes, with two locks taken in different orders (D5), or with a call out to unknown code while holding the lock. One lock and no callouts cannot deadlock. Monitor is re-entrant for the same thread.

How does contention affect throughput? Uncontended, a lock is tens of nanoseconds. Contended, threads spin briefly then block, causing context switches; throughput collapses toward one thread's worth. The fix is less work under the lock, or more locks (striping).

Anything to avoid locking on? this, a Type, a string — other code can lock them too. Use a private readonly object (or System.Threading.Lock in .NET 9+).

async/await

Does async create a new thread? No. async lets a method be suspended; await on an incomplete task returns to the caller and schedules the rest as a continuation. No thread exists for the waiting.

What happens while awaiting I/O? The OS completes the I/O (I/O completion ports on Windows, epoll on Linux) and the continuation is queued to the thread pool or the captured context. The thread was free the whole time — that is the point.

How does cancellation work? Cooperatively. You pass a CancellationToken down; APIs that accept it observe it and throw OperationCanceledException. Nothing is aborted from outside. Blocked primitives need a registration to wake them (BoundedBlockingQueue does this).

Can you await inside a lock? No — the compiler forbids it, because the continuation may run on another thread. Use SemaphoreSlim.WaitAsync with Release in a finally (R12 is what happens without the finally).

1 · Problem

A bounded queue shared by producer and consumer threads: producers block when full, consumers block when empty. Then add cancellation and graceful shutdown.

2 · Requirements
  • Enqueue blocks while full
  • TryDequeue blocks while empty; returns false once completed and drained
  • CancellationToken on both
  • Complete() for shutdown
3 · Key insight
In production C# you say Channel.CreateBounded<T> and move on. Built by hand, everything rests on two rules: wait in a while loop (re-check the condition after every wake), and PulseAll when producers and consumers share one monitor (a Pulse can wake the wrong kind of waiter).
4 · Design

One object gate, a Queue<T>, a completed flag. Cancellation registers a callback that pulses the monitor, because Monitor.Wait cannot observe a token.

5 · Data structures — and why each C# type

6 · Algorithm
  • Enqueue: lock; while full and not completed: wait. Throw if cancelled or completed. Enqueue; PulseAll.
  • TryDequeue: lock; while empty and not completed: wait. If empty now, return false (completed). Dequeue; PulseAll.

// D01 — producer/consumer: a bounded blocking queue with cancellation and shutdown. // Concurrency is the most commonly reported pivot in the AI round; this is the primitive // most of those follow-ups reduce to. // // In production C# the answer is System.Threading.Channels.Channel.CreateBounded<T>. Say so // first. Then build it, because the interviewer wants to see you own the synchronization. public sealed class BoundedBlockingQueue<T> { private readonly Queue<T> _items = new(); private readonly int _capacity; private readonly object _gate = new(); private bool _completed; public BoundedBlockingQueue(int capacity) { if (capacity <= 0) throw new ArgumentOutOfRangeException(nameof(capacity)); _capacity = capacity; } // Blocks while full. Throws OperationCanceledException if cancelled, InvalidOperationException // if the queue was completed — a producer must not silently lose an item after shutdown. public void Enqueue(T item, CancellationToken ct = default) { using var reg = ct.Register(Wake); // Monitor.Wait has no token: wake waiters on cancel lock (_gate) { while (_items.Count == _capacity && !_completed) { // WHILE, not if: re-check after every wake ct.ThrowIfCancellationRequested(); Monitor.Wait(_gate); } ct.ThrowIfCancellationRequested(); if (_completed) throw new InvalidOperationException("queue is completed"); _items.Enqueue(item); Monitor.PulseAll(_gate); // PulseAll: producers and consumers share one monitor } } // Blocks while empty. Returns false once the queue is completed AND drained — that is the // shutdown signal a consumer loop needs, and the reason Complete() exists at all. public bool TryDequeue(out T item, CancellationToken ct = default) { using var reg = ct.Register(Wake); lock (_gate) { while (_items.Count == 0 && !_completed) { ct.ThrowIfCancellationRequested(); Monitor.Wait(_gate); } ct.ThrowIfCancellationRequested(); if (_items.Count == 0) { item = default; return false; } // completed and drained item = _items.Dequeue(); Monitor.PulseAll(_gate); return true; } } // Graceful shutdown: no new items, consumers drain what is left, then see false. public void Complete() { lock (_gate) { _completed = true; Monitor.PulseAll(_gate); } } public int Count { get { lock (_gate) return _items.Count; } } private void Wake() { lock (_gate) Monitor.PulseAll(_gate); } }

What does enumerating twice cost? The whole pipeline runs twice — including any I/O behind the source. Materialise once with ToList() if you need it twice.

Allocations? An enumerator per operator, plus delegate and closure allocations for captured variables. Negligible for setup code, measurable in a per-request hot path.

When is an explicit loop better? Hot paths, early exit with complex state, mutating as you go, or when you need to state complexity exactly — R5 hid an O(n log n) sort per call inside one readable line.

1 · Problem

Count events in the last five minutes, at high rates, from many threads.

2 · Requirements
  • Record(nowSecs), Count(nowSecs)
  • Memory bounded regardless of event rate
  • Thread-safe
3 · Key insight
You do not need every event's timestamp — you need counts per second. A ring of 300 one-second buckets, each tagged with the second it holds, is O(window) memory whatever the rate. A stale bucket is detected by its tag and reset on reuse.
4 · Design

Two arrays (stamp, count) indexed by second % window; one lock.

TypeWhy
long[] stamp, int[] countThe ring; the stamp detects stale slots

6 · Algorithm
  • Record: slot = now % W; if stamp[slot] ≠ now, reset it; count[slot] += n.
  • Count: sum slots whose stamp is in (now − W, now].

// C02 — a sliding-window event counter ("hits in the last 5 minutes"). PATTERN PRACTICE: // not a reported LinkedIn AI-round question. It is here because "metrics and counters" is the // natural production follow-up to the reported cache and data-processing problems, and it // is the smallest problem that forces a time-bucketing decision and a thread-safety decision. public sealed class WindowCounter { private readonly int _windowSecs; private readonly long[] _stamp; // which second each slot currently holds private readonly int[] _count; // events in that second private readonly object _gate = new(); // Memory is O(window), not O(events): one slot per second, reused as time moves on. // An exact-timestamp queue would hold every event for five minutes — at 10k events/s, // three million entries for a number nobody needs to millisecond precision. public WindowCounter(int windowSecs = 300) { if (windowSecs <= 0) throw new ArgumentOutOfRangeException(nameof(windowSecs)); _windowSecs = windowSecs; _stamp = new long[windowSecs]; _count = new int[windowSecs]; Array.Fill(_stamp, -1); } public void Record(long nowSecs, int n = 1) { int slot = (int)(nowSecs % _windowSecs); lock (_gate) { if (_stamp[slot] != nowSecs) { _stamp[slot] = nowSecs; _count[slot] = 0; } // slot was a stale second _count[slot] += n; } } // O(window) per read. If reads dominate, keep a running total and subtract slots as they // are recycled — that makes reads O(1) and writes do the bookkeeping. State which you chose. public long Count(long nowSecs) { long total = 0; lock (_gate) { for (int i = 0; i < _windowSecs; i++) if (_stamp[i] > nowSecs - _windowSecs && _stamp[i] <= nowSecs) total += _count[i]; } return total; } }

C# deep-dive — asked only if your solution uses it

lock

What exactly is synchronised? Only code that locks the same object. lock (x) is Monitor.Enter/Exit on x's object header, in a try/finally. It also acts as a full memory barrier, so writes inside are visible to the next locker.

Can this deadlock? Yes, with two locks taken in different orders (D5), or with a call out to unknown code while holding the lock. One lock and no callouts cannot deadlock. Monitor is re-entrant for the same thread.

How does contention affect throughput? Uncontended, a lock is tens of nanoseconds. Contended, threads spin briefly then block, causing context switches; throughput collapses toward one thread's worth. The fix is less work under the lock, or more locks (striping).

Anything to avoid locking on? this, a Type, a string — other code can lock them too. Use a private readonly object (or System.Threading.Lock in .NET 9+).

Channel / Interlocked / SemaphoreSlim

What does a bounded Channel do when full? Depends on FullMode. Wait: WriteAsync waits, TryWrite returns false. DropWrite/DropNewest/DropOldest: drops and TryWrite returns true (R14).

When Interlocked instead of a lock? A single-word update with no invariant tying it to other fields — counters. Two fields that must agree need a lock.

SemaphoreSlim vs lock? SemaphoreSlim can be awaited (WaitAsync) and counts beyond 1; it is not re-entrant and must be released in a finally.

Ask two questions of every method that writes — including reads that write: "What happens if two threads execute this simultaneously?" and "Where exactly is the synchronization boundary?" The boundary is the invariant: whatever must be true across several fields must change inside one critical section.

Topics

Lock granularity

One lock for the whole cache is correct and simple. It serialises everything. Striping by key hash (N shards, N locks) cuts contention by roughly N, and costs global ordering — each shard is exact LRU, the cache is approximately LRU. Finer than that (a lock per node) is where deadlocks and bugs live; say why you are not going there.

Reader/writer trade-offs

A reader/writer lock helps when reads are frequent, writes rare, and reads genuinely do not mutate. An LRU read mutates (it moves the node), so a reader/writer lock does not help it. Saying that out loud is a strong signal. Read-mostly alternatives: approximate recency (a "touched" bit, CLOCK), or buffering reads and applying them in batches (what Caffeine does).

Deadlocks and lock ordering

Two locks taken in different orders by different threads will eventually deadlock. Fix by a global order (by id), by never calling out while holding a lock, or by not needing two locks. Debugging exercise D5 reproduces one.

Atomic operations

Check-then-act across two calls is a race even if each call is atomic — ContainsKey then indexer, TryGetValue then assignment. The fix is one atomic call (AddOrUpdate) or one lock around both. Debugging exercises D2 and D4.

Concurrent collections

They make each call atomic. They do not make your sequence of calls atomic, and they do not protect a second structure. That is why ConcurrentDictionary + LinkedList is not a thread-safe LRU (review exercise R3 corrupted in 20 of 20 trials).

Background cleanup

A sweeper that scans everything under the lock stalls every reader for the length of the scan. Bound the work per tick (a budget), or piggy-back a few entries of cleanup on each write. Review exercise R10.

Cancellation and shutdown

Every blocking call needs a way out: a CancellationToken (and a registration that wakes waiters), and a Complete() that lets consumers drain and exit. "How do you shut this down?" is a common production follow-up.

Slow dependencies

A read-through cache in front of a slow service turns a burst of misses into a burst of identical slow calls (a stampede). Cache the in-flight Lazy/Task, not just the value; add a timeout; decide what to serve when the dependency is down. Review exercise R8: eight concurrent first reads made eight calls.

C# deep-dive questions

When this comes upThe interviewer may ask how a C# feature you used actually behaves. Only when it is in your solution — this is not .NET trivia. Each answer below is tied to a defect elsewhere on this page where the behaviour bites.
Dictionary · 4 questions

Expected complexity?
O(1) average for lookup, insert, remove; O(n) worst case if many keys collide. Enumeration is O(n) and order is not guaranteed.

How are collisions handled?
Separate chaining, but without node objects: an int[] buckets of indices into an Entry[] array, each entry carrying its hash, key, value and a next index. Colliding keys form a chain through next.

What happens on resize?
When the entries array is full it grows to a larger prime (about double) and every entry is rehashed into new buckets — O(n) for that insert, amortised O(1). Pre-size with the constructor capacity when you know n.

Memory behaviour?
Removing does not shrink anything: freed slots go on a free list for reuse. TrimExcess() shrinks. A struct key that is large is copied into every entry.

ConcurrentDictionary · 4 questions

Which operations are atomic?
Each single call: TryAdd, TryRemove, TryUpdate (compare-and-swap on the value), TryGetValue, the indexer. AddOrUpdate/GetOrAdd atomically store — but see the next question.

Does a read take a lock?
No — reads are lock-free. Writes lock one stripe of buckets (lock striping), not the whole table. Count and ToArray take all the locks, so avoid them on a hot path.

Is a read-modify-write across two calls safe?
No. TryGetValue then d[k] = v + 1 is check-then-act (debugging exercise D4 lost ~80% of increments). Use AddOrUpdate, or a TryUpdate loop.

Do GetOrAdd / AddOrUpdate run the factory once?
Not guaranteed: the delegate runs outside the lock and can run on several racing threads; only one result is stored. For an expensive factory, store Lazy<T> (review exercise R8).

lock · 4 questions

What exactly is synchronised?
Only code that locks the same object. lock (x) is Monitor.Enter/Exit on x's object header, in a try/finally. It also acts as a full memory barrier, so writes inside are visible to the next locker.

Can this deadlock?
Yes, with two locks taken in different orders (D5), or with a call out to unknown code while holding the lock. One lock and no callouts cannot deadlock. Monitor is re-entrant for the same thread.

How does contention affect throughput?
Uncontended, a lock is tens of nanoseconds. Contended, threads spin briefly then block, causing context switches; throughput collapses toward one thread's worth. The fix is less work under the lock, or more locks (striping).

Anything to avoid locking on?
this, a Type, a string — other code can lock them too. Use a private readonly object (or System.Threading.Lock in .NET 9+).

async/await · 4 questions

Does async create a new thread?
No. async lets a method be suspended; await on an incomplete task returns to the caller and schedules the rest as a continuation. No thread exists for the waiting.

What happens while awaiting I/O?
The OS completes the I/O (I/O completion ports on Windows, epoll on Linux) and the continuation is queued to the thread pool or the captured context. The thread was free the whole time — that is the point.

How does cancellation work?
Cooperatively. You pass a CancellationToken down; APIs that accept it observe it and throw OperationCanceledException. Nothing is aborted from outside. Blocked primitives need a registration to wake them (BoundedBlockingQueue does this).

Can you await inside a lock?
No — the compiler forbids it, because the continuation may run on another thread. Use SemaphoreSlim.WaitAsync with Release in a finally (R12 is what happens without the finally).

LINQ · 4 questions

Deferred or immediate?
Most operators (Where, Select, OrderBy) are deferred: nothing runs until enumeration. ToList, ToArray, Count(), First, Sum execute immediately. OrderBy is deferred but buffers everything when enumerated.

What does enumerating twice cost?
The whole pipeline runs twice — including any I/O behind the source. Materialise once with ToList() if you need it twice.

Allocations?
An enumerator per operator, plus delegate and closure allocations for captured variables. Negligible for setup code, measurable in a per-request hot path.

When is an explicit loop better?
Hot paths, early exit with complex state, mutating as you go, or when you need to state complexity exactly — R5 hid an O(n log n) sort per call inside one readable line.

LinkedList · 2 questions

Why LinkedList<T> for LRU?
O(1) Remove(node), AddFirst, RemoveLast given a LinkedListNode<T> handle. Storing the handle in the dictionary avoids an O(n) search.

Is it thread-safe?
No. Concurrent Remove/AddFirst corrupts its pointers (R3 corrupted in 20/20 runs).

SortedSet / SortedDictionary · 2 questions

Complexity?
Red-black tree: O(log n) insert, remove, lookup; in-order enumeration.

How do you get a floor (largest ≤ x)?
GetViewBetween(min, x).Max — O(log n). There is no floorKey like Java's TreeMap.

Channel / Interlocked / SemaphoreSlim · 3 questions

What does a bounded Channel do when full?
Depends on FullMode. Wait: WriteAsync waits, TryWrite returns false. DropWrite/DropNewest/DropOldest: drops and TryWrite returns true (R14).

When Interlocked instead of a lock?
A single-word update with no invariant tying it to other fields — counters. Two fields that must agree need a lock.

SemaphoreSlim vs lock?
SemaphoreSlim can be awaited (WaitAsync) and counts beyond 1; it is not re-entrant and must be released in a finally.

LFU cache with GetRank() · Design · Caches35 min
Problem35 minutes

Implement a cache with Get, Put and GetRank(key), evicting the least frequently used entry and breaking ties by least recently used. GetRank returns the position of a key when entries are ordered by frequency (most frequent = rank 1). Get and Put should stay O(1).

Clarify firstbefore you touch the assistant
  • Is rank 1 the most frequent or the least?
  • What does GetRank return for a missing key — 0, -1, or an exception?
  • Does GetRank itself count as an access (does it change frequency)?
  • What is the capacity, and can it be zero?
  • Do ties in frequency need a defined rank order, or is any consistent order fine?
Your plan — write it before prompting
The structure is yoursDecide the structure before you type a prompt: a map key → node, a map frequency → doubly linked list of nodes, and a minFrequency counter. That gives O(1) get and put. Then be honest out loud that GetRank cannot be O(1) with that structure — ranking needs either a walk over frequency buckets (O(distinct frequencies)) or a separate order-statistics structure (a Fenwick tree over frequencies, O(log n)). Saying which trade you are making, before the assistant offers one, is the whole point of this round.
Prompts worth using
  • I am implementing an LFU cache in C#: Dictionary<TKey,Node>, Dictionary<int,LinkedList<Node>> by frequency, and a minFreq field. Write just the Put method, keeping O(1), and do not change my field names.
  • Now write xunit tests for: capacity 1, updating an existing key, eviction when two keys share the lowest frequency (LRU must lose), and GetRank on a missing key.
  • I need GetRank. Give me two options — walking frequency buckets, and a Fenwick tree over frequency counts — with the complexity of each. Do not write the code yet.
  • Review this method for off-by-one errors in the minFreq update after an eviction.
Verify — the tests you run yourself
  • Capacity 1 — put, put, get: the first key must be gone.
  • Two keys at frequency 1, one touched more recently: eviction must drop the other.
  • minFreq after evicting the last node of its bucket — does it reset to 1 on the next insert?
  • GetRank on a missing key, and on the only key.
  • GetRank after a Get (did frequency change, and did you say it would?).
Reference solution (C#)
public sealed class LfuCache<TKey, TValue> { private sealed class Node { public TKey Key; public TValue Value; public int Freq; public LinkedListNode<Node> Handle; // position inside its frequency list } private readonly int _capacity; private readonly Dictionary<TKey, Node> _byKey; private readonly Dictionary<int, LinkedList<Node>> _byFreq = new(); private readonly SortedDictionary<int, int> _countPerFreq = new(); // frequency -> how many keys (for GetRank) private int _minFreq; public LfuCache(int capacity) { if (capacity <= 0) throw new ArgumentOutOfRangeException(nameof(capacity)); _capacity = capacity; _byKey = new Dictionary<TKey, Node>(capacity); } public bool TryGet(TKey key, out TValue value) { if (!_byKey.TryGetValue(key, out var n)) { value = default; return false; } Touch(n); value = n.Value; return true; } public void Put(TKey key, TValue value) { if (_byKey.TryGetValue(key, out var existing)) { existing.Value = value; Touch(existing); return; } if (_byKey.Count == _capacity) { var victimList = _byFreq[_minFreq]; var victim = victimList.Last.Value; // least recently used within the lowest frequency victimList.RemoveLast(); if (victimList.Count == 0) _byFreq.Remove(_minFreq); Decrement(_minFreq); _byKey.Remove(victim.Key); } var node = new Node { Key = key, Value = value, Freq = 1 }; node.Handle = ListFor(1).AddFirst(node); _byKey[key] = node; Increment(1); _minFreq = 1; // a brand-new key always resets the floor } /// <summary>1 = most frequent. O(distinct frequencies) — say so, and offer the O(log n) variant.</summary> public int GetRank(TKey key) { if (!_byKey.TryGetValue(key, out var n)) return -1; int ahead = 0; foreach (var (freq, count) in _countPerFreq) // ascending if (freq > n.Freq) ahead += count; return ahead + 1; } private void Touch(Node n) { var list = _byFreq[n.Freq]; list.Remove(n.Handle); if (list.Count == 0) { _byFreq.Remove(n.Freq); if (_minFreq == n.Freq) _minFreq = n.Freq + 1; // the only place minFreq can advance } Decrement(n.Freq); n.Freq++; n.Handle = ListFor(n.Freq).AddFirst(n); Increment(n.Freq); } private LinkedList<Node> ListFor(int freq) => _byFreq.TryGetValue(freq, out var l) ? l : _byFreq[freq] = new LinkedList<Node>(); private void Increment(int freq) => _countPerFreq[freq] = _countPerFreq.GetValueOrDefault(freq) + 1; private void Decrement(int freq) { if (--_countPerFreq[freq] == 0) _countPerFreq.Remove(freq); } }

public IEnumerable<Chunk> Chunk(Document doc, int maxTokens = 512, int overlapTokens = 64) { foreach (var section in doc.Sections) { // structure first var units = SplitParagraphs(section.Text); // then paragraphs var buffer = new List<string>(); int tokens = 0, ordinal = 0; foreach (var unit in units) { var t = _tokenizer.Count(unit); if (t > maxTokens) { // a single huge paragraph foreach (var sentence in SplitSentences(unit)) foreach (var c in Pack(sentence, ref buffer, ref tokens, ref ordinal, section, maxTokens, overlapTokens)) yield return c; continue; } if (tokens + t > maxTokens && buffer.Count > 0) { yield return Emit(buffer, section, doc, ordinal++); buffer = Tail(buffer, overlapTokens); // keep the overlap tokens = _tokenizer.Count(string.Join("\n", buffer)); } buffer.Add(unit); tokens += t; } if (buffer.Count > 0) yield return Emit(buffer, section, doc, ordinal); } } private Chunk Emit(List<string> parts, Section s, Document d, int ordinal) => new() { Id = Hash($"{d.Id}|{s.Path}|{ordinal}"), // deterministic: stable across re-ingest Text = string.Join("\n", parts), Source = d.Uri, Section = s.Path, // "Chapter 3 > Retention" Ordinal = ordinal, Version = d.Version };

public sealed class TokenBucket { private readonly double _ratePerSecond, _capacity; private double _tokens; private long _lastTicks; private readonly object _gate = new(); public TokenBucket(double ratePerSecond, double capacity) { _ratePerSecond = ratePerSecond; _capacity = capacity; _tokens = capacity; _lastTicks = Stopwatch.GetTimestamp(); } public bool TryTake(double n, out TimeSpan retryAfter) { lock (_gate) { var now = Stopwatch.GetTimestamp(); var elapsed = (now - _lastTicks) / (double)Stopwatch.Frequency; _lastTicks = now; _tokens = Math.Min(_capacity, _tokens + elapsed * _ratePerSecond); // refill if (_tokens >= n) { _tokens -= n; retryAfter = TimeSpan.Zero; return true; } retryAfter = TimeSpan.FromSeconds((n - _tokens) / _ratePerSecond); return false; } } } // usage: two buckets + a concurrency limiter if (!_requests[tenant].TryTake(1, out var wait) || !_tokensPerMin[tenant].TryTake(EstimateTokens(req), out wait)) return Results.StatusCode(429, retryAfter: wait); await _providerConcurrency.WaitAsync(ct); // SemaphoreSlim sized to the provider limit try { return await _llm.CompleteAsync(req, ct); } finally { _providerConcurrency.Release(); }

  • Unbounded queueing, which turns a throughput problem into a latency collapse.
  • Ignoring Retry-After and retrying into the wall.
