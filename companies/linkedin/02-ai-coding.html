Coding with AI (CWAI) · 60 minutes · AI assisted

Solve software engineering problems using strong computer-science fundamentals while effectively incorporating AI into your development workflow. One or more coding problems involving common data structures, algorithms and problem-solving techniques.

What they evaluate

  • Apply strong engineering fundamentals to solve technical problems
  • Use AI intentionally to support and accelerate your workflow
  • Critically evaluate AI-generated output rather than accepting it at face value
  • Identify issues, make improvements and iterate when appropriate
  • Clearly communicate technical decisions and trade-offs
  • Deliver solutions that are correct, maintainable and well-reasoned

What to expect

  • Designing an appropriate solution
  • Writing clean and correct code
  • Validating your implementation
  • Communicating your technical decisions throughout
  • You are expected to use AI — it is not optional in this module
  • You own the final solution: understand it, validate it, explain it, fix it

How to run it

  • Conducted in CoderPad using its built-in AI Assist feature — a conversational assistant
  • Use it to explore approaches, generate or refine code, debug, create test cases, iterate
  • No prescribed workflow: reason first then accelerate, or explore with AI then refine yourself
  • It is not a prompt-engineering test
  • The interviewer may interrupt to ask about your thought process and how you are using AI
Source: LinkedIn recruiter pack — "Staff SI Onsite Prep - CWAI", Systems & Infrastructure · received 21 September 2026

The CWAI framework, in LinkedIn's words

  • You are expected to use AI. The pack says so: it is not optional in this module, though there is no expectation that AI solves every part or that you maximise its use.
  • It runs in CoderPad AI Assist — a conversational assistant in the pad. Watch the demo video the pack links before the day.
  • It is not a prompt-engineering test. They are scoring when you reach for AI, how you steer it, how you judge its output, and when you rely on your own reasoning instead.
  • You own the final solution. Understand it, validate it, explain it, correct it.
  • No prescribed workflow. Reason first then accelerate, or explore with AI then refine — either is fine if it is deliberate.

Rubric

How the AI coding round appears to be evaluated

How the round appears to be evaluated

Hello Interview describes a four-point scale with three or above passing, scored on four signals [source, Feb 2026]. Coditioning describes the same round as a "possible loop variant" and stresses that you remain responsible for transferring, editing, testing and explaining the code [source, Jun 2026].

SignalWhat scores wellWhat scores badly
Prompt qualitySpecific requests with context and constraints: "here is the class, add LFU eviction preserving O(1) get/put, do not change the public signature""Write an LFU cache"
VerificationReading the output, testing edge cases, rejecting a wrong suggestion with a reasonPasting and running until it compiles
Production thinkingConcurrency, race conditions, metrics, failure behaviour — often unpromptedStopping when the tests pass
CommunicationNarrating what you are checking and whyLong silences while reading AI output
What actually makes it hardThe problems are described as well-known patterns — caches, intervals, data processing — with manageable code volume. The difficulty is time management and depth on the production pivot, not the algorithm.

Do

  • Read existing code before prompting.
  • Prompt with context, constraints and the output shape you want.
  • Review line by line, out loud.
  • Write or request tests, then run them.
  • Reject at least one suggestion, with a reason.
  • Take the production pivot yourself.

Do not

  • Paste code you cannot explain.
  • Ask the AI to "solve the problem" in one prompt.
  • Go silent while reading model output.
  • Let the AI pick your data structure without a reason.
  • Skip testing because the AI "looks right".
  • Forget that you own the correctness of everything you submit.

Prompts that score well

0 "Here is my LruCache<TKey,TValue> class. Add an eviction policy interface so LRU and LFU are interchangeable, keeping Get/Put O(1) and without changing the public API. Show only the diff." "Write xunit tests for this cache covering: capacity 1, updating an existing key, eviction order after a Get, and a concurrent hammer test asserting no lost entries." "What race conditions exist in this implementation if two threads call Get and Put on the same key? List them; do not rewrite the code."

Things to say out loud while using the AI

  • "I am asking it for the test fixtures, not the design — the design decision is mine."
  • "It suggested a `ConcurrentDictionary`. That fixes the map but not the recency list, so I am rejecting it."
  • "Let me read this before I run it." (Then actually read it.)
  • "I will verify this with the capacity-1 case, which is where off-by-one bugs show."
The question you will be askedA 2026 candidate was asked verbatim: "Why did you choose this AI-generated approach over the other options?" Have a reason ready for every acceptance.
A senior engineer might say
"I used the AI to write the LFU cache, and it passed the tests." — describes the tool doing the work.
A staff engineer should be thinking
"I designed the structure — frequency buckets with an LRU list inside each — and used the AI for the boilerplate and the test fixtures. I rejected its ConcurrentDictionary suggestion because it only protects the map, not the recency list. In production I would shard by key hash and accept per-shard LFU." — owns the design, prices the trade-off, and thinks past the interview.

Chat completions: messages with roles, temperature, max tokens, stop sequences, seeds. Responses carry usage counts and a finish reason.

Interview angle. Interview angle: what do you do when finish_reason is length? (Continue with a continuation prompt, or raise the budget — do not silently truncate.)

GotchaGotcha: treat the provider SDK as an unreliable network dependency, not a function call.

Prompt design · concept

System prompt sets role and rules; user prompt carries the task; few-shot examples pin the format. Keep instructions positive and specific.

Interview angle. Interview angle: show you separate *instructions* (static, cacheable) from *data* (dynamic). That separation is also what makes prompt caching work.

GotchaGotcha: instructions buried after a large context get ignored. Put the task first and repeat the output contract last.

Structured output · concept

Ask for JSON with a schema, use the provider's structured-output/JSON mode when available, validate on arrival, and repair once.

Interview angle. Interview angle: never JsonSerializer.Deserialize straight into your domain model without a validation layer and a repair path.

GotchaGotcha: models emit prose around JSON, trailing commas, or markdown fences. Strip fences, then parse, then validate, then repair once, then fail.

Function / tool calling · concept

The model returns a tool name plus arguments; you execute and return the result as a tool message; loop until it stops asking.

Interview angle. Interview angle: tool schemas are an API contract. Validate arguments, enforce authorisation on the server side, and never let the model pick the identity it acts as.

GotchaGotcha: infinite tool loops. Cap iterations and total tokens, and make every tool idempotent or guarded by a request id.

RAG — retrieval augmented generation · concept

Chunk and embed a corpus, retrieve the top-k for a question, put them in the prompt with citations, generate an answer grounded in them.

Interview angle. Interview angle: the quality lever is retrieval, not the model. Measure recall@k before you touch the prompt.

GotchaGotcha: stuffing 20 chunks hurts. Retrieve widely, rerank, then pass few.

Embeddings and vector search · concept

Text → dense vector; similarity by cosine/dot. ANN indexes (HNSW, IVF) trade recall for latency.

Interview angle. Interview angle: know that embeddings are model-specific — changing the model means reindexing everything, which is a migration, not a config change.

GotchaGotcha: normalise vectors if you use dot product; filter by metadata *inside* the index, not after, or top-k collapses.

Chunking · concept

Split by structure first (headings, paragraphs, code blocks), then by size with overlap. Carry metadata: source, section, position.

Interview angle. Interview angle: chunk boundaries decide answer quality. Explain overlap as a recall/cost trade.

GotchaGotcha: fixed 1,000-character splits cut tables and code in half. Semantic boundaries beat fixed windows.

Retrieval and reranking · concept

Hybrid retrieval (BM25 + vector) recalls more; a cross-encoder reranker then orders the shortlist properly.

Interview angle. Interview angle: two-stage retrieval mirrors classic search — cheap recall, expensive precision. That framing lands well at LinkedIn.

GotchaGotcha: reranking is a latency and cost multiplier. Bound the shortlist (say 50 → 5).

Context management · concept

A budget: system + history + retrieved context + answer must fit. Decide eviction policy up front.

Interview angle. Interview angle: describe the budget arithmetic out loud — tokens per chunk × k + history + reserve for the answer.

GotchaGotcha: silently dropping the oldest turns loses the user's original goal. Summarise instead of truncating.

Conversation memory · concept

Short-term: recent turns verbatim. Long-term: rolling summary plus retrievable facts keyed by user.

Interview angle. Interview angle: memory is a storage design problem — where does it live, who owns deletion, what is the privacy boundary?

GotchaGotcha: summaries drift and compound errors. Keep the raw turns retrievable and cite them.

Agents and tool orchestration · concept

Plan → act → observe loops, with tools, a budget and a stop condition. Multi-agent only when roles genuinely differ.

Interview angle. Interview angle: the engineering content is the control loop: retries, budgets, timeouts, idempotency, and human-in-the-loop for risky actions.

GotchaGotcha: agents fail silently in loops. Emit a trace per step and enforce a hard ceiling.

Streaming · concept

Server-sent events or chunked responses; the client renders tokens as they arrive. You must handle mid-stream errors and cancellation.

Interview angle. Interview angle: streaming changes your error model — the HTTP status was already 200 when the failure happened.

GotchaGotcha: buffering middleware (proxies, compression) kills streaming. And you cannot validate JSON until it is complete, so stream prose and batch structured output.
StatusConfidence★★★★★
Token accounting and cost · concept

Cost = input tokens + output tokens, each priced differently. Caching, truncation and model choice are the levers.

Interview angle. Interview angle: give a number. "3,000 input tokens at X per million, 500 output — that is roughly Y per request, so at 10 requests per second…"

GotchaGotcha: retries and agent loops multiply cost invisibly. Meter per request id, not per call.
StatusConfidence★★★★★
Evaluation · concept

Golden set with expected answers; automatic metrics (exact match, citation accuracy, recall@k) plus LLM-as-judge with a rubric; track regressions per release.

Interview angle. Interview angle: say you would build the eval harness before tuning prompts — otherwise you cannot tell an improvement from noise.

GotchaGotcha: LLM judges drift and are biased to verbosity. Pin the judge model and calibrate against human labels.
StatusConfidence★★★★★
Hallucination handling · concept

Ground with retrieval, require citations, verify claims against the source, and refuse when support is missing.

Interview angle. Interview angle: "no answer" must be a first-class output of your API, not an exception.

GotchaGotcha: a confident answer with a fabricated citation is worse than a refusal. Validate that cited ids exist in the retrieved set.
StatusConfidence★★★★★
Guardrails and security · concept

Input filtering, output filtering, prompt-injection defence, PII redaction, allow-listed tools, least-privilege credentials.

Interview angle. Interview angle: retrieved documents are untrusted input. Treat them as data, never as instructions.

GotchaGotcha: injection via a retrieved document ("ignore previous instructions") is the classic RAG exploit. Fence untrusted content and never let it choose tools.
StatusConfidence★★★★★
Reliability · concept

Timeouts, bounded retries with jitter, circuit breakers, fallbacks to a smaller model, and graceful degradation to a non-AI path.

Interview angle. Interview angle: the LLM is a flaky dependency with seconds-long latency. Design like you would around any slow third party.

GotchaGotcha: retrying a non-idempotent tool call. Retry the model call, not the side effect.
StatusConfidence★★★★★
Observability · concept

Trace per request: prompt id and version, model, tokens, latency, retries, retrieved doc ids, tool calls, outcome. Sample and store for replay.

Interview angle. Interview angle: version your prompts like code, and be able to answer "why did this user get that answer?" a week later.

GotchaGotcha: logging full prompts can log customer data. Redact, and keep a separate retention policy.
StatusConfidence★★★★★
Caching · concept

Exact-match cache on normalised input; semantic cache on embedding similarity; provider-side prompt caching for the static prefix.

Interview angle. Interview angle: name the three levels and their invalidation rules — semantic caches can return a confidently wrong neighbour.

GotchaGotcha: cache keys must include model, prompt version, and retrieval corpus version, or you serve stale answers after a reindex.
StatusConfidence★★★★★
Rate limiting and back-pressure · concept

You are rate limited by the provider (requests and tokens per minute) and you must rate limit your own callers.

Interview angle. Interview angle: token-bucket per tenant plus a queue with bounded wait; shed load rather than letting latency grow unbounded.

GotchaGotcha: retrying into a 429 storm. Respect Retry-After and use a concurrency limiter, not just a rate limiter.
StatusConfidence★★★★★
Async processing and queues · concept

Long jobs go to a queue; the API returns a job id; workers process with idempotency keys and publish progress events.

Interview angle. Interview angle: this is where the AI round becomes a normal distributed-systems round — exactly-once effects, poison messages, dead-letter queues.

GotchaGotcha: holding an HTTP request open for a 90-second generation. Stream it or make it a job.
StatusConfidence★★★★★
Event-driven AI systems · concept

Ingest events → enrich → embed → index → serve. Reprocessing needs a replayable log and versioned indexes.

Interview angle. Interview angle: reindexing on a model change is a migration with dual-write and cutover concerns — the same shape as your Isolated Cloud tenant migration.

GotchaGotcha: no versioning on the index means no rollback when the new embedding model is worse.
StatusConfidence★★★★★

Build an LLM client wrapper with timeouts, retries and budgets · ReliabilityReliability
Requirement
Wrap a chat-completions API in a class the rest of the codebase can depend on. It must never hang, never retry forever, and never hide a failure.
Clarify firstask, do not assume
Ask these before writing code. In this round, the questions are part of the score.
  • What is the latency budget per call, and is it per attempt or total?
  • Is the call idempotent from the provider's side? (Model calls yes; tool side effects no.)
  • Do we need cancellation propagated from the caller (CancellationToken)?
  • What happens on exhaustion — throw, or return a degraded answer?
Design
One HttpClient (reused), a per-attempt timeout, total-deadline enforcement, retry only on 429/5xx/timeout with exponential backoff plus jitter, honour Retry-After, and surface usage so callers can meter cost.

Parse structured model output — and repair it once · Structured outputStructured output
Requirement
The model must return { "intent": string, "entities": [...], "confidence": number }. Turn its response into a validated domain object.
Clarify firstask, do not assume
Ask these before writing code. In this round, the questions are part of the score.
  • Is a provider JSON mode / schema available, or are we parsing free text?
  • What do we do on invalid output — retry, repair, or fail the request?
  • Is partial output acceptable (intent without entities)?
  • Is confidence meaningful, or should we ignore a self-reported number?
Design
Extract → parse → validate → repair once → fail. Extraction strips markdown fences and finds the outermost balanced JSON object. Validation is a real schema check, not just deserialisation. Repair sends the model its own output plus the validator error, exactly once, then gives up.

Stream a response to the caller · StreamingStreaming
Requirement
Expose an endpoint that streams the model's answer to the browser as it is generated, with cancellation.
Clarify firstask, do not assume
Ask these before writing code. In this round, the questions are part of the score.
  • Server-sent events or WebSocket? (SSE is enough for one-way.)
  • What happens if the model fails mid-stream, after we sent 200 OK?
  • Do we need the complete text server-side too (for logging or post-processing)?
  • Must the client be able to cancel and stop billing?
Design
Async streaming from the provider, re-emitted as SSE frames. Accumulate server-side for logging. On mid-stream failure, emit a typed error event rather than cutting the connection silently. Propagate HttpContext.RequestAborted so cancellation stops the upstream call.

Failure modes
  • Forgetting to flush — the client sees nothing until the end.
  • Compression or a proxy buffering the stream.
  • Returning a 500 after headers are sent (impossible — hence the in-band error event).
  • Not cancelling upstream when the client disconnects, so you keep paying for tokens.
