Systems and Infrastructure Design · 60 minutes

You are given a system design problem and asked to design a solution meeting functional and non-functional requirements.

What they evaluate

  • Completeness of your solution
  • Quality of your design decisions
  • Reasoning about scalability, performance, reliability, fault tolerance and extensibility

What to expect

  • Break a complex problem into logical components and explain how they interact
  • Describe the solution from high-level architecture down to implementation choices
  • As the design evolves, discuss data structures and algorithms, concurrency, multithreading, storage systems, networking, caching, partitioning, replication and consistency — where they justify a decision

How to run it

  • Ask clarifying questions
  • State your assumptions
  • Think out loud
  • Discuss trade-offs
  • "There are no perfect answers" — they want to see how you reason through ambiguity and adapt as new requirements emerge

The example question printed in the pack

Bit.lyDesign a system to take user-provided URLs and transform them to shortened URLs that redirect back to the original. Describe how the system works.
  • How would you allocate the shorthand URLs?
  • How would you store the shorthand-to-original URL mapping?
  • How would you implement the redirect servers?
  • Keep click stats. How would you store the stats?

Bit.ly — the official example question · Official example · Storage · ServingP0
The prompt

Bit.ly — the official example question

Why this designThis is the example question in LinkedIn's own prep pack, with four named sub-questions: how you allocate the shorthand URLs, how you store the mapping, how you implement the redirect servers, and how you keep and store click stats. Treat those four as the actual agenda of the hour — the pack is telling you where the interview goes.
Your clarifying questionsask before you design
Write down your five questions before opening this. Compare, then continue.
  • Scale: how many new URLs per day, and what read-to-write ratio? (Read-heavy by orders of magnitude.)
  • Custom/vanity aliases, or system-generated only?
  • Expiry and deletion — do links live forever?
  • Stats: real-time counters, or analytics that can lag minutes?
  • Global audience? (Redirect latency is the product, so edge presence matters.)
  • Guessability: must short codes be unpredictable (security) or is sequential fine?
Functional requirements
  • Create a short code for a long URL, optionally with a custom alias
  • Redirect a short code to the original URL
  • Count clicks and expose stats per link
  • Delete or expire a link
Non-functional requirements
  • Redirect p99 in tens of milliseconds, globally — this is the whole user experience
  • Very high availability on the read path; the write path can be less available
  • No collisions, ever: a code must map to exactly one URL, permanently
  • Stats may be eventually consistent; the mapping may not
Scale estimate
Assume 100 million new links per day and a 100:1 read-to-write ratio → ~1,200 writes/s and ~120,000 redirects/s. Storage: 100M/day × ~500 bytes ≈ 50 GB/day, ~18 TB/year including indexes. At 7 base-62 characters the key space is 3.5 × 10¹² — decades of headroom; at 6 characters it is 57 billion, which you would exhaust in under two years at this rate. That arithmetic is the answer to "how long should the code be?"
API
POST /links {longUrl, alias?, ttl?} → {shortCode, shortUrl}; GET /{shortCode} → 301/302 redirect; GET /links/{shortCode}/stats?from=&to=&groupBy= → click counts. Creation is idempotent on (longUrl, owner) if you want to deduplicate; say whether you do, because it changes the storage model.
Data model
Mapping: shortCode → {longUrl, ownerId, createdAt, expiresAt} in a key-value store partitioned by hash of shortCode. Stats: raw click events in a log, rolled up into (shortCode, timeBucket) → count aggregates. Keep the two apart: the mapping is small, hot and must be correct; the stats are large, append-only and tolerant of lag.
High-level architecture
Write path: API → allocate code → persist mapping → populate cache. Read path: DNS/anycast → edge → redirect service (stateless) → cache → key-value store on a miss → emit a click event. Stats path: click events → a partitioned log (this is Kafka's home ground) → stream aggregation (Samza-style) → time-bucketed rollups in an analytics store (Pinot-style) for queries, with raw events landing in cold storage for reprocessing. Saying "the mapping is a KV problem, the stats are a streaming problem, and they should not share a store" is the structural insight the sub-questions are fishing for.
Deep dives
  • Sub-question 1 — allocating short codes. Three options, and pick with reasons. (a) Hash the URL (MD5 → base62, first 7 chars): deduplicates identical URLs, but needs collision handling on write. (b) Random 7 chars: unguessable, but needs a uniqueness check, and birthday collisions start mattering as the table fills. (c) Counter + base62, with each host leasing a range (say a block of 100k) from a coordination service: no collisions by construction, no read-before-write, and ranges survive host restarts — you just lose the tail of a leased block. I would take (c), and scramble the counter (Feistel or base-62 with a keyed permutation) so codes are not sequentially guessable.
  • Sub-question 2 — storing the mapping. A key-value store partitioned by hash of the short code, replicated, with the row being immutable after creation. Immutability is the gift here: caches never need invalidation for the common case, only for deletes and expiry. Cache in front (LRU plus a bloom filter for known-missing codes to stop cache-miss stampedes on garbage traffic).
  • Sub-question 3 — redirect servers. Stateless, horizontally scaled, close to users, holding a large local cache; the hot set is tiny (a few percent of links get most traffic). 301 versus 302 is the trade-off to name: 301 is cached by browsers and CDNs, which makes redirects nearly free but destroys your click stats and your ability to change or revoke a link; 302 keeps every click visible and costs a request every time. Most link shorteners choose 302 for exactly that reason.
  • Sub-question 4 — click stats. Do not write to a database per click at 120k/s. Emit an event to a partitioned log, partitioned by short code so per-link counts land in one place, then aggregate in a stream processor into minute and hour buckets. Keep raw events for reprocessing; serve queries from the rollups. Hot links create a hot partition — pre-aggregate on the producer side (batch counts per second per host) so the fan-in is bounded.
  • Expiry and deletion. TTL in the row plus a lazy check on read, with a background sweeper for storage reclamation. Deletion must invalidate caches and edge entries, which is the second reason to prefer 302.
Failure modes
  • Key-value store unavailable → serve from cache; unknown codes fail with a clean 404 rather than a hang.
  • Cache cold after a deploy → a thundering herd on the store; stagger restarts and pre-warm from the hot-set list.
  • Coordination service for counter ranges down → hosts keep issuing from their current lease; only new leases block, which is a graceful degradation rather than an outage.
  • Stats pipeline lagging → redirects are unaffected (the paths are separate); stats catch up, and you can say so to the customer honestly.
  • Abuse: someone shortens malicious URLs → a denylist check on create and a re-check on read, plus rate limits per account.
Scaling
  • Read path scales by adding stateless redirect nodes and cache capacity; nothing coordinates.
  • Write path scales by leasing wider counter ranges — no shared hot row.
  • Stats scale by log partitions; hot links are handled by producer-side pre-aggregation.
  • Geo: replicate the mapping read-only to each region; creation can stay in one region if 1,200 writes/s is fine there.
Observability
  • Redirect p99 by region, and cache hit rate (the two numbers that define the product)
  • Unknown-code rate — a spike means either a bug or a scanning attack
  • Stats pipeline lag
  • Counter-range utilisation, so you never discover exhaustion at 3 a.m.
Security and privacy
  • Unguessable codes if links may be private; sequential codes leak volume and allow enumeration.
  • Malware/phishing denylist on create and on read.
  • Open-redirect abuse: you are a redirector by definition, so rate-limit and attribute every link to an owner.
Cost
The read path dominates: cache memory and bandwidth. Stats storage grows forever unless you tier — keep minute buckets for days, hour buckets for months, and raw events in cold storage. Quote it: 100M links/day of raw click events at ~100 bytes is ~10 GB/day per 100M clicks, which is cheap in object storage and expensive in a hot analytics store.
Trade-offs
AxisWhat you traded
301 vs 302Free, browser-cached redirects versus visible click stats and revocability — the defining trade of this design
Counter ranges vs hashingNo collisions and no read-before-write, at the cost of a coordination dependency and non-dedup
Stats freshnessReal-time counters cost a hot path; minute-level rollups are usually enough and far cheaper
Code length6 characters is compact and runs out; 7 gives decades of headroom for one extra character
Evolution
Phase 1: single region, counter ranges, KV plus cache, 302 redirects, click events to a log with hourly rollups. Phase 2: multi-region read replicas and edge caching. Phase 3: minute-level stats, custom aliases, abuse detection. The seam that makes phase 3 cheap is keeping stats out of the mapping store from day one.
Senior versus staff
A senior engineer might say
"Hash the URL, store it in a database with a cache, redirect with 301, and increment a counter per click."
A staff engineer should be thinking
"The redirect is trivial; the interesting decisions are code allocation without coordination on the hot path, 301 versus 302 as a stats-versus-cost trade, and keeping click stats entirely off the mapping store — a log plus stream aggregation, because a write per click at a hundred thousand per second is the thing that actually falls over. I would also size the code length from the arithmetic rather than picking seven by convention."

The prompt

Design a rate limiter

Why this designThe most recent design prompt found in the research — logged on Exponent as asked about a month ago (≈Aug 2026). Also the question your AI-coding rate-limiting exercise already answers in code.
Your clarifying questionsask before you design
Write down your five questions before opening this. Compare, then continue.
  • Who are we limiting — user, API key, tenant, IP, or endpoint?
  • What happens at the limit: reject with 429, queue, or degrade?
  • Hard limit or smoothed burst? (Bursty interactive traffic vs steady batch.)
  • Single region or global? Is a small over-count acceptable for lower latency?
  • Do we limit requests, or cost (tokens, bytes, CPU)?
Functional requirements
  • Allow or deny a request against a per-key quota
  • Configurable rules per key/route, changeable without deploy
  • Report remaining quota and retry-after to the caller
  • Observable: current rate, rejections, top offenders
Non-functional requirements
  • Sub-millisecond added latency at p99 (it is on every request)
  • Fail open or fail closed — a decision, and for an abuse limiter usually fail open for availability, fail closed for billing
  • Accuracy tolerance: exact vs approximate under partition
  • Multi-tenant isolation: one tenant cannot exhaust another's budget
Scale estimate
Assume 200k requests per second across 40 gateway nodes, 10 million distinct keys, rule changes hourly. 200k × 1 counter op = the whole design problem is coordination, not compute.
API
POST /check {key, cost, route} → {allowed, remaining, retryAfterMs}; rules via a control plane with versioned config; usually embedded as a library in the gateway rather than a network call.
Data model
Per key: bucket state (tokens, lastRefillTs) or a windowed counter. Rules: key pattern → {rate, burst, scope}. Hot keys need their own treatment.
High-level architecture
Gateway-embedded limiter with a local token bucket per key, synchronised against a shared store (Redis cluster) on a short interval or by leasing quota slices. Three designs to compare out loud: 1. Central Redis counter per request — exact, simple, adds a network hop and a hard dependency on every request. 2. Local bucket + periodic sync — fast, approximate, drifts by at most (rate × sync interval) per node. 3. Quota leasing: each node leases a slice of the global budget and renews; exact-ish, resilient, and the one to propose at Staff level.
Deep dives
  • Algorithm choice: token bucket (bursty, simple, O(1) state) vs sliding-window log (exact, memory-heavy) vs sliding-window counter (good compromise).
  • Hot keys: one key taking 30% of traffic. Shard the counter (key:shardN) and sum, or pin to a dedicated node.
  • Clock: never trust wall clocks across nodes for refill; use monotonic time locally and a lease epoch globally.
  • Config propagation: versioned rules pushed to nodes; a node with stale rules must fail safe and report its version.
Failure modes
  • Redis down → fall back to local buckets with conservative limits, and alarm. Say which way you fail and why.
  • Node restart loses local state → cold start allows a burst; bound it by starting buckets empty.
  • Network partition → each side enforces its own slice; total may exceed the global limit by the number of partitions.
Scaling
  • Shard by key hash; scale nodes independently of the store.
  • Batch counter updates (one round trip per interval, not per request).
  • Tiered limits: cheap local check first, expensive global check only for keys near their limit.
Observability
  • Allowed/denied per rule and per tenant
  • p99 added latency
  • Drift between local and global counts
  • Top-N keys by consumption — this is also your abuse signal
Security and privacy
  • Key spoofing: the identity must come from an authenticated token, not a header the client sets.
  • Limits must be enforced server-side; a client-side limiter is a UX feature, not a control.
Cost
Redis cluster sized for 200k ops/s is the dominant cost; local buckets with 1-second sync cut that by orders of magnitude. Give the arithmetic.
Trade-offs
AxisWhat you traded
ExactnessCentral counter is exact but adds latency and a dependency
AvailabilityLocal buckets survive a store outage but can over-admit
ComplexityLeasing is the best behaviour and the most code — justify it with the traffic numbers
Evolution
Start with a central counter (correct, simple), measure, then move to leasing when latency or the dependency hurts. Rules engine first-class from day one, because limits change far more often than code.
Senior versus staff
A senior engineer might say
"Token bucket in Redis, 429 when the bucket is empty."
A staff engineer should be thinking
"On every request means the limiter is now a dependency of everything, so I would embed it, lease quota, and define the failure mode explicitly: fail open for abuse limiting, fail closed for billing. I would also expect one key to be 30% of traffic and shard its counter."

The prompt

Design a distributed job scheduler

Why this designReported first-hand at LinkedIn (Senior SWE Infrastructure, 30 Sep 2025). The interviewer ended the round saying all the trade-offs were covered — lead with trade-offs.
Your clarifying questionsask before you design
Write down your five questions before opening this. Compare, then continue.
  • One-shot jobs, cron-style recurring, or both?
  • Delivery semantics: at-least-once or effectively-once?
  • What is the acceptable firing skew — seconds or minutes?
  • Who executes: our workers, or a callback to the owning service?
  • What happens to jobs missed during an outage — run late, or skip?
Functional requirements
  • Schedule a job for time T, or on a recurrence
  • Cancel and reschedule
  • Execute within the skew budget
  • Retry failures with a policy
  • Expose job status and history
Non-functional requirements
  • No lost jobs (durability beats latency)
  • Firing skew p99 under a few seconds
  • Horizontal scale to millions of pending jobs
  • Tenant isolation: one noisy tenant cannot delay others
Scale estimate
10 million pending jobs, 5k firings per second at peak, spiky on the hour. The hour boundary is the whole problem: 60% of daily jobs fire in 1% of the time.
API
POST /jobs {runAt|cron, payload, idempotencyKey, retryPolicy} → jobId; DELETE /jobs/{id}; GET /jobs/{id}.
Data model
Durable store partitioned by time bucket: (bucketMinute, shard) → jobs. Secondary index by jobId for cancel/status. A lease table (or a lease column) for in-flight ownership.
High-level architecture
Writer API → durable store (partitioned by minute bucket and shard) → a set of dispatcher nodes, each owning shards by consistent hashing with a lease → due jobs published to a queue → workers execute with idempotency keys → results and retries written back. Say why *not* a single timer wheel in one process: it does not survive restarts and cannot scale past one machine's clock.
Deep dives
  • The thundering herd on the hour: jitter jobs within their minute, and pre-fetch the next bucket early.
  • Exactly-once effects: at-least-once delivery plus an idempotency key checked by the executor. Say plainly that exactly-once delivery is not achievable; exactly-once *effects* are.
  • Ownership: leases with fencing tokens so a paused dispatcher cannot double-fire after a GC pause.
  • Missed windows: on recovery, decide per job class — fire late, or skip with a "missed" event. Make it a policy field, not a global rule.
  • Long jobs: the scheduler triggers, it does not execute. Keep execution in a worker pool with its own back-pressure.
Failure modes
  • Dispatcher dies → lease expires, another node picks up the shard; jobs may fire twice, hence idempotency.
  • Store slow → dispatch lag grows; shed by priority, and alarm on lag rather than on errors.
  • Poison job that always fails → retry with backoff, then dead-letter with an alert.
  • Clock skew between dispatchers → use the store's time as the authority.
Scaling
  • Partition by (time bucket, shard) so hot minutes spread across nodes.
  • Separate the read path (status) from the dispatch path.
  • Priority lanes so a bulk backfill cannot starve interactive jobs.
Observability
  • Dispatch lag (now − scheduled time) at p50/p99 — the single most important metric
  • Firings per second, retries, dead-letters
  • Lease churn (a proxy for node instability)
  • Per-tenant queue depth
Security and privacy
  • Payloads may contain secrets — encrypt at rest and redact in logs.
  • Authorisation on cancel/status: a tenant may only touch its own jobs.
Cost
Storage is cheap; the dispatcher fleet is sized for the peak minute, not the average. Point that out and propose smoothing.
Trade-offs
AxisWhat you traded
Durability vs latencyWrite to durable storage before acknowledging — slower writes, no lost jobs
Exactly-onceIdempotency at the executor instead of impossible delivery guarantees
SkewTighter skew costs more pre-fetching and more nodes idling at the boundary
Evolution
Phase 1: single-region, at-least-once, minute granularity. Phase 2: priority lanes and per-tenant isolation. Phase 3: multi-region with a regional owner per job to avoid cross-region double firing.

Scale estimate
1 million messages per second, average 1 KB → 1 GB/s ingress, ×3 replication = 3 GB/s of disk writes. That arithmetic drives the whole design.
API

Data model
Append-only log per partition, split into segment files with a sparse offset index; offsets are monotonic per partition; consumer offsets stored in an internal compacted topic.
High-level architecture
Producers hash the key to a partition → append to the leader's log → followers replicate → the in-sync replica set (ISR) defines durability → consumers read sequentially from their offset, with the page cache doing most of the work. Deep dives

  • Slow follower → dropped from ISR; durability quietly weakens. Alarm on ISR size.

  • Disk full → broker stops accepting writes; retention policy is a capacity decision.
Scaling
  • Partitions are the unit of parallelism — choose the count for the eventual consumer parallelism, because increasing it later breaks key ordering.
  • Tiered storage moves cold segments to object storage, decoupling retention from broker disk.
  • Separate high-throughput topics onto dedicated brokers.
Observability
  • Consumer lag per group and partition (the headline metric)
  • ISR size and under-replicated partitions
  • Produce/fetch latency percentiles
  • Rebalance frequency
Security and privacy
  • Per-topic ACLs, mTLS between brokers and clients, and encryption at rest for sensitive topics.
  • A shared cluster is a multi-tenant system: quotas per client id or the noisy neighbour wins.
Cost
Disk throughput and retention length dominate. Tiered storage changes the economics; quote the ingress arithmetic and then the retention multiplier.
Trade-offs
AxisWhat you traded
Durability vs latencyacks=all with a large ISR is slower and safer
Partition countMore parallelism, more metadata and more rebalancing pain
RetentionReplayability costs storage — and replay is the feature that makes the log worth having

Start with a modest partition count and acks=all for critical topics; add tiered storage when retention outgrows disks; introduce quotas the first time a tenant hurts another.
