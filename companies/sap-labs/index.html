What a Forward Deployed Engineer is

What FDE means GENERAL KNOWLEDGE

An engineer embedded with a customer who builds and deploys real software against real data, with the speed of a startup and the accountability of an owner. Popularised by Palantir; now used by AI companies and enterprise vendors because AI value only appears once it runs on the customer's own data and processes.

Why SAP would use it INFERENCE

SAP customers run their business on SAP systems, but AI and analytics value depends on getting that data — plus non-SAP data — into governed, AI-ready shape inside each customer's landscape. An embedded data engineer shortens the path from "interesting AI demo" to "agent running on our order data". The JD's team is "AI and industry expert", which fits that reading.

Customer impact INFERENCE

Measured as a business outcome the customer can see — a process that runs faster, a report that is trusted, an agent that resolves a case — not as tickets closed.

Reusable patterns INFERENCE

Every engagement should leave behind something the next one reuses: an ingestion template, a data-quality rule set, a governed data product, an agent tool. That is the difference between an FDE and a consultant.

Expert level INFERENCE

Expected to lead the technical approach in an engagement without supervision, make architecture calls under ambiguity, talk to customer architects and executives, and mentor others — consistent with the JD's 6+ years in data engineering.

Concepts

Must knowSAP JOB REQUIREMENT
What it is

A chain of steps that moves data from where it is produced to where it is used, changing its shape on the way.

Why it exists

Operational systems are built to run the business, not to answer questions about it. A pipeline gets their data somewhere it can be combined, cleaned and queried without hurting the source.

Analogy

A water treatment plant: intake, filtration, storage, distribution — each stage hands clean output to the next.

You already know this — backend connection

You already build service chains with queues between them. A pipeline is the same shape, but the unit of work is a dataset or a batch of records, and correctness is measured on the data, not on the response.

How it works

Stages: ingest (pull or receive), land raw data unchanged, transform into clean and modelled tables, serve to BI, ML or APIs. Each stage should be idempotent (re-running it gives the same result), observable (row counts, freshness, failures) and isolated (a failure in one table does not corrupt others).

Expert depth

Design for re-runs, not for success: partition outputs by date and overwrite a partition on retry, so a retried day replaces itself instead of duplicating. Separate compute from orchestration (Spark does the work, Airflow decides when). Treat schemas as contracts with producers.

Example

Nightly: SAP S/4HANA sales orders + Salesforce opportunities + web events → lakehouse → a revenue table the finance team trusts by 7 am.

Interview answer
A pipeline moves data from source systems to where it is used, and the engineering is making each step idempotent, observable and safe to re-run.
A pipeline ingests data from sources, lands it raw, transforms it into clean modelled tables and serves it. The hard parts are not the happy path: they are re-runs, late data, schema changes and knowing when the data is wrong. So I design every stage to be idempotent and observable.
I think of a pipeline as a chain of stages with contracts between them: ingest, land raw, transform, serve. I keep the raw landing untouched so I can always reprocess. Each transform writes to a partitioned output that a retry overwrites, so failures are safe to re-run. Orchestration — when and in what order — is separate from compute — how the transformation runs. And I treat quality as a first-class output: row counts, freshness and validation results are produced alongside the data, so a bad load stops before it reaches a dashboard or an AI agent. Coming from backend systems, the mindset is the same as a service chain; what changes is that correctness is a property of the dataset.
Senior follow-up: A nightly job failed halfway and someone re-ran it. Now revenue is doubled. Why, and how would you prevent it?

The job appended instead of overwriting, so the re-run duplicated rows. Make writes idempotent: overwrite the partition for that run date, or MERGE on a business key, never blind append.

Common mistake

Designing only the happy path — appending on every run, so retries create duplicates.

Must knowSAP JOB REQUIREMENT
What it is

ETL transforms data before loading it into the warehouse. ELT loads raw data first and transforms it inside the warehouse or lakehouse.

Why it exists

ETL came from the era of expensive warehouse storage and compute. Cheap storage and elastic compute made it practical to keep everything raw and transform later — which also lets you reprocess when logic changes.

Analogy

ETL: wash and chop vegetables before putting them in the fridge. ELT: put the groceries straight in, prepare them when you cook — and you still have the originals if the recipe changes.

You already know this — backend connection

Compare it to validating at the API edge (ETL) versus storing the raw event and deriving views from it (ELT) — like event sourcing: keep the facts, rebuild the projections.

How it works

ELT is the default in lakehouses: land raw (bronze), clean (silver), aggregate (gold), all inside the platform with SQL or Spark. ETL still makes sense when data must be filtered before it lands — PII that must never be stored, or huge sources where you only need a fraction.

Expert depth

The real decision is where governance and cost sit. ELT keeps raw data (great for replay and audit) but means raw PII may land — so you need masking or a restricted raw zone. ETL reduces stored volume but loses replay. Many platforms are hybrid: light ETL at ingestion (drop or tokenise PII, normalise types), ELT for business logic.

Example

Raw SAP and CRM extracts land unchanged in a bronze zone; dbt or Spark SQL builds silver and gold tables; tokenisation of national IDs happens before landing.

Interview answer
ETL transforms before loading; ELT loads raw first and transforms in the platform — the modern default because it keeps replay.
ETL transforms data before it lands; ELT lands it raw and transforms inside the lakehouse or warehouse. ELT is the modern default because storage is cheap and keeping raw data lets you reprocess when logic changes. I still do light ETL at the edge for things that must never be stored raw, like PII.
The difference is where transformation happens. ETL transforms in flight and loads only the result; ELT loads raw data first and transforms inside the platform. ELT won in the lakehouse era because storage became cheap and compute elastic, and because keeping the raw layer means you can rebuild every downstream table when business logic changes — the same reason event sourcing keeps events. The cost is governance: raw data includes sensitive fields, so the raw zone needs tight access, or you tokenise PII at ingestion. In practice I run a hybrid: minimal ETL at the edge for privacy and type normalisation, and ELT in medallion layers for business logic.
Senior follow-up: When would you deliberately choose ETL?

When data must not be stored raw (regulated PII), when the source is huge and you need a small slice, or when the target cannot do the transformation efficiently.

Common mistake

Saying ELT is "better" without mentioning governance of the raw zone.

Must knowSAP JOB REQUIREMENT
What it is

Batch processes data in bounded chunks on a schedule; streaming processes an unbounded flow continuously as events arrive.

Why it exists

Different questions need different freshness. Month-end finance needs complete, correct data; fraud detection needs it in seconds.

Analogy

Batch is collecting post and opening it once a day; streaming is answering the phone.

You already know this — backend connection

You know request/response vs async consumers. Batch is a cron job over a table; streaming is a long-running Kafka consumer with state. The streaming hard parts are the ones you already know: ordering, retries, state, backpressure, exactly-once.

How it works

Batch: simpler, cheaper, easy to re-run, latency of the schedule. Streaming: low latency, but you must handle late and out-of-order events (event time vs processing time, watermarks), state, and continuous operation. Micro-batch (Spark Structured Streaming) sits between: small batches every few seconds with batch-like semantics.

Expert depth

Most enterprise platforms are both: stream into the raw layer for freshness, batch for heavy transforms and reconciliation. A Lambda architecture runs two paths (batch for truth, stream for speed) and pays for it in duplicated logic; Kappa uses one streaming path with replay. With Delta tables, one engine can serve both, which is much of the lakehouse argument.

Example

Orders stream from Kafka into a bronze Delta table within a minute; an hourly batch builds the revenue table; a nightly batch reconciles against the ERP.

Interview answer
Batch handles bounded data on a schedule; streaming handles unbounded data continuously — choose by the freshness the business actually needs.
Batch processes bounded data on a schedule and is simple and cheap to re-run; streaming processes events continuously for low latency but must handle late data, state and exactly-once. I ask what freshness the decision actually needs, and often stream into the raw layer while doing heavy transforms in batch.
The question I ask first is: what freshness does the decision need? Month-end close needs complete, reconciled data; fraud needs seconds. Batch gives simplicity, cheap re-runs and natural backfills. Streaming gives latency but brings the problems I know from Kafka systems: out-of-order and late events, which you handle with event time and watermarks; state, which must be checkpointed; and end-to-end exactly-once, which needs idempotent or transactional sinks. Spark Structured Streaming's micro-batches are a pragmatic middle. A common pattern is to stream raw data into Delta for freshness and run batch for heavy modelling and reconciliation — one storage layer serving both, which avoids the duplicated logic of a Lambda architecture.
Senior follow-up: Your stream shows yesterday's revenue lower than the batch report. Why?

Late-arriving events: the stream closed the window before they arrived. Use event-time windows with a watermark that matches real lateness, and reconcile with batch.

Common mistake

Choosing streaming because it sounds modern, when the business needs a daily report.

Must knowSAP JOB REQUIREMENT
What it is

Capturing every insert, update and delete in a source database as a stream of change events, usually by reading the database's transaction log.

Why it exists

Full extracts of large tables are slow and heavy on the source, and polling "updated_at" misses deletes and in-between states. Reading the log captures every change with little load.

Analogy

Instead of photocopying the whole ledger every night, you get a copy of each new line as it is written.

You already know this — backend connection

You know the outbox pattern and event sourcing. Log-based CDC is the database emitting its own events from the write-ahead log, so no application change is needed. Debezium → Kafka is the common open-source shape.

How it works

Log-based CDC (Debezium reading MySQL binlog / Postgres WAL, Oracle LogMiner, vendor tools for SAP) emits change events with before/after images and an operation type. Downstream, a MERGE applies them to a target table keyed by primary key. Ordering per key matters, so partition the Kafka topic by primary key.

Expert depth

Hard parts: the initial snapshot plus switching to the log without gaps; schema changes in the source; deletes (soft vs hard) and GDPR erasure; ordering across tables in one transaction; and idempotent apply (use the source log position as a version to ignore stale events). For SAP sources, extraction usually goes through SAP-supported mechanisms rather than reading the database log directly — verify against current SAP documentation.

Example

Customer master changes in an ERP flow through CDC → Kafka → a Delta table updated with MERGE every minute, so the AI assistant answers with current addresses.

Interview answer
CDC turns a database's transaction log into a stream of change events, so you replicate changes instead of re-extracting tables.
CDC reads the source database's log and emits every insert, update and delete as events — usually into Kafka. Downstream I apply them with a MERGE keyed on the primary key. It captures deletes, puts almost no load on the source, and gives near-real-time freshness.
Change data capture turns the database's write-ahead log into a stream of change events, each with the operation and the before and after values. Compared with nightly full extracts it is lighter on the source, near real-time, and captures deletes, which timestamp polling misses. I put the events on Kafka partitioned by primary key so changes to one row stay ordered, and apply them with MERGE into a Delta table. The engineering is in the edges: a consistent initial snapshot and hand-over to the log, schema changes, hard deletes for compliance, and idempotent apply using the log position so replays do not move a row backwards. For SAP systems I would use SAP-supported extraction rather than raw log reading.
Senior follow-up: How do you make CDC apply idempotent?

Carry the source log sequence number (LSN/SCN) as a version; MERGE only when the incoming version is newer than the stored one.

Common mistake

Forgetting deletes, or ignoring per-key ordering so updates apply out of order.

Should knowSAP JOB REQUIREMENT
What it is

Shaping tables so questions are easy and fast: facts (events you measure) surrounded by dimensions (things you describe them by).

Why it exists

Normalised OLTP schemas are great for writes and terrible for analysis — a simple question becomes a dozen joins. Dimensional models make analytical queries simple and fast.

Analogy

A receipt (the fact: what was bought, how much) and the address book, product catalogue and calendar it refers to (dimensions).

You already know this — backend connection

You normalise for write integrity in OLTP. Analytics deliberately denormalises for read speed — the same trade you make when you build a read model or a cache in CQRS.

How it works

Star schema: one fact table at a declared grain (one row per order line) with foreign keys to dimensions (customer, product, date). Grain is the first decision and the most common mistake. Slowly Changing Dimensions: Type 1 overwrites; Type 2 keeps history with valid_from / valid_to / is_current so a fact joins to the dimension as it was at the time.

Expert depth

Lakehouse layers map onto this: silver holds cleaned, conformed entities; gold holds star schemas or wide aggregated tables for consumption. Wide denormalised tables are common in columnar storage because joins cost more than storage. Data Vault suits integration of many changing sources; Kimball stars suit consumption.

Example

Sales fact (order line grain) with customer as SCD2, so revenue by region uses the customer's region at order time, not today's.

Example code (sql)
-- SCD Type 2: close the current row, insert the new version
MERGE INTO dim_customer t
USING staged_customers s
ON t.customer_id = s.customer_id AND t.is_current = true
WHEN MATCHED AND t.region <> s.region THEN
  UPDATE SET is_current = false, valid_to = s.changed_at;
-- then insert the new current versions
INSERT INTO dim_customer
SELECT customer_id, region, changed_at AS valid_from, NULL AS valid_to, true AS is_current
FROM staged_customers s
WHERE NOT EXISTS (SELECT 1 FROM dim_customer t
                  WHERE t.customer_id = s.customer_id AND t.is_current AND t.region = s.region);
Interview answer
Model facts at a clear grain surrounded by dimensions; use SCD Type 2 when history of a dimension matters.
I model analytics as facts at a declared grain with dimensions around them — a star schema. The first decision is the grain. Where a dimension changes and history matters, like a customer's region, I use SCD Type 2 so each fact joins to the version that was true at the time.
Analytical modelling starts with the grain: what does one row of the fact table mean — an order, an order line, a daily snapshot? Then dimensions describe the facts: customer, product, date. That is a star schema, and it trades the write-integrity of OLTP normalisation for simple, fast reads — the same trade as a read model in CQRS. Dimensions change, and the business decides whether history matters: Type 1 overwrites, Type 2 keeps versioned rows with validity dates, so revenue by region last year uses last year's region. In a lakehouse, silver holds clean conformed entities and gold holds the stars or wide tables the consumers actually query.
Senior follow-up: Revenue by region changed for last year after a customer moved. What went wrong?

The customer dimension was Type 1 (overwritten). Use SCD Type 2 and join facts to the version valid at the transaction date.

Common mistake

Not declaring the grain, so facts at different grains get mixed and totals double-count.

What it is

Lineage records where each dataset came from and what it feeds. Observability watches the data itself — freshness, volume, schema, distribution — not just whether jobs succeeded.

Why it exists

A job can succeed and still produce wrong data. When a dashboard is wrong you need to know which upstream change caused it, and who else is affected.

Analogy

Lineage is the family tree of a number on a dashboard; observability is its health check-up.

You already know this — backend connection

You know distributed tracing (lineage is the trace across tables) and SLOs (freshness and volume are the golden signals of data). "Job green, data wrong" is the data version of a 200 with a wrong body.

How it works

Lineage: table- and column-level, captured from SQL/Spark plans or the catalogue (e.g., Unity Catalog, OpenLineage). Observability signals: freshness (last update), volume (row count vs expected), schema (unexpected change), distribution (nulls, ranges, cardinality), and quality test results. Alert on these, with owners.

Expert depth

Use lineage for impact analysis before changing a column, and for root cause after an incident. Put data SLOs on gold tables ("revenue table fresh by 07:00, 99% of days"). Make quality checks blocking at layer boundaries for critical tables so bad data stops instead of propagating to agents and dashboards.

Example

Gold revenue drops 40% overnight; lineage shows a silver table filtered by a new status code from the ERP; the volume alert on silver fired first.

Interview answer
Lineage tells you where data came from and what depends on it; observability tells you whether the data itself is healthy.
Lineage maps each table to its sources and consumers, so you can do impact analysis and root cause. Data observability monitors freshness, volume, schema and distributions, because a job can succeed and still produce wrong data. I put SLOs and owners on the critical tables.
Two complementary things. Lineage answers "where did this number come from, and what breaks if I change this column?" — it is distributed tracing for tables, captured from query plans or the catalogue. Observability answers "is the data healthy right now?" through freshness, volume, schema and distribution checks, because a green job can still produce nonsense — the data equivalent of an HTTP 200 with the wrong body. I put data SLOs and named owners on the tables that matter, make quality checks block promotion between layers for critical data, and use lineage both before changes and during incidents.
Senior follow-up: A finance dashboard is wrong but every job is green. How do you investigate?

Walk lineage upstream from the dashboard, check freshness/volume/distribution at each hop, find where the data diverged, then fix and add a check there so it fails loudly next time.

Common mistake

Monitoring only job success, not the data.

Concepts

Must knowSAP JOB REQUIREMENT
What it is

A warehouse stores structured, modelled data for SQL analytics. A lake stores any data as files on cheap object storage. A lakehouse puts warehouse features — transactions, schemas, performance — on top of lake files.

Why it exists

Warehouses were reliable but expensive and closed; lakes were cheap and flexible but became "data swamps" without transactions or quality. The lakehouse tries to get both.

Analogy

Warehouse: a library with a catalogue. Lake: a warehouse full of unlabelled boxes. Lakehouse: the boxes, but with a catalogue and a librarian who records every change.

You already know this — backend connection

Think of object storage (S3) as a giant immutable blob store. A lake is just files there. A lakehouse adds what you would add to make a blob store behave like a database: a transaction log, schema, and indexes — open formats (Parquet + Delta/Iceberg) so many engines can read the same data.

How it works

Warehouse: proprietary storage + SQL engine; strong performance and governance; storage and compute historically coupled. Lake: Parquet/JSON/CSV on S3/ADLS/GCS; any engine; no ACID; schema-on-read. Lakehouse: open table format (Delta Lake, Apache Iceberg, Hudi) adds ACID, schema enforcement, time travel and file-level statistics; one copy of data serves BI, ML and streaming.

Expert depth

Trade-offs: lakehouses still need file-layout care (small files, compaction, clustering) to match warehouse performance; governance comes from the catalogue (Unity Catalog, etc.). Many enterprises keep both: a warehouse for curated finance reporting, a lakehouse for everything else. Open formats matter for avoiding lock-in and for sharing data across platforms without copies.

Example

An enterprise keeps SAP finance data in its warehouse for statutory reporting, and builds a lakehouse combining SAP, CRM, IoT and documents for analytics and AI.

Interview answer
Warehouse = structured and governed; lake = cheap files of anything; lakehouse = warehouse guarantees on open lake files.
A warehouse holds modelled, structured data with strong SQL performance and governance. A lake holds any data cheaply as files but has no transactions. A lakehouse adds a transactional table format like Delta Lake on top of lake files, so one copy serves BI, ML and streaming with ACID guarantees.
A data warehouse is a database built for analytics: structured, modelled, fast SQL, strong governance, historically proprietary and costly. A data lake is just files on object storage — any format, very cheap, any engine — but without transactions, writes can collide, schemas drift, and it turns into a swamp. The lakehouse adds a transactional table format, Delta Lake or Iceberg, on top of the lake files: a transaction log gives ACID, schema enforcement and time travel, file statistics give performance, and because the format is open, Spark, SQL engines and ML tools all read one copy. You still need discipline on file layout and a catalogue for governance. I choose based on workload: curated statutory reporting may stay in a warehouse; mixed analytics, streaming and AI on diverse data fits a lakehouse.
Senior follow-up: Why not just put everything in the warehouse?

Cost at scale, unstructured and semi-structured data, ML workloads that want files, and lock-in. The warehouse remains good for curated, high-concurrency SQL.

Common mistake

Describing a lakehouse as "a lake with SQL" and missing the transaction log, which is the actual innovation.

Must knowSAP JOB REQUIREMENT
What it is

Delta Lake is an open table format: Parquet data files plus a transaction log that records which files make up the table at each version.

Why it exists

Plain Parquet folders have no transactions. A failed job leaves half-written files, readers see partial data, two writers corrupt each other, and you cannot update or delete rows.

Analogy

Parquet files are pages; the Delta log is the table of contents that says which pages belong to the book right now — and keeps every previous edition.

You already know this — backend connection

You know write-ahead logs and optimistic concurrency. The _delta_log is a WAL for a table on object storage: each commit is a JSON file listing files added and removed; readers reconstruct the table from the log; writers commit with optimistic concurrency.

How it works

Each write produces new Parquet files then atomically commits a new log entry (000…N.json) recording add/remove actions plus schema and statistics. Periodic checkpoints (Parquet) summarise the log. Readers see a consistent snapshot (snapshot isolation). Writers check for conflicts at commit time (optimistic concurrency) and retry. Deletes and updates rewrite affected files and mark old ones removed.

Expert depth

Because data files are immutable and the log is the source of truth, you get ACID, time travel (read version N), audit (DESCRIBE HISTORY), and schema enforcement. Operational care: OPTIMIZE compacts small files, Z-ORDER / liquid clustering co-locates data for skipping, VACUUM deletes unreferenced files after a retention period (which limits time travel). Deletion vectors avoid rewriting whole files for small deletes.

Example

A streaming job appends orders every minute while an analyst queries; the analyst always sees a consistent snapshot, and a failed batch never shows half its rows.

Updates, deletes and MERGE work by rewriting affected files. Operationally you compact with OPTIMIZE, cluster for data skipping, and VACUUM old files — remembering VACUUM limits how far back time travel can go.

Optimistic concurrency: both write files, the first commit wins, the second detects a conflict if it touched the same files/partitions and retries or fails. Partition the work or serialise writers to avoid repeated conflicts.

Saying Delta is "a better Parquet". The data is still Parquet; the log is what is new.

How it works

Enforcement: mismatched columns/types fail the write. Evolution: mergeSchema adds new columns explicitly. Time travel: SELECT … VERSION AS OF n / TIMESTAMP AS OF; RESTORE TABLE to roll back.     SELECT *, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY lsn DESC) AS rn

What it is

Why it exists

Interview-safe understanding. Know the idea and the integration questions; never claim hands-on use.

Say this if asked about HANA experience

"I have not worked with HANA hands-on. I understand its design — in-memory, columnar, running transactional and analytical work on one copy — and the integration questions that matter for a lakehouse: supported extraction, preserving business semantics, incremental changes and reconciliation."

Should knowSAP JOB REQUIREMENT
What it is

SAP HANA is SAP's in-memory, column-oriented database. It underpins S/4HANA (SAP's ERP) and is designed to run transactions and analytics on the same data.

Why it exists

Traditional ERP needed separate systems for transactions and reporting, with batch copies in between. Keeping data in memory and in columns made real-time analytics on live transactional data practical.

Analogy

Instead of photocopying the ledger to a separate reporting office every night, the accountant reads the live ledger — fast enough because it is all on the desk, sorted by column.

You already know this — backend connection

You know the OLTP/OLAP split and CDC replication. HANA's design argument is: remove the copy. You know in-memory stores (Redis) and columnar analytics; HANA combines in-memory and columnar with full SQL and ACID.

How it works

Column store (default) with compression and a write-optimised delta store merged into the main store; row store for some cases; in-memory primary storage with persistence (savepoints + logs) to disk; SQL plus calculation views for modelling; HANA Cloud is the managed cloud offering. Enterprise data reaching a lakehouse typically comes through SAP-supported integration and extraction tools rather than direct database access — VERIFY which mechanisms apply to the customer's landscape and licence.

Expert depth

Integration considerations for a lakehouse: respect SAP licensing and supported extraction paths; preserve business semantics (SAP tables are cryptic; business meaning lives in views and the application layer); handle CDC for deltas; reconcile totals with SAP reports. SAP Datasphere and SAP Business Data Cloud are SAP's data-platform offerings, and HANA Cloud has a vector engine for AI use cases — all VERIFY against current SAP documentation.

Example

A customer's S/4HANA sales orders feed an AI agent via a governed data product, with semantics from SAP views preserved, joined in the lakehouse with CRM and web data.

Interview answer
HANA is SAP's in-memory columnar database, designed to run transactions and analytics on one copy of data.
SAP HANA is SAP's in-memory, column-oriented database, the foundation of S/4HANA. Its core idea is running transactional and analytical workloads on the same data, removing the batch copy to a separate warehouse. I have not worked with HANA hands-on; I understand it through columnar storage and OLTP/OLAP design, which I know well.
HANA is SAP's in-memory, columnar, ACID database, and the platform S/4HANA runs on. SQL

The live-coding staples: joins, aggregation, window functions, dedup, top-N, optimisation.

Must knowSAP JOB REQUIREMENT
What it is

The core of analytical SQL: combine tables (joins), summarise (GROUP BY), filter groups (HAVING), and structure complex queries into readable steps (CTEs).

Why it exists

Most data-engineering logic — and most live SQL interview questions — are compositions of these.

Analogy

A CTE is naming an intermediate result on a whiteboard so the next step can refer to it.

You already know this — backend connection

You write SQL already; the shift is scale and semantics: a wrong join silently multiplies rows across a billion-row table.

How it works

INNER / LEFT / FULL / anti-join (LEFT JOIN … WHERE b.key IS NULL or NOT EXISTS) / semi-join (EXISTS). WHERE filters rows before grouping; HAVING filters groups after. CTEs (WITH) name steps; correlated subqueries run per row (often rewritable as joins or windows). NULL semantics: NULL = NULL is unknown; COUNT(col) skips NULLs; NOT IN with a NULL returns nothing.

Expert depth

Check cardinality after every join. Prefer NOT EXISTS over NOT IN. Filter early. Know that the optimiser may inline CTEs (no materialisation guarantee).

Example

Customers with no orders this month: anti-join customers to orders filtered to the month.

Interview answer
Joins combine, GROUP BY summarises, HAVING filters groups, CTEs make steps readable.
I build analytical queries as named steps with CTEs: filter early, join with known cardinality, aggregate with GROUP BY, and filter aggregates with HAVING. I watch NULL semantics, especially NOT IN.
I structure queries as a pipeline of CTEs, each one a clear step, which is easier to reason about and test. Joins are where most bugs hide: I know the expected cardinality before I write one, and check counts after, because a many-to-many join silently inflates totals. WHERE filters rows before aggregation and HAVING filters groups after. For "exists / does not exist" questions I use EXISTS and NOT EXISTS — NOT IN with a NULL in the subquery returns no rows, a classic trap.
Senior follow-up: Why does NOT IN return nothing here?

The subquery contains a NULL; x NOT IN (…, NULL) evaluates to unknown for every row. Use NOT EXISTS.

Common mistake

Joining without checking for duplicate keys on the "one" side.

Must knowSAP JOB REQUIREMENT
What it is

Window functions compute a value for each row using a set of related rows (a partition), without collapsing rows like GROUP BY does.

Why it exists

Ranking, deduplication, top-N per group, period-over-period change and running totals are everyday data-engineering tasks — and the most common live SQL questions.

Analogy

GROUP BY gives each class one average; a window gives each student their rank within the class while keeping every student on the list.

You already know this — backend connection

Like computing a per-key rolling value in a stream processor, but declaratively over a table.

How it works

func() OVER (PARTITION BY … ORDER BY … ROWS/RANGE BETWEEN …). ROW_NUMBER: unique 1..n (ties broken arbitrarily unless ordered fully). RANK: ties share, gaps after (1,1,3). DENSE_RANK: ties share, no gaps (1,1,2). LAG/LEAD: previous/next row's value. SUM() OVER (ORDER BY … ROWS UNBOUNDED PRECEDING) = running total. Filtering on a window result needs a subquery/CTE (or QUALIFY where supported).

Expert depth

Make ORDER BY deterministic (add a tiebreaker) or ROW_NUMBER results change between runs — a real source of flaky dedup. Default frame with ORDER BY is RANGE UNBOUNDED PRECEDING to CURRENT ROW, which treats ties as peers; specify ROWS for exact running totals. Windows over huge partitions cause skew in Spark.

Example

Latest record per customer from CDC: ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY lsn DESC) = 1.

Example code (sql)
-- 1. Latest version of each customer (dedup)
WITH ranked AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY updated_at DESC, lsn DESC) AS rn
  FROM bronze.customers)
SELECT * FROM ranked WHERE rn = 1;

-- 2. Top 3 products per region (ties kept)
WITH r AS (
  SELECT region, product_id, SUM(amount) AS revenue,
         DENSE_RANK() OVER (PARTITION BY region ORDER BY SUM(amount) DESC) AS dr
  FROM gold.order_lines GROUP BY region, product_id)
SELECT * FROM r WHERE dr <= 3;

-- 3. Month-over-month change and running total
SELECT month, revenue,
       revenue - LAG(revenue) OVER (ORDER BY month)                          AS mom_change,
       SUM(revenue) OVER (ORDER BY month ROWS UNBOUNDED PRECEDING)           AS running_total
FROM gold.monthly_revenue;
Interview answer
Window functions compute per-row values over a partition without collapsing rows — used for dedup, top-N and running totals.
Window functions compute across a partition of rows while keeping each row. I use ROW_NUMBER for deduplication and latest-record, RANK or DENSE_RANK for rankings with ties, LAG and LEAD for change over time, and SUM over an ordered window for running totals.
A window function computes a value for each row using related rows — the partition — ordered within it, without collapsing the rows as GROUP BY does. The three ranking functions differ only on ties: ROW_NUMBER always gives unique numbers, RANK gives ties the same rank and leaves gaps, DENSE_RANK gives ties the same rank without gaps. ROW_NUMBER partitioned by key and ordered by a change sequence descending is my standard dedup and latest-record pattern; I always add a tiebreaker so it is deterministic. LAG and LEAD give period-over-period comparisons, and SUM over an ordered frame gives running totals — specifying ROWS rather than the default RANGE so ties do not jump together. To filter on a window result I wrap it in a CTE or use QUALIFY where available.
Senior follow-up: Top 3 products by revenue per region, with ties included?

DENSE_RANK() OVER (PARTITION BY region ORDER BY revenue DESC) <= 3 in an outer query. Use ROW_NUMBER if exactly 3 rows are required.

Common mistake

Non-deterministic ORDER BY in ROW_NUMBER dedup.

What it is

Making queries fast by reading less data and moving less data — guided by the execution plan.

Why it exists

At lakehouse scale a bad query is not just slow, it costs real money and blocks others.

Analogy

A good plan is the shortest route; the execution plan is the route the satnav actually chose.

You already know this — backend connection

Same as tuning service-database queries with EXPLAIN — but in OLAP, indexes are mostly replaced by partition pruning, file statistics and clustering.

How it works

Read the plan: scans (how many files/partitions), filters pushed down, join strategy, shuffles/exchanges, spill. OLTP: B-tree indexes, covering indexes, avoid functions on indexed columns. OLAP/lakehouse: partition by low-cardinality filter columns (date), cluster/Z-order on frequent filters and join keys, keep files 128 MB–1 GB, compute statistics, avoid SELECT *.

Expert depth

Make predicates sargable (filter on the raw column, not a function of it). Push filters before joins. Pre-aggregate in gold for dashboards. Use materialised views or summary tables for repeated heavy queries. Compare cost per query, not only latency.

Example

Dashboard query scanning 4 TB is rewritten to filter on the partition column and read a pre-aggregated gold table: 12 GB scanned, 40× cheaper.

Interview answer
Read the plan, scan less (pruning, clustering), move less (broadcast, pre-aggregate).
I start from the execution plan: how much is scanned, whether filters are pushed down, how joins execute. In a lakehouse the levers are partition pruning, clustering for data skipping, file sizes and pre-aggregation, rather than classic indexes.
I start every optimisation from the plan rather than guessing: how many partitions and files are scanned, whether predicates were pushed down, which join strategy ran, and where data was shuffled or spilled. Then the levers are reading less and moving less. Reading less: filter on the partition column directly, select only needed columns, cluster or Z-order on common filters so file statistics skip data, keep file sizes healthy. Moving less: broadcast small joins, filter before joining, pre-aggregate into gold tables for repeated dashboard queries. In OLTP the equivalent tools are indexes; in OLAP they are layout and statistics. And I measure cost per query, because at this scale cost is the metric the customer feels.
Senior follow-up: Why is WHERE YEAR(order_date) = 2026 slow on a date-partitioned table?

The function on the partition column can prevent pruning. Use order_date >= '2026-01-01' AND order_date < '2027-01-01'.

Optimising without looking at the plan.

Data Quality

The JD says "ensure data quality". This is how you make that concrete.

Must knowSAP JOB REQUIREMENT
What it is

Data quality is measured on dimensions: completeness, accuracy, consistency, validity, uniqueness and freshness — each turned into automated checks.

Why it exists

Decisions and AI agents are only as good as the data. Enterprise customers lose trust in a platform after one wrong number in a board report.

Analogy

A quality inspection line in a factory: measure every batch against the spec before it ships.

You already know this — backend connection

Like contract tests and health checks — but on datasets. A null rate is an error rate; freshness is latency.

How it works

Completeness: required fields present, expected row counts. Accuracy: matches reality / source of truth (reconcile totals with SAP). Consistency: same fact agrees across tables. Validity: types, ranges, allowed values, formats. Uniqueness: no duplicate keys. Freshness: updated within SLA. Implement with expectations (Delta Live Tables / Lakeflow expectations, Great Expectations, dbt tests) at layer boundaries; decide per check: warn, drop/quarantine rows, or fail the pipeline.

Expert depth

Tier checks by impact: critical financial tables fail the pipeline; others quarantine bad rows to a table with reasons. Track quality metrics over time (trend, not only pass/fail). Reconciliation against the source system is the check finance trusts most.

Example

Silver orders: order_id unique, amount ≥ 0, currency in ISO list, customer_id exists in customers (quarantine otherwise), row count within ±20% of 7-day average, total reconciles with ERP within 0.1%.

Interview answer
Measure completeness, accuracy, consistency, validity, uniqueness and freshness with automated checks at layer boundaries.
I define quality on six dimensions — completeness, accuracy, consistency, validity, uniqueness, freshness — and implement them as automated checks at each layer boundary. Each check has an action: warn, quarantine bad rows, or fail the pipeline, depending on how critical the table is.
I treat data quality like service reliability: defined dimensions, automated checks, and an action for each failure. Completeness and uniqueness catch broken loads and duplicate keys; validity catches bad types and values; consistency checks that the same fact agrees across tables; accuracy, in an enterprise, usually means reconciling totals with the source system — for SAP data, with SAP's own reports, because that is what the business trusts; and freshness is the latency SLO. Checks run at layer boundaries. For critical tables a failure blocks promotion; for others bad rows are quarantined with a reason so the good data still flows. I track the metrics over time, and every check has an owner.
Senior follow-up: A quality check fails at 3 am on the finance table. What should happen?

Pipeline stops promoting to gold (yesterday's data stays visible, marked stale), owner is alerted with the failing rows, consumers see a freshness warning. Never silently publish.

Common mistake

Only checking for nulls and calling it data quality.

Governance and PII

Catalogue, access, lineage, audit, lifecycle — and the AI-specific leak paths.

Must knowSAP JOB REQUIREMENT
What it is

Governance is knowing what data you have, who owns it, who may use it for what, and proving it — through a catalogue, lineage, access controls, audit logs and retention rules.

Why it exists

Enterprises are regulated. They must answer "who accessed this customer's data?" and delete it when required. Without governance, an AI agent can leak data across business units.

Analogy

A library's catalogue, membership cards and check-out records — plus a policy on which books are reference-only.

You already know this — backend connection

You know IAM, RBAC, audit logging and tenant isolation. Governance applies them to tables, columns and rows, and adds lineage and lifecycle.

How it works

Catalogue: central metadata (Unity Catalog, SAP-side catalogues, etc.) with owners, descriptions, tags (PII, confidential). Access: RBAC/ABAC on catalog/schema/table, column masking, row-level filters, tag-based policies. Lineage: auto-captured. Audit: who queried what, when. Lifecycle: retention periods, archival, deletion (GDPR right to erasure — with Delta, DELETE then VACUUM to physically remove).

Expert depth

Design for least privilege by default and grant via groups. Tag at ingestion so policies follow data downstream. Erasure must reach every copy: bronze, silver, gold, caches, vector indexes, and backups per policy. AI agents should query through the same governed layer with the user's identity, not a super-user service account.

Example

A data product "customer_orders" is tagged PII; analysts in India see masked emails, the EU support agent sees rows only for EU customers, and every query is audited.

Interview answer
Governance = catalogue + ownership + access control + lineage + audit + lifecycle.
Governance means a catalogue with owners and classifications, fine-grained access control — table, column masking, row filters — automatic lineage, audit logs, and retention and deletion policies. I apply the same least-privilege principles I used for tenant isolation, and make AI agents go through the same controls.
Governance answers four questions: what data do we have and who owns it — the catalogue with classifications; who can see what — role- or attribute-based access down to columns and rows, ideally driven by tags applied at ingestion; where did it come from and where does it go — lineage; and can we prove it — audit logs and retention. Lifecycle matters too: retention rules and erasure that reaches every copy, including derived tables, caches and vector indexes. My Isolated Cloud work at Atlassian was largely a governance problem at infrastructure level — tenant isolation, controlled egress, policy-driven enforcement — and the same instincts apply here. One AI-specific rule: agents access data through the governed layer with the end user's permissions, never through a privileged service account.
Senior follow-up: A customer invokes GDPR erasure. What do you delete in a lakehouse?

Every copy: bronze/silver/gold via DELETE + VACUUM (beyond time-travel retention), derived aggregates if re-identifiable, caches, feature stores, vector indexes and embeddings; record the erasure in an audit log.

Common mistake

Giving pipelines and agents a single admin service account.

Must knowSAP JOB REQUIREMENT
What it is

Techniques to protect personal data: masking hides it from viewers, tokenisation replaces it with a reversible surrogate held in a vault, encryption makes stored or transmitted data unreadable without keys.

Why it exists

The JD names PII protection explicitly. A leak is a regulatory, legal and trust failure — and AI systems create new leak paths (prompts, logs, embeddings).

Analogy

Masking: showing only the last four digits of a card. Tokenisation: a cloakroom ticket for your coat. Encryption: a locked safe.

You already know this — backend connection

You know TLS, KMS and secrets management. Add field-level protection and the data-specific leak paths: joins re-identifying people, logs, model inputs.

How it works

Classify and tag PII at ingestion. Encryption at rest (KMS, customer-managed keys) and in transit (TLS). Tokenisation of identifiers (deterministic tokens keep joinability without exposing values). Dynamic masking by role at query time. Pseudonymisation for analytics; aggregation thresholds to avoid re-identification. For AI: redact before sending to models, do not log raw prompts with PII, govern embeddings like the source text.

Expert depth

Deterministic tokenisation enables joins but is vulnerable to dictionary attacks on low-entropy values — use keyed (HMAC) tokens. Masking is a view-level control, not protection of the underlying storage. Data residency may constrain where processing (including model inference) happens. Customer-managed keys let the customer revoke access.

Example

National ID tokenised at ingestion (HMAC with a vaulted key); email masked except for the support role; prompts to the LLM redact names and IDs; vector index built only from approved fields.

Interview answer
Classify PII, then encrypt, tokenise or mask by use — and cover AI leak paths.
I classify PII at ingestion and protect it by use: encryption at rest and in transit, tokenisation for identifiers that must stay joinable, dynamic masking by role, and redaction before data reaches an LLM or logs. Embeddings are governed like the text they came from.
I start by classifying and tagging PII as it lands, because policies can only follow data that is labelled. Then I pick the control by use. Encryption at rest and in transit is the baseline, ideally with customer-managed keys. Identifiers that analytics needs to join on are tokenised with a keyed hash, so joins work but the raw value is not exposed. Fields people need to see partially are masked dynamically by role. For AI there are new leak paths: prompts, model logs, and embeddings that can reproduce source text. So I redact before inference, avoid logging raw prompts, keep vector indexes under the same access control as their source, and respect data residency for where the model runs. This is very close to my Isolated Cloud work, where customer data could not leave the customer's boundary.
Senior follow-up: Is masking enough to protect PII?

No — it is a presentation control. Storage, copies, logs, extracts and model inputs still hold the raw value. Combine with tokenisation/encryption and access control.

Common mistake

Forgetting logs, prompts and embeddings as places PII ends up.

Agentic AI

The JD asks you to "operate effectively in an Agentic AI context". Here is what that means in engineering terms.

Must knowSAP JOB REQUIREMENT
What it is

An AI agent is an LLM in a loop: it decides the next step, calls tools (APIs, queries, actions), observes the results, and continues until the goal is reached or it hands back to a human.

Why it exists

A plain LLM can only produce text from what it already knows. Business processes need it to look things up in live systems and take actions — under control.

Analogy

A capable new assistant with a list of systems they may use, a checklist, and a manager who approves anything risky.

You already know this — backend connection

An agent is an orchestrator whose control flow is decided by a model at runtime instead of code. Tools are APIs with schemas; the agent loop is a workflow engine; guardrails are authorisation and validation middleware. Everything you know about API design, idempotency and authz applies.

How it works

Components: model; tools (function definitions with schemas — read tools and write tools); planning/reasoning; memory (conversation state; long-term memory in a store); retrieval (RAG) for knowledge; orchestration (single agent loop or multi-agent with a supervisor); guardrails (input/output filters, tool allowlists, parameter validation, spending/step limits); human-in-the-loop approval for consequential actions; observability (traces of every step).

Expert depth

Prefer deterministic workflows with LLM steps where the path is known; use agents where the path genuinely varies. Tools should be narrow, idempotent, permission-checked with the end user's identity, and return structured data. Write actions need confirmation and audit. Failure modes: loops, wrong tool, hallucinated parameters, prompt injection via tool outputs, runaway cost.

Example

A procurement agent checks inventory (read tool on a governed data product), finds a shortfall, drafts a purchase requisition (write tool), and routes it to a buyer for approval before anything is created in the ERP.

Interview answer
An agent is an LLM that plans, calls tools, observes results and iterates — with guardrails and human approval on consequential actions.
An agent runs an LLM in a loop: it plans the next step, calls a tool such as a data query or a business API, reads the result, and repeats until done. In enterprises the engineering is in the controls: narrow permission-checked tools, validation, step and cost limits, human approval for actions, and full tracing.
An agent is an LLM in a control loop. Given a goal, it decides on a step, calls a tool — query a data product, look up an order, create a draft requisition — observes the result, and continues, possibly handing off to other agents or a human. The model provides the reasoning; the engineering provides everything that makes it safe in a business process. Tools are narrow, typed, idempotent APIs that check authorisation with the end user's identity. Read tools are cheap; write tools require confirmation or human approval and are audited. Guardrails cap steps and spend, validate parameters, and treat tool outputs as untrusted to resist prompt injection. Every step is traced so you can debug and evaluate. And I only use an agent where the path really varies — if the steps are known, a deterministic workflow with LLM calls in it is cheaper and more reliable. For a data engineer the biggest lever is data: agents are only as good as the governed, well-described data products they can query.
Senior follow-up: Where would you NOT use an agent?

Fixed, auditable processes with known steps (use a workflow), high-volume low-latency paths, and anything where an error is irreversible without human approval.

Common mistake

Giving an agent broad write access through a service account "to make the demo work".

Example

Interview answer
LLM answers from memory; RAG grounds answers in retrieved data; agents plan and take actions with tools.
An LLM answers from training data; RAG retrieves the relevant enterprise documents or data first so answers are grounded and current; an agent goes further, planning and calling tools to complete tasks. Jumping to multi-agent systems for a document Q&A problem.

RAG

A search system with a generator on the end — engineer it that way.

Must knowSAP JOB REQUIREMENT
What it is

Retrieval-augmented generation: find the most relevant pieces of your content for a question, give them to the LLM, and ask it to answer only from them.

Why it exists

LLMs do not know your private, current data, and they invent plausible details. Grounding answers in retrieved sources fixes both — if retrieval is good.

Analogy

An open-book exam: the quality of the answer depends on finding the right page.

You already know this — backend connection

It is a search system with an LLM on the end. Indexing is an ETL pipeline; retrieval is a search query; the prompt is a template; freshness and access control are your usual cache-invalidation and authorisation problems.

How it works

Ingest: extract text, clean, chunk (by structure; 200–800 tokens with overlap), attach metadata (source, date, ACL). Embed chunks into vectors; store in a vector index (Databricks Vector Search, HANA Cloud vector engine — VERIFY — pgvector, etc.). Query: embed the question, retrieve top-k by similarity, often hybrid with keyword (BM25) for names and codes, filter by metadata/ACL, rerank with a cross-encoder, then prompt with sources and require citations. For structured data, retrieval is SQL against governed tables (text-to-SQL or predefined tools), not vectors.

Expert depth

Most RAG failures are retrieval failures: bad chunking, missing metadata filters, stale index, no keyword search for exact identifiers. Enforce access control at retrieval time (filter by the user's permissions) — never rely on the prompt. Keep the index fresh with incremental pipelines (CDC on documents). Evaluate retrieval separately (recall@k) from generation (faithfulness).

Example

Support assistant over 40,000 product manuals and tickets: hybrid retrieval, filtered to products the customer owns, reranked to 5 chunks, answer with citations; index updated hourly from a Delta table.

Interview answer
RAG retrieves relevant, permitted content and asks the LLM to answer only from it, with citations.

Studied in Delta Lake

Must know
Short answer

Delta Lake = Parquet files + a transaction log, giving ACID, schema enforcement and time travel on a data lake.

Detailed answer

Delta Lake adds a transaction log on top of Parquet files. Every write is an atomic commit listing which files were added and removed, so readers get consistent snapshots, concurrent writers are safe, and you can update, delete, MERGE and time-travel — none of which plain Parquet supports.

Senior-level answer

Delta Lake is a table format, not a different file format: the data is still Parquet. What it adds is the _delta_log, which works like a write-ahead log for a table on object storage. A write first creates new Parquet files, then atomically commits a log entry saying "add these files, remove those". Readers build a snapshot from the log, so they never see partial writes; concurrent writers use optimistic concurrency and retry on conflict. Because files are immutable and the log keeps history, you get ACID, time travel to earlier versions, an audit history, and schema enforcement. Updates, deletes and MERGE work by rewriting affected files. Operationally you compact with OPTIMIZE, cluster for data skipping, and VACUUM old files — remembering VACUUM limits how far back time travel can go.

Follow-up: Two jobs MERGE into the same Delta table at once. What happens?

Optimistic concurrency: both write files, the first commit wins, the second detects a conflict if it touched the same files/partitions and retries or fails. Partition the work or serialise writers to avoid repeated conflicts.

Saying Delta is "a better Parquet". The data is still Parquet; the log is what is new.

Walk lineage upstream from the dashboard, check freshness/volume/distribution at each hop, find where the data diverged, then fix and add a check there so it fails loudly next time.

Short answer

Joins combine, GROUP BY summarises, HAVING filters groups, CTEs make steps readable.

Detailed answer

I build analytical queries as named steps with CTEs: filter early, join with known cardinality, aggregate with GROUP BY, and filter aggregates with HAVING. I watch NULL semantics, especially NOT IN.

Senior-level answer

I structure queries as a pipeline of CTEs, each one a clear step, which is easier to reason about and test. Joins are where most bugs hide: I know the expected cardinality before I write one, and check counts after, because a many-to-many join silently inflates totals. For "exists / does not exist" questions I use EXISTS and NOT EXISTS — NOT IN with a NULL in the subquery returns no rows, a classic trap.

Follow-up: Why does NOT IN return nothing here?

The subquery contains a NULL; x NOT IN (…, NULL) evaluates to unknown for every row. Use NOT EXISTS.

Joining without checking for duplicate keys on the "one" side.
