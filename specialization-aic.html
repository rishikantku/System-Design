Atlassian Isolated Cloud

One project, told properly. What you built, why you built it that way, and the questions you will be asked about it.

📖 How to use this

Fifteen sections, about twenty minutes to read. Three parts:

  • Part 1 — The system. What Isolated Cloud is. Skim it; you know it.
  • Part 2 — What you built. The architecture and the decisions. This is the material the interview is about.
  • Part 3 — The interview. The format, your story, the drill chains, your questions.

If you only have ten minutes: read §6, §12 and §13.

One rule above all others. Do not invent a number, an outcome or a fact. “I’d have to check” costs nothing in a retrospective. A number that unravels costs you the interview.
Part 1

The system

1

What Isolated Cloud is

Atlassian Cloud is multi-tenant. That works for almost everyone.

Some enterprises cannot use it. Banks, critical infrastructure, regulated industries. Their rules say they may not share infrastructure. Logical isolation does not satisfy a rule that says dedicated.

Isolated Cloud gives those customers a dedicated environment, run by Atlassian.

What they getDetail
Dedicated infrastructureTheir own AWS accounts, VPC, networking, compute, storage, databases
Their own keysCustomer-managed encryption keys, held in the customer’s own AWS account
Egress blocked by defaultData does not leave unless a policy allows it
Their own domainDedicated edge and domain, not the shared one
Not their own control planeProvisioning, deployment and operations stay shared. This is the whole design.

The last row matters most. Atlassian did not build a separate copy of itself per customer. That would mean running hundreds of Atlassians. The data plane is dedicated. The control plane is shared.

🎯 Say this in one breath

“Isolated Cloud is Atlassian Cloud deployed one customer at a time. Dedicated infrastructure, dedicated keys, no egress by default. But the control plane stays shared, because duplicating it per customer does not scale. All the hard engineering is at that boundary.”

2

What you can cite, and what you cannot

Two kinds of claim in this document. Keep them apart in the interview.

TagMeaning
PUBLICIn Atlassian’s public documentation. Anyone can check it. Safe to state as fact.
YOURSYour own work and architecture. Not public, so not citable. You know it first-hand, which is better.

Almost everything in Part 2 is YOURS. That is the point. The interview is about what you did.

Use your judgement on which internal names you say out loud.

Part 2

What you built

3

The one idea

YOURS Atlassian had about 178 engineering teams. Every service assumed one deployment serves all tenants.

Isolated Cloud breaks that assumption. A tenant now needs its own deployment.

There were two ways to fix it.

OptionWhat happens
Each product fixes itself178 teams each build provisioning, placement and lifecycle. 178 different answers. It never converges, and product 179 starts from nothing.
The platform fixes it onceThe platform owns provisioning, routing, placement, lifecycle and egress. Teams adopt a configuration model. Future products get isolation for free.
🎯 The sentence everything comes from

Isolation is a platform capability, not a product feature.

Every component below exists because of that choice.

This is also why it was a Staff problem, not a Senior one. Pushing work into the platform is a normal engineering move. Getting 178 teams to accept an abstraction they did not design, when each has a fair case for being an exception, is the hard part.

4

Control plane and data plane

YOURS Two planes, with opposite characteristics.

Control planeCustomer data plane
JobProvisioning and lifecycleServing customer traffic
Shared?Shared across customersDedicated per customer
How oftenRarelyConstantly
On the request path?NoYes

The control plane creates AWS accounts, VPCs, databases, storage and keys. It configures deployment, monitoring and logging. It holds tenant metadata and manages the environment’s lifecycle.

Then it gets out of the way. It does not serve customer requests. Provisioning can take minutes and can fail. A request cannot.

5

The request path

Draw this first if someone asks how a request works.

Client | v GLOBAL EDGE handles the request, forwards to Router | v ROUTER is this tenant commercial or isolated? | caches tenant context in memory | miss -> Tenant Context Service v TENANT CONTEXT who is this tenant, which environment | +--- commercial ---> commercial runtime | +--- isolated -----> SHARD MANAGER | v which shard serves this tenant? ISOLATED SHARD | replica 1 / 2 / 3 | v DEDICATED DATA | v EGRESS GATEWAY policy check | v external systems

Two things people get wrong here.

The edge does not decide placement. It handles the request and passes it on.

The Router does not pick the shard. It only decides commercial or isolated. The next section explains why.

6

Why Router and Shard Manager are separate

YOURS This is your strongest answer. It is a decision with a reason, not a component description.

Two questions have to be answered at runtime:

ComponentAnswers
Router“Who is this tenant, and is it commercial or isolated?”
Shard Manager“Which shard serves this tenant right now?”

The obvious design puts both in the Router. One component, one lookup. We did not, because the two facts behave differently.

Tenant contextShard placement
ChangesRarelyOften
Changes whenA tenant moves environment or entitlementFailure, maintenance, deployment, migration, capacity
Cacheable?VeryOnly against a moving truth
NatureIdentityOperational

Putting both in the Router ties a stable thing to a volatile one. The Router sits on every request. It would have to track placement changes constantly.

Separating them means a shard can be replaced without anything about the tenant changing.

The cost

One more component to run. One more hop for isolated tenants. We took that trade.

The catch worth volunteering

The Router caches tenant context. When a tenant moves from commercial to isolated, that cache must be invalidated. Until it is, requests go to the wrong place.

That is a correctness problem, not a performance one. Say this before you are asked. It shows you thought about the transition, not just the end state.

7

Shards and replicas

⚠ Fix this before anything else
“A shard is a tenant’s instance of a service.”

YOURS A shard is a logical isolated deployment for one tenant and one product. It contains several replicas.

Shard is not replica. Shard is not a machine.

Also: people hear “shard” and think data partition. It is not that either. Say so early or the whole explanation drifts.

Tenant A | +-- Jira Shard-123 | +-- Replica 1 +-- Replica 2 +-- Replica 3 Traffic rises replicas scale AWS Auto Scaling the shard does not change A replica fails infrastructure replaces it the tenant -> shard mapping does not change A shard is replaced Tenant A -> Shard-123 becomes Shard-456 now placement is updated and the cache invalidated

That last distinction is what interviewers probe. Confusing replica failure with shard replacement is the clearest sign someone has only heard the architecture described.

Where placement truth lives

The shard configuration repository is the source of truth. A cache may sit in front of it for speed.

The cache is never the source of truth. If it is lost, you pay latency while it refills. You do not lose correctness.

Why not Kubernetes

Scaling uses AWS-native Auto Scaling. Isolation multiplies environments, so every extra moving part is multiplied too. Another orchestration layer would have been a second platform to operate inside every isolated environment, for a problem AWS already solved.

8

The shard descriptor

YOURS Each service used to have a service descriptor: CPU, memory, keys, database, scaling strategy.

That worked when there was one deployment. It breaks when every tenant needs their own.

So the model split. The service descriptor describes the service. A shard descriptor describes one tenant’s runtime of it.

ONE PRODUCT SERVICE | +-- Shard A -> Tenant A config +-- Shard B -> Tenant B config +-- Shard C -> Tenant C config compute, memory, networking, storage, keys, monitoring

Now one tenant can be sized for their traffic without touching the service definition or any other tenant.

This is what made adoption cheap. Teams did not rewrite business logic. They adopted a configuration model. That is the link between the technical design and 178 teams actually finishing.

Expect: “You just multiplied your config surface by the number of tenants.”

Fair. The service level still holds what is common; a shard descriptor holds what is specific, and it lives in the repository rather than in 178 hand-edited places.

Concede the real risk: per-shard settings are easy to add and nobody removes them. Over time you get tenants on bespoke config whose reason is forgotten.

9

The Egress Gateway

YOURS Outbound data goes through one place, where policy is checked.

PRODUCT -> EGRESS GATEWAY -> POLICY CHECK -> external system

Why centralise it: outbound data control is a cross-cutting compliance concern.

If 178 teams each write their own policy, the guarantee is only as strong as the weakest one. And a policy that is too permissive produces no error. You find out at an audit.

Do not name a policy engine you have not verified. Say “policy-driven enforcement”.

10

Migrating 178 teams

YOURS Phased, not all at once. Grouped by dependency, criticality and priority.

TierWhatExamples
L0Foundation. Migrate first.Identity, Global Edge
L1Near the edge, shared platformShared gateway services, observability
L2Products the first enterprise tenants needJira, Jira Service Management, Confluence, Trello
L3The tail. Lower priority, less traffic.Everything else

Nothing migrates before what it depends on. That is why identity and the edge are L0.

YOURS You also inserted an L2.5 for services that fit neither L2 nor L3. A fractional tier refines the order without renumbering 178 services, which would have broken every dashboard and runbook keyed to the old values.

What the ordering considered

Dependency graph, business priority, traffic, risk, operational readiness.

Only the first is a hard constraint. A pure dependency sort gives a valid order and an unworkable plan, because it ignores whether the team at position 40 has capacity this quarter.

🎯 The Staff point

This was an organisational strategy, not a technical one. Say that.

You had no authority over any of those teams. Adoption came from keeping the integration cost low enough that teams chose it.

Part 3

The interview

11

What a retrospective is

Not a system design round. They are not testing whether you can design something. They are testing whether you owned something.

System designRetrospective
Tense“I would…”“We did, and here is why”
WantsOptionsDecisions and their consequences
Last question“How would you scale it?”“What would you change today?”

The hour: a short intro, about 40 minutes on one project, about 15 minutes of your questions.

Forty minutes on one project means they go deep, not wide. Expect five to seven levels on a single thread.

⚠ The failure mode
Drifting into design mode. “You could also do X, and another option would be Y…”

The moment you list options in the abstract, you sound like someone describing a system they read about.

Alternatives belong in the answer, but in past tense with a verdict. “We considered putting it in the Router. We rejected it because…”

12

Your story

Ninety seconds

“Atlassian’s cloud is multi-tenant. Regulated enterprises need stronger isolation, and their rules don’t accept shared infrastructure. So we built Isolated Cloud — dedicated environments per customer.

The obvious way is for every product to redesign itself for isolation. We had about 178 teams, so that doesn’t finish.

The position we took was that isolation is a platform capability, not a product feature. The platform owns provisioning, routing, placement, lifecycle and egress. Teams adopt a configuration model instead of rewriting business logic.

At runtime, a request goes edge to Router. The Router decides commercial or isolated. If isolated, the Shard Manager resolves which shard serves them. A shard is a logical isolated runtime for one tenant and product, with replicas underneath it.

The decision I’d highlight is separating tenant context from shard placement. Identity is static and caches well. Placement is operational and changes constantly. Keeping them apart means a shard can be replaced without anything about the tenant changing.”

The shape of a good answer

For your two or three big answers, walk this chain. For smaller questions, pick the three or four links that were actually asked about.

context → problem → constraint → options → decision → why → trade-off → execution → impact → lesson

Always include the constraint and the trade-off. Those two are what make it a retrospective instead of a description, and they are the two people skip.

Senior versus Staff

Both answers below are correct. Only one gets the level.

AskedSeniorStaff
Why a Shard Manager?What it does: owns placement, maps tenant to shard, handles lifecycle.Why it is separate: two facts with different volatility, and coupling them makes placement changes touch tenant identity.
How did teams adopt it?“We documented it and leadership backed it.”“Mandates don’t work at 178 teams. We kept integration cost low and sequenced by dependency so nobody was blocked.”
What went wrong?Names an incident and the fix.Names what the incident revealed about the design, and what changed so the class of failure can’t recur.
🎯 The pattern

Senior describes the system. Staff describes the decision and what it cost.

If you catch yourself listing what a component does, add: “we did it that way because the alternative would have…” That one sentence usually moves the answer a level.

13

The drill chains

They will go five to seven levels down one thread. Practise the depth, not a script. A memorised answer collapses at level four, because level four asks about a consequence.

1The separation decisionOpen

  1. “Why did you introduce a Shard Manager?”

    Good answer: Placement needed an owner, and placement is dynamic. It changes on failure, maintenance, deployment and migration.

    Trap: Listing what it does. That is a component, not a decision.

  2. “Why couldn’t the Router do it?”

    Good answer: Tenant context is identity and rarely changes, so it caches well. Placement is operational and changes often. Coupling them makes the Router chase a moving target on every request.

    Trap: “Separation of concerns.” True, generic, and it does not show you understood these concerns.

  3. “What alternatives did you consider?”

    Good answer: Resolving the shard in the Router. One component, one lookup, less to run. Say it was the simpler option, because it was.

    Trap: Claiming there was no alternative.

  4. “What was the trade-off?”

    Good answer: An extra component and an extra hop. Bought: a shard can be replaced without touching tenant identity.

    Trap: Saying it was free.

  5. “What happened when a shard failed?”

    Good answer: Separate the two cases. A replica fails and infrastructure replaces it, mapping unchanged. A shard is replaced, so placement updates and the cache is invalidated.

    Trap: Confusing the two. This is the clearest tell that you only heard the architecture.

  6. “How did you convince other teams?”

    Good answer: Mostly invisible to them, which was the point. Where visible, the argument was cost: they did not have to build placement themselves.

    Trap: “Leadership mandated it.”

  7. “What would you change today?”

    Good answer: Cache invalidation as a first-class design concern from the start, not an operational detail.

    Trap: “Nothing.” Weak note to end on.

Rehearse rungs 2, 4 and 7. Reasoning, cost, reflection.
2The platform thesisOpen

  1. “Why was this a platform problem?”

    Good answer: 178 teams. Per-product isolation is 178 implementations that never converge.

    Trap: Starting with components. Start with the number.

  2. “Didn’t that slow every team down?”

    Good answer: It constrained them. They gave up local control of deployment config. Cheaper than rewriting business logic.

    Trap: Denying there was a cost.

  3. “What if a team said they were special?”

    Good answer: Tell a real gap from a preference. A gap several teams hit is a platform bug. A preference gets held, because one exception makes the abstraction optional.

    Trap: Absolutism either way.

  4. “What did it cost the organisation?”

    Good answer: A platform everything depends on, and a team that must keep it healthy. Centralising turns many small risks into one shared one.

    Trap: Only listing benefits.

Lead with 178 teams, not with architecture.
3Operations and failureOpen

  1. “What happens when something breaks at runtime?”

    Good answer: Pick a level and be specific: replica failure, shard replacement, stale Router cache, cold placement cache.

    Trap: Generic reliability talk.

  2. “What if the Router cache is stale after a migration?”

    Good answer: Requests keep going to the commercial runtime. Correctness problem, not performance.

    Trap: Treating it as latency.

  3. “What if the placement cache is lost?”

    Good answer: The repository is the source of truth. You pay latency, not correctness.

    Trap: Describing the cache as authoritative.

  4. “Tell me about a real incident.”

    Good answer: One incident: what happened, how you found it, what changed structurally afterwards.

    Trap: “We were more careful.” The fix must prevent the class, not the instance.

Have one real incident with a structural outcome.
4Cross-team executionOpen

  1. “How did you get 178 teams to migrate?”

    Good answer: Phased. Grouped by dependency, criticality and priority. Ordered against dependency, traffic, risk and readiness.

    Trap: Describing it as purely technical.

  2. “Why that order?”

    Good answer: Dependency is the hard constraint. Identity and edge first. Everything else optimises inside that.

    Trap: Giving only the dependency answer.

  3. “Where did it stall?”

    Good answer: The long tail. Teams with other priorities, or no owner after a reorg.

    Trap: Claiming it went smoothly. Nobody believes that at 178 teams.

  4. “What did you do when a team deprioritised it?”

    Good answer: Work out whether it was capacity, a platform gap, or disagreement. Each needs a different response. Repeated blockers are platform bugs.

    Trap: Escalating first.

  5. “How did you know a team was actually done?”

    Good answer: It has to be mechanical, not self-reported. Self-reported status at 178 teams is uniformly optimistic.

    Trap: Trusting status updates.

This is where the Staff signal is strongest. Do not let it become technical.
5ReflectionOpen

  1. “What would you do differently?”

    Good answer: One or two real, specific, architectural things. Cache invalidation is defensible.

    Trap: “Nothing.” Or something cosmetic.

  2. “What is the weakest part of the design?”

    Good answer: Pick something real and say why you accepted it. Centralisation concentrates risk. Per-shard config accumulates drift.

    Trap: Deflecting to things outside your control.

  3. “What surprised you?”

    Good answer: Something harder or easier than expected, and what it taught you about how you estimate.

    Trap: A non-answer. This is an invitation.

  4. “What would you tell a team here doing something similar?”

    Good answer: Transfer the principle, not the architecture. Decide early what belongs to the platform, because retrofitting that line is expensive.

    Trap: Re-describing your project.

Most under-rehearsed chain, and it usually lands last.
14

Your fifteen minutes

A quarter of the interview. It is scored. Running dry after three questions is noticeable.

Lead with these

QuestionWhy
“How does a decision affecting several teams actually get made here?”Tells you whether a Staff engineer can be effective or is just advisory. Listen for a mechanism, not a person.
“What is the most recent architectural decision this team got wrong, and how did you find out?”Tests whether there is a real feedback loop, and whether it is safe to be wrong.
“What would you want someone in this role to have changed a year in?”Gets the real expectation, not the job description.

Then, as the conversation allows

  • “Where does the line sit between what the platform owns and what product teams own?”
  • “What architectural decision made years ago do you still work around?”
  • “What does on-call look like — pages per shift, honestly?”
  • “Is there a cross-cutting migration in flight now? How is it sequenced?”
  • “When two senior engineers disagree on architecture, how does it resolve?”
  • “What separates Staff from Senior here in practice, not on the ladder?”

The close

“Is there anything about my background you’re unsure about?”

Slightly uncomfortable, and it can surface a misunderstanding while you can still fix it.

One page to revise from

The thesis

Isolation is a platform capability, not a product feature. 178 teams — per-product isolation never converges.

The planes

Control plane provisions and manages, shared, off the request path. Data plane serves traffic, dedicated per customer.

The path

Client → Global Edge → Router → Tenant Context → Shard Manager → shard → replicas → data → Egress Gateway.

The decision

Router answers commercial-or-isolated. Shard Manager answers which shard. Identity is static and cacheable; placement is operational and moves.

Shards

A shard is a logical isolated runtime for one tenant and product, holding replicas. Replica failure ≠ shard replacement.

Config

Service descriptor describes the service. Shard descriptor describes one tenant’s runtime of it. That kept adoption cheap.

Migration

L0 identity and edge, L1 shared platform, L2 products, L3 the tail. Ordered by dependency, priority, traffic, risk, readiness.

Do not say

Shard = instance. Cache = source of truth. Kubernetes. A named policy engine. Any number you cannot evidence.

Three sentences to have automatic

  1. The thesis. “Isolation is a platform capability, not a product feature.”
  2. The decision. “Tenant context is static and cacheable. Shard placement is dynamic and operational. Coupling them would make every placement change touch tenant identity.”
  3. The scale. “About 178 teams, phased by dependency, priority, traffic, risk and readiness. I had authority over none of them.”

Architecture, judgement, scope. Almost every question is a drill-down from one of those.
