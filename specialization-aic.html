Part 1

The system

1

What Isolated Cloud is

Atlassian Cloud is multi-tenant. That works for almost everyone.

Some enterprises cannot use it. Banks, critical infrastructure, regulated industries. Their rules say they may not share infrastructure. Logical isolation does not satisfy a rule that says dedicated.

Isolated Cloud gives those customers a dedicated environment, run by Atlassian.

What they getDetail
Dedicated infrastructureTheir own AWS accounts, VPC, networking, compute, storage, databases
Their own keysCustomer-managed encryption keys, held in the customer’s own AWS account
Egress blocked by defaultData does not leave unless a policy allows it
Their own domainDedicated edge and domain, not the shared one
Not their own control planeProvisioning, deployment and operations stay shared. This is the whole design.

The last row matters most. Atlassian did not build a separate copy of itself per customer. That would mean running hundreds of Atlassians. The data plane is dedicated. The control plane is shared.

🎯 Say this in one breath

“Isolated Cloud is Atlassian Cloud deployed one customer at a time. Dedicated infrastructure, dedicated keys, no egress by default. But the control plane stays shared, because duplicating it per customer does not scale. All the hard engineering is at that boundary.”

Part 2

What you built

3

The one idea

YOURS Atlassian had about 178 engineering teams. Every service assumed one deployment serves all tenants.

Isolated Cloud breaks that assumption. A tenant now needs its own deployment.

There were two ways to fix it.

OptionWhat happens
Each product fixes itself178 teams each build provisioning, placement and lifecycle. 178 different answers. It never converges, and product 179 starts from nothing.
The platform fixes it onceThe platform owns provisioning, routing, placement, lifecycle and egress. Teams adopt a configuration model. Future products get isolation for free.
🎯 The sentence everything comes from

Isolation is a platform capability, not a product feature.

Every component below exists because of that choice.

This is also why it was a Staff problem, not a Senior one. Pushing work into the platform is a normal engineering move. Getting 178 teams to accept an abstraction they did not design, when each has a fair case for being an exception, is the hard part.

4

Control plane and data plane

YOURS Two planes, with opposite characteristics.

Control planeCustomer data plane
JobProvisioning and lifecycleServing customer traffic
Shared?Shared across customersDedicated per customer
How oftenRarelyConstantly
On the request path?NoYes

The control plane creates AWS accounts, VPCs, databases, storage and keys. It configures deployment, monitoring and logging. It holds tenant metadata and manages the environment’s lifecycle.

Then it gets out of the way. It does not serve customer requests. Provisioning can take minutes and can fail. A request cannot.

5

The request path

Draw this first if someone asks how a request works.

Client | v GLOBAL EDGE handles the request, forwards to Router | v ROUTER is this tenant commercial or isolated? | caches tenant context in memory | miss -> Tenant Context Service v TENANT CONTEXT who is this tenant, which environment | +--- commercial ---> commercial runtime | +--- isolated -----> SHARD MANAGER | v which shard serves this tenant? ISOLATED SHARD | replica 1 / 2 / 3 | v DEDICATED DATA | v EGRESS GATEWAY policy check | v external systems

Two things people get wrong here.

The edge does not decide placement. It handles the request and passes it on.

The Router does not pick the shard. It only decides commercial or isolated. The next section explains why.

6

Why Router and Shard Manager are separate

YOURS This is your strongest answer. It is a decision with a reason, not a component description.

Two questions have to be answered at runtime:

ComponentAnswers
Router“Who is this tenant, and is it commercial or isolated?”
Shard Manager“Which shard serves this tenant right now?”

The obvious design puts both in the Router. One component, one lookup. We did not, because the two facts behave differently.

Tenant contextShard placement
ChangesRarelyOften
Changes whenA tenant moves environment or entitlementFailure, maintenance, deployment, migration, capacity
Cacheable?VeryOnly against a moving truth
NatureIdentityOperational

Putting both in the Router ties a stable thing to a volatile one. The Router sits on every request. It would have to track placement changes constantly.

Separating them means a shard can be replaced without anything about the tenant changing.

The cost

One more component to run. One more hop for isolated tenants. We took that trade.

The catch worth volunteering

The Router caches tenant context. When a tenant moves from commercial to isolated, that cache must be invalidated. Until it is, requests go to the wrong place.

That is a correctness problem, not a performance one. Say this before you are asked. It shows you thought about the transition, not just the end state.

7

Shards and replicas

⚠ Fix this before anything else
“A shard is a tenant’s instance of a service.”

YOURS A shard is a logical isolated deployment for one tenant and one product. It contains several replicas.

Shard is not replica. Shard is not a machine.

Also: people hear “shard” and think data partition. It is not that either. Say so early or the whole explanation drifts.

Tenant A | +-- Jira Shard-123 | +-- Replica 1 +-- Replica 2 +-- Replica 3 Traffic rises replicas scale AWS Auto Scaling the shard does not change A replica fails infrastructure replaces it the tenant -> shard mapping does not change A shard is replaced Tenant A -> Shard-123 becomes Shard-456 now placement is updated and the cache invalidated

That last distinction is what interviewers probe. Confusing replica failure with shard replacement is the clearest sign someone has only heard the architecture described.

Where placement truth lives

The shard configuration repository is the source of truth. A cache may sit in front of it for speed.

The cache is never the source of truth. If it is lost, you pay latency while it refills. You do not lose correctness.

Why not Kubernetes

Scaling uses AWS-native Auto Scaling. Isolation multiplies environments, so every extra moving part is multiplied too. Another orchestration layer would have been a second platform to operate inside every isolated environment, for a problem AWS already solved.

8

The shard descriptor

YOURS Each service used to have a service descriptor: CPU, memory, keys, database, scaling strategy.

That worked when there was one deployment. It breaks when every tenant needs their own.

So the model split. The service descriptor describes the service. A shard descriptor describes one tenant’s runtime of it.

ONE PRODUCT SERVICE | +-- Shard A -> Tenant A config +-- Shard B -> Tenant B config +-- Shard C -> Tenant C config compute, memory, networking, storage, keys, monitoring

Now one tenant can be sized for their traffic without touching the service definition or any other tenant.

This is what made adoption cheap. Teams did not rewrite business logic. They adopted a configuration model. That is the link between the technical design and 178 teams actually finishing.

Expect: “You just multiplied your config surface by the number of tenants.”

Fair. The service level still holds what is common; a shard descriptor holds what is specific, and it lives in the repository rather than in 178 hand-edited places.

Concede the real risk: per-shard settings are easy to add and nobody removes them. Over time you get tenants on bespoke config whose reason is forgotten.

9

The Egress Gateway

YOURS Outbound data goes through one place, where policy is checked.

PRODUCT -> EGRESS GATEWAY -> POLICY CHECK -> external system

Why centralise it: outbound data control is a cross-cutting compliance concern.

If 178 teams each write their own policy, the guarantee is only as strong as the weakest one. And a policy that is too permissive produces no error. You find out at an audit.

Do not name a policy engine you have not verified. Say “policy-driven enforcement”.

10

Migrating 178 teams

YOURS Phased, not all at once. Grouped by dependency, criticality and priority.

TierWhatExamples
L0Foundation. Migrate first.Identity, Global Edge
L1Near the edge, shared platformShared gateway services, observability
L2Products the first enterprise tenants needJira, Jira Service Management, Confluence, Trello
L3The tail. Lower priority, less traffic.Everything else

Nothing migrates before what it depends on. That is why identity and the edge are L0.

YOURS You also inserted an L2.5 for services that fit neither L2 nor L3. A fractional tier refines the order without renumbering 178 services, which would have broken every dashboard and runbook keyed to the old values.

What the ordering considered

Dependency graph, business priority, traffic, risk, operational readiness.

Only the first is a hard constraint. A pure dependency sort gives a valid order and an unworkable plan, because it ignores whether the team at position 40 has capacity this quarter.

🎯 The Staff point

This was an organisational strategy, not a technical one. Say that.

You had no authority over any of those teams. Adoption came from keeping the integration cost low enough that teams chose it.

The interview

11

What a retrospective is

Not a system design round. They are not testing whether you can design something. They are testing whether you owned something.

System designRetrospective
Tense“I would…”“We did, and here is why”
WantsOptionsDecisions and their consequences
Last question“How would you scale it?”“What would you change today?”

The hour: a short intro, about 40 minutes on one project, about 15 minutes of your questions.

Forty minutes on one project means they go deep, not wide. Expect five to seven levels on a single thread.

⚠ The failure mode
Drifting into design mode. “You could also do X, and another option would be Y…”

The moment you list options in the abstract, you sound like someone describing a system they read about.

Alternatives belong in the answer, but in past tense with a verdict. “We considered putting it in the Router. We rejected it because…”

12

Your story

Ninety seconds

“Atlassian’s cloud is multi-tenant. Regulated enterprises need stronger isolation, and their rules don’t accept shared infrastructure. So we built Isolated Cloud — dedicated environments per customer.

The obvious way is for every product to redesign itself for isolation. We had about 178 teams, so that doesn’t finish.

The position we took was that isolation is a platform capability, not a product feature. The platform owns provisioning, routing, placement, lifecycle and egress. Teams adopt a configuration model instead of rewriting business logic.

At runtime, a request goes edge to Router. The Router decides commercial or isolated. If isolated, the Shard Manager resolves which shard serves them. A shard is a logical isolated runtime for one tenant and product, with replicas underneath it.

The decision I’d highlight is separating tenant context from shard placement. Identity is static and caches well. Placement is operational and changes constantly. Keeping them apart means a shard can be replaced without anything about the tenant changing.”

The shape of a good answer

For your two or three big answers, walk this chain. For smaller questions, pick the three or four links that were actually asked about.

context → problem → constraint → options → decision → why → trade-off → execution → impact → lesson

Always include the constraint and the trade-off. Those two are what make it a retrospective instead of a description, and they are the two people skip.

1. Why I took this on

I was a principal engineer in platform engineering when Isolated Cloud got funded. The commercial reason was simple. We had large regulated customers, a lot of them banks and critical-infrastructure companies, who wanted to move to our cloud and couldn’t. Their compliance teams wouldn’t sign off on shared infrastructure, however good our logical isolation was.

About a month in, I sat through design reviews from three product teams in the same week. Jira was planning its own per-customer stack with its own routing. Confluence was planning something different. A third team hadn’t started and was waiting to copy whichever looked better. That was the moment for me. We weren’t building one Isolated Cloud. We were about to build five or six of them.

I wrote a one-page note to my VP that weekend. The ask was to pause product teams designing isolation on their own until we’d decided what belonged in the platform. My VP agreed and asked me to lead that design.

2. What the problem actually was

Once we counted, it was about 178 teams whose services would have to run in an isolated environment.

Every one of those services assumed one deployment serves every tenant. Tenancy was a field in a request or a column in a table, not a deployment. Isolated Cloud needs a runtime per customer.

So each service suddenly needed to know how it gets provisioned per tenant, how a request finds the right runtime, how it scales, how it’s replaced when it breaks, and what data it’s allowed to send out. Left to each team, that’s 178 answers.

The part that worried me most was egress. Our compliance story would only be as strong as the weakest team’s implementation, and a policy that’s too loose doesn’t throw an error. You find out in an audit, or from a customer.

3. How I came up with the approach

I made a list of everything a service does differently for an isolated tenant. Then I went through it with the Jira and Confluence tech leads and marked each item: is this product-specific, or the same for every service? Almost everything landed on the same-for-everyone side. Provisioning, identifying the tenant, finding the runtime, lifecycle, egress. What stayed with products was their business logic and how their own runtime should be sized.

That exercise gave me the principle I built everything on: isolation is a platform capability, not a product feature.

I wrote it up as an architecture proposal with both options side by side. I didn’t take it straight to review. I spent two weeks walking the biggest product leads through it one-on-one first, because if Jira and Confluence said no in the room, the proposal was dead.

The pushback was real, and it was fair. They worried about losing control of their deployments and waiting on a platform team’s backlog whenever they needed something. The Jira lead put it bluntly: they weren’t handing their pager to someone else’s roadmap. Two things got us through. Product teams kept their business logic and sized their own shards through shard descriptors. And we committed to a written platform contract: what the platform guarantees, what it doesn’t, and how teams ask for changes. Once the big two were on board, the architecture review with engineering leadership was short.

4. The trade-offs we accepted

The biggest was centralisation, and I said so plainly in the review. Teams were giving up some control over deployment configuration, and every product would depend on the platform.

If we got the platform wrong, we’d get it wrong for everyone at once. That’s why the contract and staged rollouts of platform changes mattered so much to me.

Second, the complexity moved rather than disappeared. We now had to build and run the Router changes, the Tenant Context Service, the Shard Manager, the shard configuration repository and the Egress Gateway.

Third, cost. A dedicated runtime per customer costs more than a shared one. That was the requirement, so we couldn’t avoid it, but shard descriptors meant each shard was sized for its own tenant’s traffic instead of everyone being provisioned like the largest customer.

We also looked at adding a separate orchestration layer for shards and dropped it. Isolation multiplies environments, so every extra moving part multiplies with it. AWS-native infrastructure and Auto Scaling already handled replica scaling.

What we got back was one implementation, one egress policy, and isolation that any new product inherits without redesigning anything.

5. How we planned it

I didn’t plan 178 migrations. I planned dependencies.

I worked with a program manager, the identity and edge leads, and our SRE lead. We started from the service catalogue, and it was wrong for more services than I expected. Dependencies had changed and nobody had updated them. So we sent every team a short form: what do you call, what calls you, and do you send data outside Atlassian. That form ended up being the most useful thing we produced in planning.

From it we built the dependency map and the tiers. Planning took about a quarter. After that, the program manager and I reviewed the order with leadership every two weeks. Customer commitments moved, and when they did, the order had to move with them.

6. The phasing rules

I classified services into four tiers. L0 was the foundation that had to move first: identity and the Global Edge. L1 was services close to the edge and shared platform services, like shared gateways and observability. L2 was the major products our first enterprise customers needed: Jira, Jira Service Management, Confluence and Trello. L3 was the long tail: lower priority and a smaller share of traffic.

The rules were simple. A service can’t move before the things it depends on. Among services that can move, the ones our first customers need go first. Traffic and risk decide how carefully a service moves. And teams that aren’t ready move later on purpose.

L2.5 came out of planning, not the original design. When we sorted services, one group didn’t fit. They weren’t products the first customers needed, so not L2. But several L2 products called them on common paths, so they couldn’t wait in the L3 tail either.

Rather than renumber everything, which would have broken the dashboards, alerts and runbooks already keyed to the tiers, we added L2.5 between them.

7. How I built the onboarding tool

The tool came from watching the first few teams. Most of their time wasn’t going into hard problems. It went into the same setup work, done slightly differently each time, and slightly wrong in a different way each time.

So the tool took that work off them. At 178 teams, every manual step becomes 178 different results.

It worked in five steps. It checked readiness: were the service’s dependencies already migrated, and had the team declared every external destination it sends data to? It generated a starting shard descriptor from the service’s existing service descriptor, so teams reviewed a file instead of writing one. It ran the data transfer. It validated the result. And it reported status to a shared dashboard.

Every transfer it made was encrypted, so no team had to get that right on its own.

Teams ran it as a step in their existing deployment pipeline. The first version didn’t have the egress check. We added it after the third team got blocked at the gateway halfway through testing. The early teams took a few weeks, with someone from my team working alongside them. By the later waves, most teams got through in a few days on their own.

8. How the architecture works

There are two planes. The control plane is shared. It onboards tenants and provisions their environment: AWS accounts, VPC, databases, storage, keys, plus monitoring and logging configuration. It isn’t on the request path. The customer data plane is dedicated, and it serves traffic.

A request arrives at the Global Edge, which passes it to the Router. The Router answers one question: is this tenant commercial or isolated? It keeps tenant context in an in-memory cache, and on a miss it asks the Tenant Context Service.

If the tenant is isolated, the Shard Manager answers the second question: which shard serves this tenant right now? A shard is a logical isolated runtime for one tenant and one product, with several replicas that scale with AWS Auto Scaling. Placement lives in the shard configuration repository, which is the source of truth, with a cache in front for speed.

Each shard has a shard descriptor for its own compute, memory, networking, storage, keys and monitoring. Anything going out passes through the Egress Gateway, where policy is checked.

9. Hiccups in the architecture, and how we improved it

The first version of the design had the Router resolving the shard directly. It was simpler, and honestly I favoured it at first. What changed my mind was listing every event that changes placement: a shard failing, maintenance, a deployment, a migration, a capacity change. Not one of them changes who the tenant is.

Putting placement in the Router meant the component on every request would be chasing operational changes all day. So placement moved into the Shard Manager, and the Router only answers commercial or isolated.

The second was stale tenant context, and we found it in rehearsal. We switched a test tenant from commercial to isolated and watched requests keep landing on the commercial runtime for a few minutes. Some Router instances were still serving from their cache. No customer was affected, but it changed the design: cache invalidation became an explicit step in the switch, not something we left to expire.

The third was egress declarations. Teams found out late that their services sent data to places they’d never written down, and the gateway blocked them mid-testing. The gateway was doing its job, but it cost those teams days. That’s what put the egress check into the onboarding tool.

The fourth was shard descriptor drift. About two months into the migrations I pulled a report of every override in the shard descriptors. A lot had been added during an incident or a load test and never removed, and nobody could say why they were there. From then on every override needed an owner and a reason, and the report became a monthly review.

10. How we built observability

Monitoring and logging configuration was provisioned per isolated environment by the control plane, like everything else. The Shard Manager tracked each shard’s health and state, and that’s what drove failover and replacement.

We watched four things. Shard health. Latency and error rates per tenant and per product, not just per service, because a problem for one isolated customer disappears into a service-wide average. Migration progress per team. And egress denials.

Egress denials were the surprise. I expected a compliance metric. It became our best early warning. When a service started trying to send data somewhere it hadn’t declared, the denial count moved before anything else did.

Our own telemetry was outbound data too, so it went through the Egress Gateway like everything else.

That forced a conversation with a lot of teams about what their logs actually contained.

11. How we did the data migration

It was phased by tier, never all at once, and every transfer was encrypted.

For each tenant the order never changed: provision and register the isolated shard, move the data, switch tenant context from commercial to isolated, and make sure the Router cache reflects it. Until it does, requests can still reach the commercial runtime, so we treated that as a correctness risk, not a performance detail.

The data moved in three stages. A bulk copy while the source stayed live. Incremental catch-up runs, each smaller than the last. Then a short write freeze to copy the final changes. We didn’t switch traffic until record counts and checksums matched.

Rollback was the thing we argued about longest. Before the switch it’s free: the tenant just stays commercial. After customers write data in the isolated environment, rolling back loses that data. So we agreed a short rollback window with each customer before cutover, and after it we fixed forward. Having that conversation up front, not during an incident, was the whole point.

12. Phase one

Phase one was L0, L1, and the L2 products our first customers needed. We started with a pilot customer, a large bank. We rehearsed their cutover twice in staging before touching production, and the stale tenant context problem showed up in the first rehearsal. That’s exactly what rehearsals are for.

Before we opened phase two we’d changed three things: cache invalidation was an explicit step in the switch, egress declarations were part of the readiness check, and every team’s status was on the shared dashboard.

13. Phase two

Phase two was L2.5 and the L3 tail. More teams, smaller services, less traffic each. I assumed it would be faster. It wasn’t. It took about as long as phase one.

Phase one was an engineering problem. Phase two was an adoption problem. Teams had other priorities, and some services had no real owner left after reorganisations. We found a few of those only because the readiness check failed on a dependency nobody claimed.

What moved the tail was unglamorous. Weekly office hours. Publishing every team’s status to leadership so priorities were visible. Chasing owners for orphaned services. And fixing common blockers once in the platform instead of team by team.

14. How adoption worked

I had no authority over any of those teams, so mandates weren’t an option. The pitch was always cost: adopt a shard descriptor and run the tool, and you don’t build placement, lifecycle or egress rules yourself.

The team I remember most pushed back hard. They had years of custom deployment scripts and didn’t want to touch them. I assumed at first it was resistance to change. When I sat down with their tech lead, it wasn’t. Their service scaled on a pattern the shard descriptor genuinely couldn’t express. We added it to the model. They migrated, and four or five teams after them used the same addition.

That’s when I stopped treating blockers as team problems. If two teams hit the same thing, it went on the platform backlog.

We tracked adoption with status the tool computed from its own checks, not status teams reported. Self-reported status was always greener than reality.

15. Production issues, and how we fixed them

The worst one was during an early production cutover. Cache invalidation was already a step in the switch after the rehearsal. But a few Router instances didn’t receive the invalidation, and for about ten minutes a small share of that customer’s requests went to the commercial runtime. Users saw errors. We caught it from the per-tenant error rate before the customer raised it, and forced a refresh.

The lasting fix was that a switch isn’t complete until every Router instance confirms it has the new context. If any Router reports the old one, the cutover doesn’t finish.

The second came from a shard replacement during maintenance. We updated placement and invalidated the cache, but in the wrong order. The cache refilled with the old placement before the repository update landed, so some requests went to a shard we were retiring. We fixed the order: update the shard configuration repository first, then invalidate the cache, then route new traffic. And we added an alert for any request that reaches a retired shard.

Neither fix was ’be more careful’. Both changed the process so it couldn’t happen that way again.

16. What I’d do differently

Two things. I’d design cache invalidation in from day one. Both production issues and the rehearsal problem came from the same place, and we hardened it in three rounds instead of one.

And I’d publish the platform contract and the shard descriptor model before phase one, not during it. We spent weeks negotiating things with teams that a written contract would have settled in an afternoon.

Architecture decisions

7“Why split the control plane from the data plane?”Answer

They do different jobs. The control plane provisions environments: AWS accounts, VPC, databases, storage, keys. That’s rare, slow and can fail.

The data plane serves requests constantly and is latency-sensitive. So the control plane is shared and stays off the request path. Once a tenant is provisioned, its metadata reaches the runtime through tenant context, so no request ever waits on provisioning.

Next they ask: “What happens to customers if the control plane is down?”

Avoid: Forgetting how provisioned state reaches the runtime.
8“Why a separate Shard Manager? Why not resolve the shard in the Router?”Answer

The first version did it in the Router, and I favoured that at first. It was simpler.

What changed my mind was listing every event that changes placement: a shard failing, maintenance, deployments, migrations, capacity changes. None of them change who the tenant is. Tenant context rarely changes and caches well; placement changes constantly. So placement moved to the Shard Manager. The cost was one more component and one more hop.

Next they ask: “What happens when a shard fails?”

Avoid: Saying separation of concerns and stopping there.
9“What exactly is a shard?”Answer

A logical isolated deployment for one tenant and one product, like one customer’s Jira. It has several replicas behind it.

It’s not a machine and not a data partition. When traffic rises, replicas scale. The shard stays the same.

Next they ask: “What happens when one replica fails?”

Avoid: Calling a shard an instance.
10“Why is tenant context cached in the Router?”Answer

The Router is on every request, so calling the Tenant Context Service each time would slow everything. Tenant context rarely changes, so caching is safe. On a miss the Router calls the service.

The catch is invalidation when a tenant switches. We learned that in rehearsal, and again in production.

Next they ask: “What happened in production?”

Avoid: Not mentioning invalidation.
11“Why split the service descriptor into shard descriptors?”Answer

The service descriptor assumed one runtime. With a runtime per tenant, each shard needs its own compute, memory, keys and monitoring. Teams got a generated starting shard descriptor and reviewed it instead of rewriting code.

The downside was drift. Overrides got added in incidents and never removed. We made every override need an owner and a reason, and reviewed the report monthly.

Next they ask: “How did you notice the drift?”

Avoid: Treating it as a config-format change. It’s what made adoption cheap.
12“Why centralise egress in a gateway?”Answer

One policy instead of 178. With per-team policies, compliance is only as strong as the weakest one, and a loose policy fails silently.

It also became our best early warning. A spike in egress denials meant a service was sending data somewhere it hadn’t declared.

Next they ask: “Isn’t the gateway a single point of failure?”

Avoid: Naming a specific policy engine. Say policy-driven enforcement.
13“Why AWS-native scaling instead of adding an orchestration layer?”Answer

We looked at it and dropped it. Isolation multiplies environments, so every extra moving part multiplies too. AWS-native infrastructure and Auto Scaling already handled replica scaling inside a shard.

Next they ask: “What do you lose without an orchestrator?”

Avoid: Sounding like you never considered it.
14“What was your single most important architectural decision?”Answer

Treating isolation as a platform capability, not a product feature. Everything else came from that: the control plane, the Router, tenant context, the Shard Manager, shard descriptors, the Egress Gateway.

The second was separating tenant identity from runtime placement.

Next they ask: “What would have happened if you’d gone the other way?”

Avoid: Naming a component instead of the decision.

Trade-offs

15“What was the biggest trade-off?”Answer

Centralisation. Teams gave up some control over deployment config, and every product came to depend on the platform. If we got it wrong, we got it wrong for everyone.

We managed that with the written contract and by rolling platform changes out tenant by tenant, never everywhere at once.

Next they ask: “Did a platform change ever hurt several teams at once?”

Avoid: Saying there was no downside.
16“Where did you trade latency against correctness?”Answer

The Router caches tenant context for speed, which is only safe because it rarely changes and we invalidate on every switch.

For placement, the shard configuration repository is the source of truth and the cache only speeds up lookups. Getting the order wrong there caused one of our production issues.

Next they ask: “What was that issue?”

Avoid: Treating a cache as the source of truth.
17“Dedicated shards cost more. How did you justify that?”Answer

Dedicated infrastructure was the requirement. Without it these customers couldn’t use our cloud at all.

We limited the waste by sizing new tenants from their existing commercial usage, then adjusting shard descriptors after a few weeks of real traffic.

Next they ask: “How often did you resize?”

Avoid: Arguing cost only in general terms.
18“What did it cost to avoid asking teams to rewrite code?”Answer

The complexity moved to my side. We built and ran the Router changes, the Tenant Context Service, the Shard Manager, the configuration repository and the Egress Gateway.

One platform team carrying that was far cheaper than 178 teams each carrying part of it.

Next they ask: “Was the platform team sized for it?”

Avoid: Implying the complexity went away.

Data migration

19“Walk me through how data migration worked.”Answer

Per tenant, the order never changed: provision and register the shard, move the data, switch tenant context to isolated, confirm every Router has the new context.

The data moved in three stages: a bulk copy while the source stayed live, incremental catch-up runs, then a short write freeze for the final changes. Every transfer was encrypted, and we didn’t switch traffic until counts and checksums matched.

Next they ask: “How did you avoid losing or duplicating data?”

Avoid: Describing only the copy and skipping the switch.
20“How did you make sure no data was lost or duplicated?”Answer

Counts and checksums had to match before the switch. Each stage was safe to rerun, so a failed catch-up run was simply repeated.

The write freeze meant nothing changed underneath us at the moment of cutover.

Next they ask: “What did you do when checksums didn’t match?”

Avoid: Claiming exactly-once delivery.
21“What did the migration tool actually do for teams?”Answer

Five steps: a readiness check on dependencies and declared egress destinations, a generated starting shard descriptor, the encrypted data transfer, validation, and status to a shared dashboard.

Teams ran it as a step in their existing deployment pipeline.

Next they ask: “What did teams still have to do themselves?”

Avoid: Describing the tool without what it saved teams.
22“How did you onboard teams?”Answer

The first teams had someone from my team working alongside them, and that’s how we learned what the tool was missing. The egress check was added after the third team got blocked at the gateway mid-testing.

Onboarding went from a few weeks with our help to a few days on their own by the later waves. Weekly office hours covered the rest.

Next they ask: “What did the early teams teach you?”

Avoid: Only mentioning documentation.
23“How did you switch a tenant without breaking requests?”Answer

Shard first, then data, then tenant context, then confirmation that every Router had the new context.

That last step exists because of a production cutover where a few Routers missed the invalidation and some requests hit the commercial runtime for about ten minutes.

Next they ask: “How did you detect that?”

Avoid: Leaving out the Router cache.
24“Why was every transfer encrypted, and why centrally?”Answer

These are regulated customers. Encrypting in the tool made it a platform guarantee instead of 178 separate promises, one of which someone would eventually get wrong.

Next they ask: “Who managed the keys?”

Avoid: Treating encryption as a checkbox.
25“What was your rollback plan?”Answer

Before the switch, rollback was free: the tenant stayed commercial. After customers wrote data in the isolated environment, rolling back would lose it.

So we agreed a short rollback window with each customer before cutover, and fixed forward after it.

Next they ask: “Did you ever roll back?”

Avoid: Saying you could always roll back.
26“How did you know a migration was really complete?”Answer

The tool computed status from its own checks. We didn’t use self-reported status, because it was always greener than reality.

Next they ask: “What was the most common reason a team wasn’t really done?”

Avoid: Trusting status updates.

Execution across teams

27“Why were identity and the Global Edge in L0?”Answer

Nothing isolated works without them. No tenant can log in or reach a service. Everything else waits on L0.

Next they ask: “What did L1 depend on?”

Avoid: Only saying they were important.
28“Why did you add an L2.5 tier?”Answer

It came out of planning. One group wasn’t a product the first customers needed, so not L2, but several L2 products called them on common paths, so they couldn’t wait with L3.

A half tier avoided renumbering, which would have broken dashboards, alerts and runbooks keyed to the tiers.

Next they ask: “Isn’t a half tier a sign the model was wrong?”

Avoid: Getting defensive about it.
29“A team said they had no capacity. What did you do?”Answer

Moved them later in their tier on purpose, and checked nothing depended on them first. When something did, it became a priority conversation with leadership, with the dependency map in front of everyone.

Next they ask: “What if they simply refused?”

Avoid: Escalating first.
30“Where did the migration stall?”Answer

Phase two. More teams, smaller services, and I expected it to be faster. It took about as long as phase one.

Teams had other priorities and some services had no owner left after reorganisations. Office hours, visible status for leadership, and chasing owners moved it.

Next they ask: “What would you do differently for the tail?”

Avoid: Claiming it went smoothly.

Conflict and disagreement

31“Tell me about a disagreement.”Answer

The biggest was with the product leads over the platform approach. The Jira lead said they weren’t handing their pager to someone else’s roadmap.

It was a fair concern. We kept business logic and shard sizing with product teams and wrote a platform contract. It took two weeks of one-on-ones before review.

Next they ask: “Did you have to give anything up to win them over?”

Avoid: Making the other side look unreasonable.
32“How did you convince people the extra Shard Manager was worth it?”Answer

I’d favoured the Router approach myself at first, so I used the same thing that changed my mind: the list of events that change placement. None of them change the tenant.

Once that list was on the table, coupling placement to the Router was obviously the wrong call.

Next they ask: “Who still disagreed?”

Avoid: Arguing from principle instead of the event list.
33“A team wanted to keep their own deployment approach. What did you do?”Answer

A team with years of custom deployment scripts pushed back hard. I assumed resistance to change. It wasn’t: their scaling pattern genuinely couldn’t be expressed in a shard descriptor.

We added it to the model. They migrated, and four or five teams used the same addition afterwards.

Next they ask: “Did you ever make an exception outside the model?”

Avoid: Saying you never bend.
34“Were you ever overruled?”Answer

Yes. After the rehearsal I wanted to delay phase one until we could confirm invalidation on every Router. Leadership held the date because of the pilot commitment.

I committed, we shipped invalidation as a step in the switch, and the confirmation step came after the first production incident. In hindsight we were both partly right.

Next they ask: “Would you push harder next time?”

Avoid: Telling it as a grievance.

Operations and failures

35“A replica fails. Then a whole shard fails. What’s different?”Answer

A replica failing is handled by the infrastructure, and the tenant-to-shard mapping doesn’t change.

A shard being replaced means placement changes. We update the shard configuration repository first, then invalidate the cache, then route new traffic. We learned that order the hard way.

Next they ask: “What happened when you got the order wrong?”

Avoid: Treating them as the same event.
36“The placement cache is lost. What happens?”Answer

Nothing is lost. The repository is the source of truth. Lookups are slower until the cache refills, but still correct.

Next they ask: “What if the repository is down?”

Avoid: Saying placement lives in the cache.
37“Tell me about a production incident.”Answer

During an early production cutover, a few Router instances missed the tenant context invalidation. For about ten minutes some of that customer’s requests went to the commercial runtime, and users saw errors.

We caught it from per-tenant error rates before the customer raised it and forced a refresh. The lasting fix: a switch isn’t complete until every Router confirms the new context.

Next they ask: “Why hadn’t the rehearsal caught that?”

Avoid: A fix that amounts to being more careful.
38“How did you monitor the system?”Answer

Four signals: shard health, latency and errors per tenant and product, migration progress per team, and egress denials.

Per tenant mattered because one isolated customer’s problem disappears in a service-wide average. Egress denials turned out to be the earliest warning we had.

Next they ask: “What did you add after going live?”

Avoid: Listing dashboards without saying what they caught.

Impact

39“What was the impact?”Answer

Isolation became a platform capability instead of 178 separate redesigns. Regulated customers who couldn’t use our cloud could move, starting with a large bank.

Onboarding a team went from a few weeks with our help to a few days on their own. And new products get isolation without redesigning anything.

Next they ask: “How did you measure that?”

Avoid: Only listing technical outcomes.
40“Why did this matter to the business?”Answer

These customers couldn’t be cloud customers at all without it. Their compliance teams wouldn’t sign off on shared infrastructure.

Next they ask: “How did that change engineering priorities?”

Avoid: Only talking about technology.
41“How did you measure success?”Answer

Three measures: teams fully migrated as computed by the tool, time for a team to onboard, and problems per cutover.

The slowest to move was teams migrated in phase two.

Next they ask: “Why was phase two slow?”

Avoid: Vague success claims.

Reflection

42“What would you do differently?”Answer

Design cache invalidation in from day one. The rehearsal problem and both production issues came from the same place, and we hardened it in three rounds instead of one.

And publish the platform contract before phase one. We spent weeks negotiating things a written contract would have settled.

Next they ask: “Why didn’t you do that at the time?”

Avoid: Saying nothing, or something cosmetic.
43“What’s the weakest part of the design today?”Answer

Centralisation makes the platform a shared dependency. And shard descriptor overrides still need discipline. The monthly review helps, but it depends on people doing it.

Next they ask: “What would it take to fix it?”

Avoid: Blaming things outside your control.
44“What did you learn about leading across teams?”Answer

Mandates don’t work at 178 teams. The moment it clicked was the team with custom scripts. What looked like resistance was a real gap in our model.

After that, if two teams hit the same thing, it was a platform problem, not a team problem.

Next they ask: “Where did that approach not work?”

Avoid: A generic lesson with no moment behind it.
45“If you joined a team here doing something similar, what would you tell them first?”Answer

Decide early what belongs to the platform and what belongs to the product. Moving that line later is far more expensive than drawing it at the start.

Next they ask: “How would you decide where that line goes?”

Avoid: Re-describing your project instead of giving advice.
15

Your fifteen minutes

A quarter of the interview. It is scored. Running dry after three questions is noticeable.

Lead with these

QuestionWhy
“How does a decision affecting several teams actually get made here?”Tells you whether a Staff engineer can be effective or is just advisory. Listen for a mechanism, not a person.
“What is the most recent architectural decision this team got wrong, and how did you find out?”Tests whether there is a real feedback loop, and whether it is safe to be wrong.
“What would you want someone in this role to have changed a year in?”Gets the real expectation, not the job description.

Then, as the conversation allows

  • “Where does the line sit between what the platform owns and what product teams own?”
  • “What architectural decision made years ago do you still work around?”
  • “What does on-call look like — pages per shift, honestly?”
  • “Is there a cross-cutting migration in flight now? How is it sequenced?”
  • “When two senior engineers disagree on architecture, how does it resolve?”
  • “What separates Staff from Senior here in practice, not on the ladder?”

The close

“Is there anything about my background you’re unsure about?”

Slightly uncomfortable, and it can surface a misunderstanding while you can still fix it.

One page to revise from

The thesis

Isolation is a platform capability, not a product feature. 178 teams — per-product isolation never converges.

The planes

Control plane provisions and manages, shared, off the request path. Data plane serves traffic, dedicated per customer.

The path

Client → Global Edge → Router → Tenant Context → Shard Manager → shard → replicas → data → Egress Gateway.

The decision

Router answers commercial-or-isolated. Shard Manager answers which shard. Identity is static and cacheable; placement is operational and moves.

Shards

A shard is a logical isolated runtime for one tenant and product, holding replicas. Replica failure ≠ shard replacement.

Config

Service descriptor describes the service. Shard descriptor describes one tenant’s runtime of it. That kept adoption cheap.

Migration

L0 identity and edge, L1 shared platform, L2 products, L3 the tail. Ordered by dependency, priority, traffic, risk, readiness.

Do not say

Shard = instance. Cache = source of truth. Kubernetes. A named policy engine. Numbers that don’t match across your answers.

Three sentences to have automatic

  1. The thesis. “Isolation is a platform capability, not a product feature.”
  2. The decision. “Tenant context is static and cacheable. Shard placement is dynamic and operational. Coupling them would make every placement change touch tenant identity.”
  3. The scale. “About 178 teams, phased by dependency, priority, traffic, risk and readiness. I had authority over none of them.”

Architecture, judgement, scope. Almost every question is a drill-down from one of those.
