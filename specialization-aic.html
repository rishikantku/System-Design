Part 1

The system

1

What Isolated Cloud is

Atlassian Cloud is multi-tenant. That works for almost everyone.

Some enterprises cannot use it. Banks, critical infrastructure, regulated industries. Their rules say they may not share infrastructure. Logical isolation does not satisfy a rule that says dedicated.

Isolated Cloud gives those customers a dedicated environment, run by Atlassian.

What they getDetail
Dedicated infrastructureTheir own AWS accounts, VPC, networking, compute, storage, databases
Their own keysCustomer-managed encryption keys, held in the customer’s own AWS account
Egress blocked by defaultData does not leave unless a policy allows it
Their own domainDedicated edge and domain, not the shared one
Not their own control planeProvisioning, deployment and operations stay shared. This is the whole design.

The last row matters most. Atlassian did not build a separate copy of itself per customer. That would mean running hundreds of Atlassians. The data plane is dedicated. The control plane is shared.

🎯 Say this in one breath

“Isolated Cloud is Atlassian Cloud deployed one customer at a time. Dedicated infrastructure, dedicated keys, no egress by default. But the control plane stays shared, because duplicating it per customer does not scale. All the hard engineering is at that boundary.”

Part 2

What you built

3

The one idea

YOURS Atlassian had about 178 engineering teams. Every service assumed one deployment serves all tenants.

Isolated Cloud breaks that assumption. A tenant now needs its own deployment.

There were two ways to fix it.

OptionWhat happens
Each product fixes itself178 teams each build provisioning, placement and lifecycle. 178 different answers. It never converges, and product 179 starts from nothing.
The platform fixes it onceThe platform owns provisioning, routing, placement, lifecycle and egress. Teams adopt a configuration model. Future products get isolation for free.
🎯 The sentence everything comes from

Isolation is a platform capability, not a product feature.

Every component below exists because of that choice.

This is also why it was a Staff problem, not a Senior one. Pushing work into the platform is a normal engineering move. Getting 178 teams to accept an abstraction they did not design, when each has a fair case for being an exception, is the hard part.

4

Control plane and data plane

YOURS Two planes, with opposite characteristics.

Control planeCustomer data plane
JobProvisioning and lifecycleServing customer traffic
Shared?Shared across customersDedicated per customer
How oftenRarelyConstantly
On the request path?NoYes

The control plane creates AWS accounts, VPCs, databases, storage and keys. It configures deployment, monitoring and logging. It holds tenant metadata and manages the environment’s lifecycle.

Then it gets out of the way. It does not serve customer requests. Provisioning can take minutes and can fail. A request cannot.

5

The request path

Draw this first if someone asks how a request works.

Client | v GLOBAL EDGE handles the request, forwards to Router | v ROUTER is this tenant commercial or isolated? | caches tenant context in memory | miss -> Tenant Context Service v TENANT CONTEXT who is this tenant, which environment | +--- commercial ---> commercial runtime | +--- isolated -----> SHARD MANAGER | v which shard serves this tenant? ISOLATED SHARD | replica 1 / 2 / 3 | v DEDICATED DATA | v EGRESS GATEWAY policy check | v external systems

Two things people get wrong here.

The edge does not decide placement. It handles the request and passes it on.

The Router does not pick the shard. It only decides commercial or isolated. The next section explains why.

6

Why Router and Shard Manager are separate

YOURS This is your strongest answer. It is a decision with a reason, not a component description.

Two questions have to be answered at runtime:

ComponentAnswers
Router“Who is this tenant, and is it commercial or isolated?”
Shard Manager“Which shard serves this tenant right now?”

The obvious design puts both in the Router. One component, one lookup. We did not, because the two facts behave differently.

Tenant contextShard placement
ChangesRarelyOften
Changes whenA tenant moves environment or entitlementFailure, maintenance, deployment, migration, capacity
Cacheable?VeryOnly against a moving truth
NatureIdentityOperational

Putting both in the Router ties a stable thing to a volatile one. The Router sits on every request. It would have to track placement changes constantly.

Separating them means a shard can be replaced without anything about the tenant changing.

The cost

One more component to run. One more hop for isolated tenants. We took that trade.

The catch worth volunteering

The Router caches tenant context. When a tenant moves from commercial to isolated, that cache must be invalidated. Until it is, requests go to the wrong place.

That is a correctness problem, not a performance one. Say this before you are asked. It shows you thought about the transition, not just the end state.

7

Shards and replicas

⚠ Fix this before anything else
“A shard is a tenant’s instance of a service.”

YOURS A shard is a logical isolated deployment for one tenant and one product. It contains several replicas.

Shard is not replica. Shard is not a machine.

Also: people hear “shard” and think data partition. It is not that either. Say so early or the whole explanation drifts.

Tenant A | +-- Jira Shard-123 | +-- Replica 1 +-- Replica 2 +-- Replica 3 Traffic rises replicas scale AWS Auto Scaling the shard does not change A replica fails infrastructure replaces it the tenant -> shard mapping does not change A shard is replaced Tenant A -> Shard-123 becomes Shard-456 now placement is updated and the cache invalidated

That last distinction is what interviewers probe. Confusing replica failure with shard replacement is the clearest sign someone has only heard the architecture described.

Where placement truth lives

The shard configuration repository is the source of truth. A cache may sit in front of it for speed.

The cache is never the source of truth. If it is lost, you pay latency while it refills. You do not lose correctness.

Why not Kubernetes

Scaling uses AWS-native Auto Scaling. Isolation multiplies environments, so every extra moving part is multiplied too. Another orchestration layer would have been a second platform to operate inside every isolated environment, for a problem AWS already solved.

8

The shard descriptor

YOURS Each service used to have a service descriptor: CPU, memory, keys, database, scaling strategy.

That worked when there was one deployment. It breaks when every tenant needs their own.

So the model split. The service descriptor describes the service. A shard descriptor describes one tenant’s runtime of it.

ONE PRODUCT SERVICE | +-- Shard A -> Tenant A config +-- Shard B -> Tenant B config +-- Shard C -> Tenant C config compute, memory, networking, storage, keys, monitoring

Now one tenant can be sized for their traffic without touching the service definition or any other tenant.

This is what made adoption cheap. Teams did not rewrite business logic. They adopted a configuration model. That is the link between the technical design and 178 teams actually finishing.

Expect: “You just multiplied your config surface by the number of tenants.”

Fair. The service level still holds what is common; a shard descriptor holds what is specific, and it lives in the repository rather than in 178 hand-edited places.

Concede the real risk: per-shard settings are easy to add and nobody removes them. Over time you get tenants on bespoke config whose reason is forgotten.

9

The Egress Gateway

YOURS Outbound data goes through one place, where policy is checked.

PRODUCT -> EGRESS GATEWAY -> POLICY CHECK -> external system

Why centralise it: outbound data control is a cross-cutting compliance concern.

If 178 teams each write their own policy, the guarantee is only as strong as the weakest one. And a policy that is too permissive produces no error. You find out at an audit.

Do not name a policy engine you have not verified. Say “policy-driven enforcement”.

10

Migrating 178 teams

YOURS Phased, not all at once. Grouped by dependency, criticality and priority.

TierWhatExamples
L0Foundation. Migrate first.Identity, Global Edge
L1Near the edge, shared platformShared gateway services, observability
L2Products the first enterprise tenants needJira, Jira Service Management, Confluence, Trello
L3The tail. Lower priority, less traffic.Everything else

Nothing migrates before what it depends on. That is why identity and the edge are L0.

YOURS You also inserted an L2.5 for services that fit neither L2 nor L3. A fractional tier refines the order without renumbering 178 services, which would have broken every dashboard and runbook keyed to the old values.

What the ordering considered

Dependency graph, business priority, traffic, risk, operational readiness.

Only the first is a hard constraint. A pure dependency sort gives a valid order and an unworkable plan, because it ignores whether the team at position 40 has capacity this quarter.

🎯 The Staff point

This was an organisational strategy, not a technical one. Say that.

You had no authority over any of those teams. Adoption came from keeping the integration cost low enough that teams chose it.

The interview

11

What a retrospective is

Not a system design round. They are not testing whether you can design something. They are testing whether you owned something.

System designRetrospective
Tense“I would…”“We did, and here is why”
WantsOptionsDecisions and their consequences
Last question“How would you scale it?”“What would you change today?”

The hour: a short intro, about 40 minutes on one project, about 15 minutes of your questions.

Forty minutes on one project means they go deep, not wide. Expect five to seven levels on a single thread.

⚠ The failure mode
Drifting into design mode. “You could also do X, and another option would be Y…”

The moment you list options in the abstract, you sound like someone describing a system they read about.

Alternatives belong in the answer, but in past tense with a verdict. “We considered putting it in the Router. We rejected it because…”

12

Your story

Ninety seconds

“Atlassian’s cloud is multi-tenant. Regulated enterprises need stronger isolation, and their rules don’t accept shared infrastructure. So we built Isolated Cloud — dedicated environments per customer.

The obvious way is for every product to redesign itself for isolation. We had about 178 teams, so that doesn’t finish.

The position we took was that isolation is a platform capability, not a product feature. The platform owns provisioning, routing, placement, lifecycle and egress. Teams adopt a configuration model instead of rewriting business logic.

At runtime, a request goes edge to Router. The Router decides commercial or isolated. If isolated, the Shard Manager resolves which shard serves them. A shard is a logical isolated runtime for one tenant and product, with replicas underneath it.

The decision I’d highlight is separating tenant context from shard placement. Identity is static and caches well. Placement is operational and changes constantly. Keeping them apart means a shard can be replaced without anything about the tenant changing.”

The shape of a good answer

For your two or three big answers, walk this chain. For smaller questions, pick the three or four links that were actually asked about.

context → problem → constraint → options → decision → why → trade-off → execution → impact → lesson

Always include the constraint and the trade-off. Those two are what make it a retrospective instead of a description, and they are the two people skip.

The full journey, as you would tell it

1. Why I took this on

Atlassian’s cloud is multi-tenant, and that works for most customers. But some of our largest enterprise customers are in regulated industries. Their rules don’t let them share infrastructure, so they couldn’t move to our cloud at all. Isolated Cloud was the answer: a dedicated environment per customer, still run by Atlassian.

Story I was a principal engineer in the platform organisation. Leadership had committed to Isolated Cloud for a first group of regulated enterprise customers. In the early design reviews I noticed something worrying: each product team was planning its own approach. Jira had one design, Confluence had another, and they didn’t match.

The hard part wasn’t setting up AWS accounts. It was that about 178 teams had services built on the assumption of multi-tenancy.

Story I raised this in the architecture forum. My point was that we were about to build the same thing many times, differently each time. Engineering leadership asked me to lead the cross-team platform design.

2. What the problem actually was

Every service assumed one deployment serves every tenant. Isolated Cloud needs a separate runtime per customer.

So every service would suddenly need provisioning, routing, placement, scaling, lifecycle management and outbound data rules for isolated tenants. If each team solved that alone, we’d get 178 different versions. They’d never behave the same, our compliance would only be as strong as the weakest one, and every new product would start from zero.

3. How I came up with the approach

The question I kept asking was: which parts of this are the same for every team? The answer was almost all of it. Provisioning, knowing what kind of tenant a request belongs to, finding the right runtime, managing its lifecycle, and controlling outbound data. None of that is product logic.

So the position I took was that isolation is a platform capability, not a product feature. The platform owns those concerns. Product teams keep their business logic and adopt a configuration model instead.

Story I wrote an architecture proposal that compared the two options side by side: every product builds its own isolation, or the platform provides it once. Before taking it to a formal review, I walked through it one-on-one with the tech leads of the biggest products. If Jira and Confluence agreed, the rest would follow.

Story The real pushback came from product leads. They worried about losing control of their deployments and being blocked on a platform team’s roadmap. That was a fair concern. We answered it in two ways: product teams kept their business logic and could tune their own shards through shard descriptors, and we committed to a written platform contract so they knew exactly what they could rely on. With that, engineering leadership approved the approach.

4. The trade-offs we accepted

We accepted three costs. First, centralisation. Teams gave up some control over their deployment configuration, and the platform became something every product depends on.

Second, the platform had more to run: the Router, the Tenant Context Service, the Shard Manager, the shard configuration repository and the Egress Gateway. The complexity didn’t disappear. It moved to one place.

Third, a dedicated runtime per tenant costs more than a shared one. We limited that by sizing each shard to its own traffic, not to the largest tenant.

We also chose AWS-native infrastructure and Auto Scaling rather than adding another orchestration layer, because isolation multiplies environments and every extra moving part gets multiplied with it.

In return we got one implementation instead of 178, consistent compliance, and isolation that future products inherit for free.

5. How we planned it

I didn’t plan 178 migrations. I planned by dependency. First I mapped which services depend on which. Then I grouped services into tiers, and ordered services inside each tier by business priority, traffic, risk and whether the team was ready.

Story I ran planning with a program manager, the identity and edge leads, and SRE. We built the dependency map from the service catalogue and by talking to teams, because the catalogue alone was out of date for some services. Planning took about a quarter. After that, we reviewed the plan with leadership every two weeks, so changes in customer commitments showed up in the order early rather than late.

6. The phasing rules

I classified services into four tiers. L0 was the foundation that had to move first: identity and the Global Edge. L1 was services close to the edge and shared platform services, like shared gateways and observability. L2 was the major products our first enterprise customers needed: Jira, Jira Service Management, Confluence and Trello. L3 was the long tail: lower priority and a smaller share of traffic.

The rules were simple. A service can’t move before the things it depends on. Among services that can move, the ones our first customers need go first. Traffic and risk decide how carefully a service moves. And teams that aren’t ready move later on purpose.

Some services didn’t fit cleanly in L2 or L3, so we added L2.5. A half tier let us refine the order without renumbering everything, which would have broken the dashboards, alerts and runbooks keyed to the existing tiers.

7. How I built the onboarding tool

The point of the tool was to take work off the teams. At 178 teams, every manual step turns into 178 different results, and some teams stall.

Every data transfer it made was encrypted, so no team had to get that right on its own. And it helped teams adopt the shard descriptor model instead of rewriting code.

Story It worked in five steps. First, a readiness check: are this service’s dependencies already migrated, and has it declared every external destination it sends data to? Second, it generated a starting shard descriptor from the service’s existing service descriptor, so the team reviewed a file instead of writing one. Third, it ran the encrypted data transfer. Fourth, it validated the result. Fifth, it reported status to a shared dashboard.

Story Teams ran it as a step in their existing deployment pipeline. The first teams took a few weeks, with my team working alongside them. By the later waves, most teams could do it themselves in a few days.

8. How the architecture works

There are two planes. The control plane is shared. It onboards tenants and provisions their environment: AWS accounts, VPC, databases, storage, keys, plus monitoring and logging configuration. It isn’t on the request path. The customer data plane is dedicated, and it serves traffic.

A request arrives at the Global Edge, which passes it to the Router. The Router answers one question: is this tenant commercial or isolated? It keeps tenant context in an in-memory cache, and on a miss it asks the Tenant Context Service.

If the tenant is isolated, the Shard Manager answers the second question: which shard serves this tenant right now? A shard is a logical isolated runtime for one tenant and one product, with several replicas that scale using AWS Auto Scaling. Placement lives in the shard configuration repository, which is the source of truth, with a cache in front for speed.

Each shard has a shard descriptor for its own compute, memory, networking, storage, keys and monitoring. And any data going out passes through the Egress Gateway, where policy is checked.

9. Hiccups in the architecture, and how we improved it

Early on we considered having the Router resolve the shard directly. It was simpler: one component, one lookup. We moved placement into a separate Shard Manager, because placement changes for operational reasons, like failures, maintenance, deployments and migrations, that have nothing to do with who the tenant is. Keeping them together would have tied something stable to something that changes all the time.

Story The second hiccup was stale tenant context. In our pilot rehearsal, we switched a test tenant from commercial to isolated, and some Router instances kept using their cached context for a few minutes. Requests went to the wrong runtime. It was caught in rehearsal, not with a customer, but it changed the design: cache invalidation became part of the tenant switch itself, and a switch wasn’t considered done until every Router saw the new context.

Story The third was egress. Several teams declared their external destinations late, so in testing their services were blocked at the Egress Gateway. The gateway was doing its job, but it cost those teams days. We added egress declarations to the onboarding tool’s readiness check, so teams found out before migrating, not after.

Story The fourth was descriptor drift. Teams added per-shard overrides and rarely removed them. We added a report comparing each shard descriptor to the defaults, and every override needed an owner and a reason.

10. How we built observability

Monitoring and logging configuration was provisioned per isolated environment by the control plane, like everything else. The Shard Manager tracked each shard’s health and state, and that’s what drove failover and replacement.

The part that’s different from normal cloud: logs and telemetry leaving the environment are outbound data. They go through the Egress Gateway and its policy like anything else, so what they contain matters.

Story We watched four things: shard health, latency and error rates per tenant and product, migration progress per team, and egress denials. Egress denials turned out to be the best early warning we had. A spike meant a service was trying to send data somewhere it hadn’t declared, usually before anything else looked wrong.

11. How we did the data migration

It was phased by tier, never all at once, and every transfer was encrypted.

For each tenant, the isolated shard had to be provisioned and registered first. The switch itself was a change in tenant context from commercial to isolated. The Router’s cache then had to be refreshed. Until it was, requests could still go to the commercial runtime, so we treated that as a correctness risk, not just a speed issue.

Story The data moved in three stages. A bulk copy first, while the source stayed live. Then incremental catch-up runs, each one smaller than the last. Then a short write freeze to copy the final changes. We validated before switching traffic by comparing record counts and checksums.

Story Rollback was cheap before the switch, because we could simply leave the tenant as commercial. Once customers wrote data in the isolated environment, rolling back would lose that data. So we agreed a short rollback window with each customer in advance, and after it we fixed forward.

12. Phase one

Story Phase one was the foundation and the first customers: L0 identity and Global Edge, L1 shared platform and observability, and the L2 products our first enterprise tenants needed.

Story We started with a pilot customer. The stale tenant context issue came up in the rehearsal before their real cutover, which is exactly why we rehearsed. Before moving to phase two we changed three things: invalidation became part of the switch, egress declarations went into the readiness check, and every team’s status went onto a shared dashboard.

13. Phase two

Story Phase two was L2.5 and the L3 long tail. More teams, less traffic each, and a different kind of problem. Phase one was mostly engineering. Phase two was mostly adoption: teams with other priorities, and some services whose owners had changed after reorganisations.

Story What unblocked the tail was a mix of things. Weekly office hours. Publishing per-team status to leadership, so priorities were visible. Finding owners for services nobody owned. And fixing common blockers in the platform, not team by team. Phase two involved smaller services, but it took about as long as phase one.

14. How adoption worked

I had no authority over those teams, and mandates don’t work at 178 of them. What worked was making the platform the cheaper path: adopt a shard descriptor, use the onboarding tool, and don’t build placement or egress rules yourself. I also helped teams onboard directly.

Story One team pushed back hard. They had custom deployment scripts and didn’t want to change. When we dug in, it wasn’t stubbornness: the shard descriptor genuinely couldn’t express their scaling pattern. We added that to the model, they migrated, and the same fix helped several other teams later.

Story We tracked adoption with status the tool computed from its checks, not status teams reported themselves. Self-reported status is always optimistic.

15. Production issues, and how we fixed them

Story The most serious one was during an early production cutover. For a few minutes, a small share of requests still reached the commercial runtime, because some Router instances hadn’t refreshed tenant context yet. Users saw errors. We caught it from per-tenant error rates. The immediate fix was forcing a refresh. The lasting fix was making the switch wait until every Router confirmed the new context.

Story A second one came from a shard replacement during maintenance. The cached placement still pointed at the old shard for some requests. We fixed the order of operations: update the shard configuration repository first, then invalidate the cache, then route new traffic. We also added an alert for any request that reaches a retired shard.

Story In both cases, the fix wasn’t ’be more careful’. We changed the process so that class of failure couldn’t happen again.

16. What I’d do differently

Story Two things. I’d make cache invalidation a core part of the design from day one, not something we hardened after the pilot. And I’d publish the platform contract and the shard descriptor model earlier. We spent time in phase one negotiating things with teams that a written contract would have settled.

Architecture decisions

7“Why split the control plane from the data plane?”Answer

They do different jobs. The control plane provisions environments: AWS accounts, VPC, databases, storage, keys. That work is rare, slow and can fail.

The data plane serves customer requests. That is constant and latency-sensitive. So the control plane is shared and stays off the request path. Once a tenant is provisioned, its metadata reaches the runtime through tenant context, so requests never wait on provisioning.

Next they ask: “What happens to customers if the control plane is down?”

Avoid: Forgetting the handoff. Say how provisioned state reaches the runtime.
8“Why a separate Shard Manager? Why not resolve the shard in the Router?”Answer

We considered putting shard resolution in the Router. One component, one lookup. It was the simpler option.

We separated them because the two facts change at different rates. Tenant context is identity. It rarely changes and caches well. Shard placement is operational. It changes on failure, maintenance, deployment, migration and capacity changes. In one component, a stable thing gets tied to a volatile one. The cost was one more component and one more hop for isolated tenants.

Next they ask: “What happens when a shard fails?”

Avoid: Calling it ’separation of concerns’ and stopping. Say which concerns and why they differ.
9“What exactly is a shard?”Answer

A shard is a logical isolated deployment for one tenant and one product. For example, Tenant A’s Jira shard. It contains several replicas.

It is not a single machine, and it is not a data partition. If traffic rises, replicas scale. The shard itself stays the same.

Next they ask: “What happens when one replica fails?”

Avoid: Saying a shard is an instance. Every later answer about scaling and failure then comes out wrong.
10“Why is tenant context cached in the Router?”Answer

The Router is on every request. Calling the Tenant Context Service each time would add latency to everything.

Tenant context rarely changes, so caching it is safe. On a miss the Router calls the service and fills its cache. The catch is invalidation. When a tenant’s environment changes, the cache must be refreshed.

Next they ask: “What if the cache is stale when a tenant migrates?”

Avoid: Not mentioning invalidation. It is the one real risk of this choice.
11“Why split the service descriptor into shard descriptors?”Answer

A service descriptor assumed one runtime: one set of CPU, memory, keys, database and scaling settings.

With a runtime per tenant, that breaks. So one product service now has many shards, each with its own shard descriptor. A tenant can be sized for its own traffic without touching the service or other tenants. And teams adopted a configuration model instead of rewriting code.

✎ Add your detail: How divergence between shard configs was kept under control.

Next they ask: “Doesn’t that multiply your configuration by the number of tenants?”

Avoid: Presenting it as a file-format change. It is what made adoption cheap.
12“Why centralise egress in a gateway?”Answer

Controlling outbound data is a compliance concern that applies to every product.

If 178 teams each wrote their own policy, the guarantee would only be as strong as the weakest one. And a policy that is too loose fails silently. One gateway means one place where policy is checked, reviewed and changed.

✎ Add your detail: How the gateway was kept available, since outbound traffic depends on it.

Next they ask: “Isn’t the gateway a bottleneck or a single point of failure?”

Avoid: Naming a policy engine you have not verified. Say policy-driven enforcement.
13“Why AWS-native scaling instead of Kubernetes?”Answer

Replicas inside a shard scale with AWS Auto Scaling.

Isolation multiplies environments, so every extra moving part is multiplied too. Another orchestration layer would have been a second platform to run inside every isolated environment, for a problem AWS already solved.

Next they ask: “What do you lose by not having an orchestrator?”

Avoid: Sounding like you did not consider it. Say it was a deliberate choice.
14“What was your single most important architectural decision?”Answer

Treating isolation as a platform capability, not a product feature. Everything else follows from it: the control plane, the Router, tenant context, the Shard Manager, shard descriptors and the Egress Gateway.

If they want a second one, it is separating tenant identity from runtime placement.

Next they ask: “What would have happened if you had gone the other way?”

Avoid: Picking a component. Pick the decision the components came from.

Trade-offs

15“What was the biggest trade-off?”Answer

Centralisation. Product teams gave up some local control over deployment and configuration, and the platform became something every product depends on.

In return we got one implementation instead of 178, consistent egress policy, and isolation that future products inherit.

✎ Add your detail: How you protected the platform, since it became a shared dependency.

Next they ask: “How did you reduce the risk of that shared dependency?”

Avoid: Saying there was no downside.
16“Where did you trade latency against correctness?”Answer

Two places. The Router caches tenant context for speed. That is only safe because tenant context rarely changes, and we invalidate on a tenant change.

For placement, the shard configuration repository is the source of truth. The cache only makes lookups fast. If the cache is lost, we lose speed, not correctness.

Next they ask: “What if the cache and the repository disagree?”

Avoid: Treating a cache as the source of truth.
17“Dedicated shards per tenant cost more. How did you justify that?”Answer

Dedicated infrastructure is the requirement. It is what these customers need to use the cloud at all.

Shard descriptors reduce the waste. Each shard is sized to its own traffic, not to the biggest tenant.

✎ Add your detail: Any real cost figures or pricing context you are allowed to share.

Next they ask: “How did you size a new tenant before you had traffic data?”

Avoid: Inventing cost numbers.
18“What did it cost to avoid asking teams to rewrite code?”Answer

The complexity moved into the platform. We had to build and run the Router, the Tenant Context Service, the Shard Manager, the configuration repository and the Egress Gateway.

We accepted that, because one platform team carrying complexity is far cheaper than 178 teams each carrying it.

Next they ask: “Was the platform team big enough for that?”

Avoid: Implying the complexity disappeared. It moved.

Data migration

19“Walk me through how data migration worked.”Answer

It was phased by tier, not done all at once. Every data transfer was encrypted. We provided tooling so each team did not write its own migration.

At the tenant level, the switch was tenant context. Once a tenant’s isolated shard was ready, its context changed from commercial to isolated, and the Router’s cache was refreshed so traffic followed.

✎ Add your detail: How the data physically moved: bulk copy, incremental catch-up, a freeze window. And what the tool did, step by step. Use only what actually happened.

Next they ask: “How did you make sure nothing was lost?”

Avoid: Filling gaps with a textbook migration design. They will drill into it and it won’t hold.
20“How did you make sure no data was lost or duplicated?”Answer

Answer only with what you actually did. If it helps, these are the checks a strong answer usually covers:

Progress is recorded only after the destination confirms a write. Writes are safe to retry, so a retry cannot duplicate. And counts or checksums are compared before traffic moves.

✎ Add your detail: The validation you really ran before switching a tenant.

Next they ask: “What happened when validation found a mismatch?”

Avoid: Claiming exactly-once delivery. Say how retries were made safe instead.
21“What did the migration tool actually do for teams?”Answer

Its purpose was to take work off 178 teams. Every manual step is a step where 178 teams produce 178 different results, and some stop.

One thing it guaranteed centrally was encryption of every transfer, so no team had to get that right on its own.

✎ Add your detail: The three or four steps the tool automated, and what teams still did by hand.

Next they ask: “What did teams still have to do themselves?”

Avoid: Describing the tool without saying what it saved teams.
22“How did you onboard teams onto the platform and the tool?”Answer

Helping teams onboard was part of my role. The shape that works: go hands-on with the first teams to learn what the tooling is missing. Then make it self-serve. When many teams hit the same problem, fix the platform, not the teams.

✎ Add your detail: How you actually ran onboarding: docs, office hours, pairing, a checklist. And one thing early teams taught you.

Next they ask: “What did the first teams teach you?”

Avoid: Only describing documentation.
23“How did you move a tenant from commercial to isolated without breaking requests?”Answer

The isolated shard had to be provisioned and registered first. Then the tenant context changed to isolated.

The risk was the Router cache. Until it refreshed, requests could still go to the commercial runtime. That is a correctness problem, not a speed problem, so invalidation had to be part of the switch.

✎ Add your detail: Whether there was a write freeze or cutover window, and how long.

Next they ask: “What if some requests landed on the old runtime during the switch?”

Avoid: Leaving out the cache. It is the part that shows you ran it.
24“Why was every transfer encrypted, and why centrally?”Answer

These are regulated customers. Their data moving between environments must be protected.

Doing it centrally means it is a platform guarantee for everyone, not 178 separate promises that someone would eventually get wrong.

Next they ask: “Who managed the keys?”

Avoid: Treating encryption as a checkbox. The point is that it is centralised.
25“What was your rollback plan?”Answer

Answer with your real plan. The useful distinction to show: before traffic moves, rolling back is cheap, because you just leave tenant context as commercial.

After customers write data in the isolated environment, rolling back loses those writes. So the plan usually becomes fixing forward after a short window, decided in advance.

✎ Add your detail: Your actual rollback window and whether you ever used it.

Next they ask: “Did you ever roll back?”

Avoid: Saying you could always roll back. After new writes, you can’t cleanly.
26“How did you know a migration was really complete?”Answer

It has to be checked, not self-reported. At 178 teams, self-reported status is always optimistic, and the last 20% takes as long as the first 80%.

✎ Add your detail: The actual definition of done and how it was verified.

Next they ask: “What was the most common reason a team wasn’t really done?”

Avoid: Trusting status updates.

Execution across teams

27“Why were identity and the Global Edge in L0?”Answer

Everything depends on them. No isolated tenant can log in or reach a service without identity and the edge. Nothing else can migrate until they have.

Next they ask: “What did L1 depend on?”

Avoid: Only saying they were important. Say what depended on them.
28“Why did you add an L2.5 tier?”Answer

Some services fit neither L2 nor L3. A fractional tier let us refine the order without renumbering. Renumbering would have broken dashboards, alerts and runbooks keyed to the old tiers.

✎ Add your detail: What kind of services went into L2.5.

Next they ask: “Isn’t a half tier a sign the model was wrong?”

Avoid: Getting defensive. The model was built for multi-tenant only; this was a cheap fix.
29“A team said they had no capacity this quarter. What did you do?”Answer

Find out why first. It is usually one of three things: real capacity limits, a gap in the platform, or disagreement with the approach. Each needs a different response.

The ordering already weighed readiness, so some teams were moved later on purpose.

✎ Add your detail: A real example of a team that pushed back and how it ended.

Next they ask: “What if they simply refused?”

Avoid: Escalating first.
30“Where did the migration stall?”Answer

Be honest. Large migrations stall in the long tail: teams with other priorities, or services with no clear owner after a reorg. Say what you did about it.

✎ Add your detail: Where yours actually stalled, and what unblocked it.

Next they ask: “What would you do differently for the tail?”

Avoid: Claiming it went smoothly. Nobody believes that at 178 teams.

Conflict and disagreement

31“Did you face conflict? Tell me about a disagreement.”Answer

Pick one real disagreement. Two likely candidates from this project, use only if true:

A technical one: whether the Router should resolve shards directly. An ownership one: product teams wanting to keep control of their own configuration.

Tell it fairly. What was their position, why was it reasonable, how was it decided, and what happened.

✎ Add your detail: The real disagreement, the other person’s role, and how it ended.

Next they ask: “Were you right?”

Avoid: Choosing a trivial disagreement to look agreeable, or making the other side look foolish.
32“How did you convince people the extra Shard Manager was worth it?”Answer

Admit the Router option was simpler. Then make it concrete: list the events that change placement, like failure, maintenance, deployment, migration and capacity. None of them change who the tenant is.

Once that list is on the table, tying placement to the Router is visibly a bad coupling.

✎ Add your detail: Who needed convincing, and whether it happened in a review, a doc or a conversation.

Next they ask: “What if they still disagreed?”

Avoid: Arguing from principle instead of from the list of real events.
33“A product team wanted to keep full control of its configuration. How did you handle it?”Answer

Use only if this happened. Separate a real gap from a preference. If several teams need something the model can’t express, that is a platform bug to fix.

If it is a preference, hold the line, because one exception makes the model optional for everyone. Shard descriptors still let teams tune their own shards within the model.

✎ Add your detail: The real case, if there was one.

Next they ask: “Did you ever make an exception?”

Avoid: Saying you never bend, or that you always did.
34“Were you ever overruled?”Answer

If yes, show three things: you made your case properly, you committed once it was decided, and you set a way to find out who was right.

✎ Add your detail: The real decision and what happened after.

Next they ask: “Looking back, who was right?”

Avoid: Telling it as a grievance.

Operations and failures

35“A replica fails. Then a whole shard fails. What’s different?”Answer

A replica failing is handled by the infrastructure. It replaces the replica, and the tenant-to-shard mapping does not change.

A shard being replaced is different. The tenant moves, say from Shard-123 to Shard-456. The Shard Manager updates placement, the cache entry is invalidated, and new traffic follows.

Next they ask: “How long were tenants affected during a shard replacement?”

Avoid: Treating them as the same event. This is the question that shows whether you ran it.
36“The placement cache is lost. What happens?”Answer

Nothing is lost. The shard configuration repository is the source of truth. Lookups are slower until the cache refills, but they are still correct.

Next they ask: “What if the repository itself is down?”

Avoid: Describing the cache as where placement lives.
37“Tell me about a real incident.”Answer

Pick one. Say what happened, how it was found, what you did, and what changed afterwards so that kind of failure could not happen again. The structural change is what they are scoring.

✎ Add your detail: The incident, its impact, and the structural fix.

Next they ask: “How did you find out about it?”

Avoid: A fix like ’we were more careful’. It must stop the whole class of failure.
38“How did you monitor the system?”Answer

Shard health was tracked as part of the shard lifecycle, which is what triggered replacement. Say what else you watched, and be honest about what was thin.

✎ Add your detail: Your real signals and alerts.

Next they ask: “What did you add after going live?”

Avoid: Claiming full coverage without specifics.

Impact

39“What was the impact?”Answer

Isolation became a reusable platform capability instead of 178 separate redesigns. About 178 teams adopted it, and future products get isolation without rebuilding it. It let regulated customers use Atlassian Cloud.

✎ Add your detail: Real numbers only: teams migrated, customers onboarded, time to onboard a tenant.

Next they ask: “How did you measure that?”

Avoid: Inventing metrics. ’I’d have to check the exact figure’ is fine.
40“Why did this matter to the business?”Answer

These customers could not use multi-tenant cloud because of their rules. Without isolation, they could not be cloud customers at all.

✎ Add your detail: Any business context you can share.

Next they ask: “How did that change engineering priorities?”

Avoid: Only talking about technology.
41“How did you measure success?”Answer

Use your real measures. Honest examples of the kind of thing to name, not facts: teams fully migrated, time to onboard a new tenant, incidents during migration.

✎ Add your detail: Your actual success measures.

Next they ask: “Which measure moved least?”

Avoid: Presenting example measures as real ones.

Reflection

42“What would you do differently?”Answer

One or two real things. A good one: treat cache invalidation as a core design concern from day one. A stale tenant context sends requests to the wrong place, and that is a correctness problem.

✎ Add your detail: Anything else you genuinely learned the hard way.

Next they ask: “Why didn’t you do that at the time?”

Avoid: Saying nothing, or something cosmetic.
43“What’s the weakest part of the design today?”Answer

Pick something real and say why you accepted it. Two honest ones: centralisation makes the platform a shared dependency. And per-shard configuration can drift, because settings get added and rarely removed.

Next they ask: “What would it take to fix it?”

Avoid: Blaming things outside your control.
44“What did you learn about leading across teams?”Answer

Mandates don’t scale to 178 teams. Adoption comes from making the platform the cheaper path, and from treating repeated blockers as platform problems rather than difficult teams.

✎ Add your detail: A moment where you learned this.

Next they ask: “Where did that approach fail?”

Avoid: A generic leadership lesson with no example.
45“If you joined a team here doing something similar, what would you tell them first?”Answer

Decide early what belongs to the platform and what belongs to the product. Moving that line later is far more expensive than setting it at the start.

Next they ask: “How would you decide where that line goes?”

Avoid: Re-describing your project instead of giving advice.
15

Your fifteen minutes

A quarter of the interview. It is scored. Running dry after three questions is noticeable.

Lead with these

QuestionWhy
“How does a decision affecting several teams actually get made here?”Tells you whether a Staff engineer can be effective or is just advisory. Listen for a mechanism, not a person.
“What is the most recent architectural decision this team got wrong, and how did you find out?”Tests whether there is a real feedback loop, and whether it is safe to be wrong.
“What would you want someone in this role to have changed a year in?”Gets the real expectation, not the job description.

Then, as the conversation allows

  • “Where does the line sit between what the platform owns and what product teams own?”
  • “What architectural decision made years ago do you still work around?”
  • “What does on-call look like — pages per shift, honestly?”
  • “Is there a cross-cutting migration in flight now? How is it sequenced?”
  • “When two senior engineers disagree on architecture, how does it resolve?”
  • “What separates Staff from Senior here in practice, not on the ladder?”

The close

“Is there anything about my background you’re unsure about?”

Slightly uncomfortable, and it can surface a misunderstanding while you can still fix it.

One page to revise from

The thesis

Isolation is a platform capability, not a product feature. 178 teams — per-product isolation never converges.

The planes

Control plane provisions and manages, shared, off the request path. Data plane serves traffic, dedicated per customer.

The path

Client → Global Edge → Router → Tenant Context → Shard Manager → shard → replicas → data → Egress Gateway.

The decision

Router answers commercial-or-isolated. Shard Manager answers which shard. Identity is static and cacheable; placement is operational and moves.

Shards

A shard is a logical isolated runtime for one tenant and product, holding replicas. Replica failure ≠ shard replacement.

Config

Service descriptor describes the service. Shard descriptor describes one tenant’s runtime of it. That kept adoption cheap.

Migration

L0 identity and edge, L1 shared platform, L2 products, L3 the tail. Ordered by dependency, priority, traffic, risk, readiness.

Do not say

Shard = instance. Cache = source of truth. Kubernetes. A named policy engine. Any number you cannot evidence.

Three sentences to have automatic

  1. The thesis. “Isolation is a platform capability, not a product feature.”
  2. The decision. “Tenant context is static and cacheable. Shard placement is dynamic and operational. Coupling them would make every placement change touch tenant identity.”
  3. The scale. “About 178 teams, phased by dependency, priority, traffic, risk and readiness. I had authority over none of them.”

Architecture, judgement, scope. Almost every question is a drill-down from one of those.
